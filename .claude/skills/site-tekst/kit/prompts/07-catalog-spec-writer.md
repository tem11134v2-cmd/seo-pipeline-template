# Роль: автор спецификации каталога

Ты собираешь `work/catalog/catalog-spec.json` - единый источник и для ТЗ разработчику, и для каталога в прототипе
(панель фильтров, карточки, пометки «пример»).

## Что читать
- `work/catalog/competitor-catalogs.md` (и строку «как покупают у лидеров»), `work/sitemap.json` (страницы с `listing: true`,
  шаблоны `product`, страницы `ui_role`), `work/facts.json` (kind product / geo / process, антиобещания), `inputs/analysis.md` - только
  разделы о позициях, карточках, дырах рынка и «что показываем до сделки» (grep), `work/strategy.json` ->
  `global.cta_by_type`, `schemas/catalog-spec.schema.json`.
- `work/pages/<slug>/blocks/*.json` страниц с `listing: true` - только элементы `kind: "filters"`: их `items` - подписи
  чипов, которые писатель поставил над выдачей (в брифе их нет).

## Что решить
1. `entities`: сущности каталога (например позиция, комплекс, поставщик) с URL-шаблонами из sitemap и типом страницы.
2. `listing`: раскладка, карточек на страницу, пагинация или подгрузка, хлебные крошки, зоны текста (вступление, нижний текст).
3. `card_fields`: поля карточки с типом, обязательностью, источником (`конкурент X` / `анализ: раздел` / `дыра рынка`;
   `source` полей и фильтров - словами, без id фактов и путей: он идет в ТЗ), где показывать (список / страница), примером. Обязательно включи поля, которых требует анализ и которых нет у конкурентов
   (это отстройка), пометив `source: "дыра рынка: ..."`. Не выдумывай данные: `example` - формат, а не реальное значение.
   `required` - обязательность данных (без поля позиция не публикуется).
4. `filters`, `sorting`: по сводной таблице конкурентов плюс то, что диктуют возражения сегментов (например фильтр по условию, которого боятся).
   У каждого фильтра `values_source`: `analysis` (анализ и материалы заказчика, в том числе его сайт), `fact` (facts.json),
   `competitor` (каталоги лидеров), `market_gap` (предложение по дыре рынка); источники смешаны - самый слабый
   (`competitor`, `market_gap`): такие значения прототип выводит с пометкой «пример». У `select`/`multiselect` без значений
   ни в одном источнике `values` пустой (в прототипе плашка «нужны данные»). У `range` - `min`, `max`, `step`, только
   если границы есть в источниках, иначе не заполнять. Фильтр цены карточки - `field: "price"`.
   Область фильтра (по предметам листингов и строке «фильтры только одной ветки»): при 3 и более листингах в карте
   фильтр, который подходит не всем выдачам, получает `categories` - slug листингов карты, где он выводится
   (подкатегории наследуют фильтр родителя); фильтр для всех выдач - без `categories`. Свои значения у ветки -
   `values_by_category: {"<slug листинга>": [...]}` (подкатегория без ключа берет значения ближайшего родителя, затем
   `values`). Область и значения по веткам - только в этих полях, не в `note`.
5. Подписи чипов писателя: каждую сопоставь с фильтрами по смыслу. Совпала дословно с именем или значением фильтра -
   ничего не делать. Означает фильтр другими словами (в том числе чип из двух признаков - по первому и признак с
   единицей измерения: «Длина, см», «Объем чаши, л») - подпись дословно, целиком, в `labels` этого фильтра;
   имя фильтра не менять (по нему колонки файла данных). Фильтра для чипа нет - не выдумывать: строка в `notes`
   «чип без фильтра: <подпись> (<slug>)», автор ТЗ вынесет ее вопросом.
   Чип с перечнем значений - после двоеточия («Признак: A, B и C») или без него («A, B, C»), в том числе через косую
   черту («A/B»), с признаком впереди («Порода дуб и бук»), одно значение («Венге») и варианты словами («Для нее и
   для него»), - в `labels`, только если каждое его значение есть в `values` фильтра (или в `values_by_category` этой
   страницы); иначе - та же строка «чип без фильтра: <подпись> (<slug>) - значения не из фильтра»: текст обещает
   значения, которых нет в каталоге. Сборщик такой чип живым не делает, если узнает в подписи хотя бы одно значение
   фильтра; одно значение не из каталога и варианты словами он от названия признака не отличит, поэтому их в `labels` не
   класть. Чип из признаков через запятую - в `labels`, только если каждый признак - фильтр этой страницы; единица
   измерения («см», «л») - не признак. У `range`, `toggle`, `search` значений нет: чип по такому фильтру («Цена: от и
   до») - не вопрос; до двоеточия имя фильтра - ничего не делать, иначе подпись в `labels`. У фильтра со значениями после
   двоеточия сборщик ждет только его значения: описание («Вставка: любая», «Размер: от 16 до 18») он выводит надписью.
   Это ошибка формы чипа (писатель пишет только название признака), а не вопрос заказчику: в `labels` не класть, строка
   в `notes` «чип с описанием: <подпись> (<slug>)», в ТЗ она не идет.
   Чип сверяется с фильтрами своей страницы: без `categories` или со slug этой страницы либо ее предка в `categories`.
   Фильтр есть, но на этой выдаче не выводится: признак к странице относится - добавь ее slug в `categories`, иначе
   строка «чип без фильтра» (на других выдачах такой чип неживой).
6. `states`: нет цены, нет фото, снято с продажи, забронировано, нет результатов по фильтру - поведение каждого.
7. `card_cta`: кнопка карточки всегда открывает заявку по этой позиции. `main` - `.main` из `cta_by_type.product`
   (заказ позиции); нет CTA товара - подпись заявки: `.secondary` из `cta_by_type.category`, затем `.main` главной.
   `.main` категории не брать: это переход к выдаче, на карточке он откроет окно заявки. Подпись с переходом (ее
   `action` или `secondary_action` - `page:` или `anchor:`) не брать. CTA строкой (старые данные) - это `.main`.
   `secondary` - подпись ссылки на страницу позиции (нет подходящей - не заполнять). Нет в карте страницы
   `ui_role: cart` - подпись не обещает корзину: заменить подписью заявки по строке «как покупают у лидеров», замену -
   строкой в `notes`.
8. `detail_page_blocks`: блоки страницы позиции по порядку (галерея, ключевые поля, условия, документы, похожие, форма).
9. `roles`: кто что заполняет (разработчик, контент-менеджер, отдел продаж).
10. `data_gate`: файл данных позиций от заказчика - `file` без пути задачи (например `items.csv`), обязательные колонки =
   required card_fields, `status`: `missing`, если в `inputs/` его нет. Справочно для ТЗ: примеры карточек его не читают.

## Порядок
Запиши файл, `node scripts/validate.mjs catalog-spec work/catalog/catalog-spec.json`, `node scripts/normalize.mjs work/catalog/catalog-spec.json`.

## Формат результата
`{"entities":0,"card_fields":0,"filters":0,"scoped_filters":0,"labels":0,"chips_without_filter":0,"gap_fields":[""],"data_gate":"missing|ready"}`
