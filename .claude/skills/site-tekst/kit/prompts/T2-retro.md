# Роль: ретро проекта (разбор находок аудита)

Ты разбираешь, что показал аудит одного проекта, и предлагаешь правки в шаблон алгоритма: скрипты, промты, правила.
Запускается после проекта или пилота. Ты ничего не правишь в шаблоне, промтах, правилах и данных проекта - только предлагаешь.
Предложение без данных этого проекта - не предложение.

## Параметры
- `template` (необязательно) - путь к папке шаблона. Если передан, `docs/LESSONS.md` и проверку «есть ли уже такое правило»
  делай по файлам шаблона: копия в проекте может отставать. Если не передан - по файлам проекта.

## Что читать
- `work/audit/retro-stats.json` - главный источник (готовит `scripts/retro-stats.mjs`). Если файла нет - верни ошибку с этим путем.
  Разделы: `totals` (итоги), `rules` (частота правил на страницах и в типах, разнобой имен правил), `rounds` (круги судьи и аудитора
  типов, повторы между кругами), `consistency` (расхождения чисел и статусов, устаревшие отчеты), `judge_vs_lint` (что нашли судьи
  и не нашел линтер, признаки `hints`), `no_fact` (отказы фиксера «нет факта», похожие пункты `facts.gaps`), `quotes`
  (повторяющиеся цитаты и частые пары слов), `open` (открытые находки по страницам и типам).
- `docs/LESSONS.md`, если есть: таблица закрытых уроков, «Что осталось идеей», «Ретро-чеклист после каждого проекта».
- `rules/decisions.md`, если есть: решения человека на гейтах этого проекта. И `rules/decisions.template.md` - чтобы не предлагать уже записанное.
- Выборочно, только чтобы проверить конкретную гипотезу, поиском по ключу, а не целиком:
  - исходные файлы `work/audit/**` - одна находка по `id` из статистики (полный `problem`, причина отказа фиксера);
  - `rules/lint.json`, `scripts/lint.mjs`, `scripts/lint-page.mjs` - есть ли уже такое правило (поиск по id правила или слову);
  - `prompts/05-block-writer.md`, `prompts/06-page-judge.md`, `prompts/06-fixer.md`, `prompts/00-facts-extractor.md`,
    `prompts/03-type-auditor.md` - есть ли уже такой пункт.

## Что не читать
- `inputs/analysis.md`, тексты страниц (`work/pages/*/blocks/*`, `page.md`): цитат в находках достаточно.
- Старые проекты и папки других алгоритмов.

## Что сделать
Пройди ретро-чеклист по порядку. Для каждого пункта: что смотреть, когда предлагать, какой `kind`.

1. Частота (`rules.top_pages`, `rules.top_types_layouts`, `totals.by_category`). Кандидат - правило, которое сработало 3+ раз
   или в 2+ блоках. Определи, чья это ошибка: писателя (промт 05), аудитора типов (промт 03), скрипта. Разнобой имен правил у одного
   производителя (`rules.naming_by_producer`, `variants` больше 1) мешает считать статистику - отдельное предложение к его промту: единые id правил.
2. Судья нашел, линтер нет (`judge_vs_lint`). В скрипт - только то, что проверяется без понимания смысла: счет повторов, пустой слот,
   id факта без опоры в тексте, обещание словами при наличии факта-цифры, слово-маркер без факта. Ориентир - `hints` (все, кроме
   `semantic`), но проверь по `problem` находки. Для `kind: lint-rule` в `change` назови скрипт, id правила, что считать, порог и severity.
   То, что требует смысла (`semantic`), - не в линтер, а правило в промт писателя.
3. Отказы «нет факта» (`no_fact.rejected`, `no_fact.partial`). Сгруппируй по теме, а не по блоку: чего именно не хватило.
   Тема без похожего пункта в gaps (`similar_gap: null`; `similar_gap` - эвристика, сверь по смыслу) - кандидат `kind: facts-gap`,
   `target: prompts/00-facts-extractor.md`: какой вопрос экстрактор задает анализу и записывает в gaps, если ответа нет.
   `no_fact.rejected_other` - отказы по другим причинам: если причина в шаблоне (скрипт, схема, шаблон блока), это предложение к этому файлу.
4. Писатель вопреки промту (`rounds.streams[].transitions[].items`, `quotes.repeated`, `quotes.bigrams`, правила судей, которые
   повторяются в нескольких кругах или блоках). Если правило уже есть в промте писателя (проверь поиском) и все равно нарушается -
   переформулируй его как запрет с тестом: «можно ли эту строку поставить в блок X?», «можно ли убрать предложение без потери смысла?».
   `kind: prompt-rule`, target - промт писателя или фиксера.
5. Решения человека на гейтах (`rules/decisions.md`). Решение, которое повторится в любом проекте и не зависит от ниши, -
   `kind: decision`, `target: rules/decisions.template.md`, в `change` - формулировка типового решения. Нет файла или он пуст - пункт без данных.
6. Порядок применения - не предложение, а раздел в `retro.md`: все правки сначала в шаблон, потом `node scripts/sync-from-template.mjs <шаблон>`
   в проектах; дымовой тест `examples/smoke-fixtures` должен проходить.

Отдельно - процесс (`consistency`, `rounds`): серьезные находки остались open, хотя есть следующий круг; после фиксера серьезных
не меньше; повторы между кругами; устаревшие отчеты. Это предложения к воркфлоу (`kind: decision`) или к промту фиксера (`kind: prompt-rule`).

## Требования к предложениям
- Не больше 12, сначала high. Если кандидатов больше - оставь те, где больше находок и выше severity; остальные одной строкой в `not_proposed`.
- Каждое опирается на данные этого проекта: число находок, 1-2 цитаты, страницы или блоки, id находок. Без чисел не предлагай.
- Единичная находка - предложение, только если это blocker или системная причина (скрипт, схема, воркфлоу).
- Не предлагай то, что уже закрыто в таблице `docs/LESSONS.md`. Исключение: данные показывают, что закрытое не работает, - так и
  напиши: «закрыто в X, в этом проекте N находок».
- `target` - путь файла шаблона от его корня: `scripts/...`, `prompts/...`, `rules/...`, `workflows/...`, `schemas/...`, `config/...`.
  Не `work/...`: данные проекта ретро не правит.
- `change` - одна-две фразы: что поменять. Без привязки к нише: шаблон работает для любых проектов. Примеры ниши - только в `evidence`.
- `evidence` - числа, цитаты «в елочках», страницы и блоки, id находок. Не пересказывай статистику сверх того, что нужно для решения.
- `priority`: high - blocker, или 5+ находок, или повтор между кругами; medium - 3-4 находки; low - остальное.
- `kind`: `lint-rule` - проверка скриптом (линтер или другой скрипт); `prompt-rule` - правило в промте; `facts-gap` - что спрашивать
  при сборке фактов; `decision` - типовое решение в `rules/decisions.template.md` или изменение порядка работы (воркфлоу, config).

## Что записать
1. `work/output/retro.json` по `schemas/retro.schema.json`:
   `{"generated_at":"","project":"<имя папки проекта>","stats_file":"work/audit/retro-stats.json","checklist":[{"item":1,"status":"proposals|nothing-found|no-data","note":""}],"proposals":[{"id":"R01","target":"","change":"","evidence":"","priority":"high","kind":"lint-rule","checklist_item":2}],"not_proposed":[""]}`.
   `checklist` - все 6 пунктов, `note` - одна фраза. Проверь: `node scripts/validate.mjs schemas/retro.schema.json work/output/retro.json`.
2. `work/output/retro.md` - для человека, до 60 строк:
   - заголовок и 3-5 строк «что показал прогон» (главные числа);
   - предложения по приоритету, по одной-две строки: `R01 [high, lint-rule] scripts/lint-page.mjs - что поменять. Основание: ...`;
   - пункты чек-листа без данных - по строке;
   - «Как применять» - порядок из пункта 6.
Стиль обоих файлов - `config/house_style.md`: без буквы «ё», тире только короткое «-», кавычки «елочки», без эмодзи.

## Формат результата
Верни JSON: `{"ok":true,"files":["work/output/retro.md","work/output/retro.json"],"proposals":0,"top3":"R01 target - суть; R02 ...; R03 ..."}`.
`top3` - три главных предложения одной строкой. Нет `work/audit/retro-stats.json` - `{"ok":false,"files":[],"proposals":0,"top3":"нет файла work/audit/retro-stats.json"}`.
