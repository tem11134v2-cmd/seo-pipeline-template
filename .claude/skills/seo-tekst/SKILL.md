# seo-tekst

Скил-оркестратор: продающие тексты коммерческих страниц + HTML-прототип. Запускается **в worktree-сессии**. Порт авторской услуги У5+У6-Ф1 (claude.ai) с идеями из proto-v3 - см. [ADR-015](../../../docs/adr/015-tekst-task-type.md).

**Два уровня работы:**
- **Проектный (один раз):** анализ ЦА (`audience-analyst`) + стратегия оффера (`offer-strategist`) + после гейта - блок-план всех страниц в две половины (`block-planner` решает состав и порядок блоков, `slot-mapper` разворачивает их в слоты и лимиты); в финале текстов - кросс-страничный аудит (`site-reviewer`). Результат анализа согласуется с заказчиком (Google Doc) ДО написания текстов.
- **Постраничный (веером, параллельно):** `direction-scanner` разведывает контент топ-10 по каждому направлению -> `page-writer` пишет копию по своему blueprint (каталоги BLOCKS/COPY он НЕ читает - только VOICE.md, контекст писателя тощий, см. ADR-020/021) -> `copy-auditor` чистит -> `prototype-builder` собирает HTML поверх kit (по умолчанию ч/б wireframe). Десяток страниц идут пачками.

**Две клиентские точки в Google Drive:** `Analysis_<slug>.docx` (на согласование) и `Texts_<slug>.docx` (финальные тексты). Прототипы отдаются локальными `.html`-файлами.

FAQ / возражения / плитку тегов / перелинковку / SEO-нормализацию НЕ делает - это отдельный скил **/seo-faq** (фаза 2).

## Аргументы
```
/seo-tekst [--from-structure <NNN>] [--from-table <путь>] [--from-analysis <NNN>] [--from-brief [<путь>]]
           [--mode A|B] [--review|--auto] [--theme <палитра>]
           [--scan-leaders|--no-scan] [--recon|--no-recon] [--resume]
```
- Без источника - скил **спросит** (шаг 1b).
- `--from-structure <NNN>` - «да»-страницы из `structures/<NNN>-*/` (самый богатый путь: маркеры + конкуренты + анализ рядом).
- `--from-table <путь>` - готовая таблица URL/Тип/Маркер[/запросы] (csv/tsv).
- `--from-analysis <NNN>` - направления из `analyses/<NNN>-*/brief.json` (черновой список, уточнить вручную).
- `--from-brief [<путь>]` - **АВТОНОМНЫЙ источник** (ADR-031): ни структуры, ни анализа, ни `ЗАКАЗЧИК.md` нет - только бриф/ТЗ заказчика (можно несколько файлов, можно текстом в чат). Состав страниц собирается из фактуры (`intake-analyst` -> `pages-planner`) и подтверждается на гейте шага 2a. Для проектов, где SEO не покупается (например сайт делает партнёр-разработчик по своему ТЗ). Поисковых проверок в этом источнике **нет принципиально**: ни частотностей, ни оптимизации под выдачу.
- `--mode A` (по умолчанию) - новый сайт; `--mode B` - существующий (direction-scanner сканирует свои живые страницы, page-writer берёт из них фактуру). Ось независима от источника; для `--from-brief` практически всегда `A` (сайт ещё делается) - `B` осмыслен только если у страниц есть URL живого сайта под переделку.
- `--auto` (по умолчанию) - автономно, единственная обязательная пауза = согласование анализа заказчиком. `--review` - добавляет паузу после текстов (до сборки прототипов).
- `--theme <палитра>` - тема прототипа. **По умолчанию `wireframe` (ч/б): согласование текста без споров о дизайне.** Цветные (`premium|b2b|mass-services|ecommerce|saas|military-dark`) - только если заказчик попросил; `strategy.design_theme` от offer-strategist остаётся в запасе для финального сайта.
- `--scan-leaders` / `--no-scan` - доказательный подбор блоков по лидерам (шаг 2b). По умолчанию ВКЛ, если есть лидеры (источник структура/анализ) - **обязателен для каталогов**; `--no-scan` выключает (быстрее, по статической матрице).
- `--recon` / `--no-recon` - контент-разведка топ-10 по КАЖДОМУ направлению (шаг 2c, `direction-scanner`): что публикуют однотипные конкуренты, must_have/gaps. По умолчанию ВКЛ. В mode B шаг выполняется даже при `--no-recon` (сканируются только свои живые страницы - вход block-planner).
- `--resume` - продолжить по `meta.json`.

## State machine
```
init -> pages-ready -> audience-done -> strategy-done -> analysis-shared
     -> [approved] -> blueprints-ready -> texts-written -> copy-audited
     -> site-reviewed -> verified -> texts-shared -> prototypes-built -> completed

--from-brief вставляет два состояния в начало:
init -> intake-done -> pages-drafted -> pages-ready -> (дальше как обычно)
```
`analysis-shared -> approved` - **клиентский гейт** (revising-цикл, как /seo-analiz). `meta.json` - источник истины, обновляется `bash .claude/hooks/update-meta.sh <texts_dir> <state>`.
`intake-done` / `pages-drafted` - только у источника `--from-brief`; остальные источники идут из `init` сразу в `pages-ready`.
**Legacy (задачи, начатые до ADR-021):** state `approved` + blueprints на все страницы -> считать `blueprints-ready`; state `texts-written` без `site_audit.json` -> прогнать 6c (идемпотентно) и дальше по цепочке.

## Артефакты
```
texts/NNN-<slug>/
├── meta.json              # state + drive (analysis/texts) + revisions
├── inputs.json            # slug/domain/регион/ниша/УТП/запрещёнки + реквизиты (company,inn,ogrn,address,email,phone)
├── facts.json             # ЕДИНЫЙ ИСТОЧНИК ИСТИНЫ: реквизиты/гарантия/числа (все цифры сайта - ТОЛЬКО отсюда)
│                          #   + словарь проекта `lexicon` (опц.): locked (дословные слова заказчика) /
│                          #   translate (внутренний термин -> слова клиентов) / canonical (одна мысль = одна формулировка)
├── brief_raw.txt          # (--from-brief) исходная фактура, если заказчик прислал текстом
├── intake.json            # (--from-brief) факты с провенансом + gaps + conflicts (intake-analyst)
├── ВВОДНЫЕ.md             # (--from-brief) человекочитаемый конспект фактуры
├── pages_draft.json       # (--from-brief) черновой состав страниц + вопросы на гейт (pages-planner)
├── pages.json             # целевые страницы (read-tekst-input)
├── leader_blocks.json     # (опц.) матрица покрытия блоков лидерами по типу + фишки (leader-block-scanner)
├── recon/<slug>.json      # (опц.) контент-разведка топ-10 направления: must_have/gaps/офферы; в mode B + own_page (direction-scanner)
├── audience.json          # анализ ЦА (audience-analyst)
├── strategy.json          # стратегия оффера (offer-strategist)
├── blueprints/<slug>.draft.json # ЧЕРНОВИК блок-плана (block-planner): состав и порядок блоков, функции Р/Д/К/В, цели/боли, режим блока
├── blueprints/<slug>.json # ФИНАЛЬНЫЙ блок-план (slot-mapper): тот же состав, развёрнутый в слоты, char-лимиты и правила заполнения
│                          #   Читают писатели и все нижестоящие - ТОЛЬКО финальный файл; черновик служебный
├── site_audit.json        # кросс-страничный аудит: самоповторы/уникальность H1/консистентность фактов + вердикт (site-reviewer)
├── verify_report.json     # независимая вычитка: функции/баланс блоков, факты, словарь, decisions, чистота (tekst-verifier, НЕ чинит)
├── HANDOFF.md             # контракт передачи дизайнеру/разработчику: что сохранить дословно, что переопределяется, чего намеренно нет (build-handoff.mjs)
├── Analysis_<slug>.docx   # КЛИЕНТУ на согласование (-> Google Doc)
├── pages/<page-slug>/
│   ├── page.json          # тексты блоков (page-writer): blocks[] (type/fragment/h2/slots/opts) + title/description
│   │                      #   `fill_notes` - ТОЛЬКО дыры фактуры заказчика строками `[ЗАПОЛНИТЬ: ...]` (уезжают в docx, HANDOFF, прототип)
│   │                      #   `notes_internal` - СЛУЖЕБНОЕ: пометки агентов друг другу (что срезано, что перепроверить, почему так).
│   │                      #   В клиентские документы не выводится ничем; сборщики его не читают
│   ├── manifest.json      # копия + рендер-решения (prototype-builder)
│   └── prototype.html     # ФИНАЛ - self-contained прототип (build-prototype.mjs)
├── Texts_<slug>.docx      # КЛИЕНТУ финальные тексты (-> Google Doc)
└── share.json             # ссылки Drive (analysis + texts)
```

## Алгоритм

### 0a. Проверка worktree
```bash
GIT_DIR=$(git rev-parse --git-dir); COMMON=$(git rev-parse --git-common-dir)
```
`GIT_DIR == COMMON` -> main. Предупредить (не блокировать): «Тексты в main; для многозадачности переоткрой с галочкой worktree».

### 0b. Parse args
`from_structure / from_table / from_analysis / from_brief / mode (A) / review|auto (auto) / theme / resume`.
`--from-brief` без пути - фактуру спросим в чате (шаг 1c).

### 1. Setup

**1a. `--resume`** - найти `texts/<NNN>-*/`, прочитать `meta.json`, спросить «продолжить с state `<state>`? [Y/n]», перейти к ветке после state. Особые случаи:
- `init` + источник brief: к шагу 1.5. `intake_sources` брать из `meta.json`; ключа нет (задача начата до этой версии) или файлы по путям исчезли - спросить фактуру заново, не догадываться.
- `intake-done` (только brief): к шагу 2a. `intake.json` есть - НЕ пере-собирать интейк.
- `pages-drafted` (только brief): `pages_draft.json` есть, но состав ещё не подтверждён гейтом (или подтверждён, а `pages.json` не собран). Показать гейт 2a заново, затем шаг 2. Ответы, уже вписанные в `pages_draft.json`, показать как текущий вариант - не спрашивать по второму кругу то, что закрыто.
- `pages-ready`: если скан лидеров не отключён и `leader_blocks.json` отсутствует - сначала шаг 2b; если разведка не отключена и папки `recon/` нет - шаг 2c; затем шаг 3. **Для brief-источника порядок обратный: сначала 2c, потом 2b** (лидеры выводятся из recon, см. фазу разведки).
- `approved`: смотреть на `blueprints/` (шаг 6a двухчастный, см. 6a1/6a2):
  - **финальный** `<slug>.json` есть на КАЖДУЮ страницу pages.json -> шаг 6a пропустить целиком, считать `blueprints-ready`, к 6b (готовые blueprints НЕ перегенерировать - под них могли быть написаны page.json);
  - финальных нет (или неполны), но есть **черновики** `<slug>.draft.json` -> выполнить только **6a2** (`slot-mapper`) по страницам без финального файла; состав НЕ перепланировать;
  - нет ни того ни другого -> 6a1 + 6a2 с `pages_subset` = только недостающие slug.
  - **Задачи, начатые до разделения планировщика** (есть финальные `<slug>.json`, черновиков нет): это норма, шаг пропускается по первому правилу - черновики задним числом не собирать.
- `texts-written`: прогнать 6c заново (copy-auditor идемпотентен), state по завершении - `copy-audited`.
- `site-reviewed`: к шагу 6e (верификатор). `verify_report.json` уже есть с `verdict: "pass"` - шаг пропустить, к 7; `needs-fix` / `fail` - отработать 6e по ветвлению.
- `verified` и позже: как раньше. **Задачи, начатые до ADR-035** (нет `verify_report.json`, state `site-reviewed`) - прогнать 6e один раз и идти дальше; state `texts-shared` без `verify_report.json` не переигрывать (тексты уже у заказчика).

**1b. Источник (фрэш-старт)** - если ни один `--from-*` не задан, спросить:
```
Откуда берём страницы для текстов?
  1. Из структуры (NNN) - возьму «да»-страницы из structures/NNN-*/ (маркеры + анализ рядом).
  2. Таблицей - URL / Тип / Маркер [/ запросы] (csv/tsv/построчно).
  3. Из анализа (NNN) - черновые направления из брифа (уточним вручную).
  4. От брифа (автономно) - SEO по проекту не делалось: соберу состав страниц из вводной
     фактуры и подтвержу его с тобой. Нужен бриф/ТЗ (файлы или текст).
```
Если в проекте нет ни `structures/`, ни `analyses/` - вариант 4 предложить первым (остальные всё равно перечислить: таблица может лежать сбоку).

**1c. slug, NNN, регион, УТП, реквизиты -> папка.**
- Источник структура: `structure_dir/inputs.json` -> slug, domain, region; `analysis_dir/brief.json` -> УТП-блок. **NNN texts зеркалит NNN структуры.**
- **Реальные поля `brief.json`** (от brief-structurer, маппинг в inputs.json): `company_name`->brand_name, `niche`, `region`, `business_type`, `keyso_base`, `utp_technical/service/social`, `assortment`, `forbidden_wordings`, `not_in_assortment`, `ca_data` (строка - данные ЦА), `client_target_queries`. (Не `brand_name`/`forbidden_phrasings` - таких полей нет.)
- Источник таблица/анализ: из корневого `ЗАКАЗЧИК.md` (`.claude\scripts\_node.cmd .claude\scripts\_client.mjs --field "<поле>" ЗАКАЗЧИК.md`) взять бренд, регион, реквизиты (Название/ИНН/ОГРН/Юр.адрес/Телефон/Email), УТП, стоп-слова. Чего нет - спросить (реквизиты можно отложить плейсхолдерами `[... - требует уточнения]`). NNN - следующий свободный в `texts/`.
- **Источник brief (автономный).** `ЗАКАЗЧИК.md` в таких проектах обычно НЕТ - не считать его отсутствие ошибкой (есть - прочитать как ещё один источник фактуры).
  1. **Получить фактуру.** Путь передан флагом - взять его. Не передан - спросить: «Пришли бриф/ТЗ - файлы (дай пути, не вставляй содержимое в чат) или текст, я сохраню сам. Минимум: чем занимается компания и в каком городе.»
  2. **Разложить по путям, НЕ читая в свой контекст** (как /seo-analiz 1b): дал пути - собрать список, не открывать `Read`'ом; вставил текст - одним `Write` сохранить в `<texts_dir>/brief_raw.txt` и дальше оперировать только путём. Собрать `intake_sources = [{path, label, type}]` и **записать его в `meta.json`** (ключ `intake_sources`) - иначе после `--resume` из состояния `init` пути к файлам заказчика потеряны, они больше нигде не хранятся.
  3. **slug** - из первого источника одной попыткой (без MCP) выделить домен (если будущий адрес известен) или связку ниша+регион: `slug = "montazh-ventilyacii-kazan"`. Для этого можно прочитать только шапку/первые строки файла, не весь массив. NNN - следующий свободный в `texts/`.
  4. `inputs.json` и `facts.json` на этом шаге **НЕ заполнять фактами** - фактов ещё нет, интейк не отработал (правило «факт раньше утверждения», CLAUDE.md). Записать только стаб: `{slug, source:"brief", mode, region_yandex:null, region_name:null, niche:null}`. Полностью они пишутся на шаге 2a, когда есть `intake.json` + ответы заказчика.
- Создать `texts/<NNN>-<slug>/`. **Записать `.claude/tmp/current-task.txt = texts/<NNN>-<slug>/`** (без этого pre-commit откажет).
- Записать `inputs.json` (slug, domain, region_yandex, region_name, niche, business_type, keyso_base, source, mode, **brand_name** (из brief.company_name), utp_technical/service/social, assortment, **forbidden_wordings**, **not_in_assortment**, **ca_data**, client_target_queries + legal-блок `company, inn, ogrn, address, domain, email, phone, date` (+ `schedule`, если известен режим работы) из ЗАКАЗЧИК.md или плейсхолдеры) и `meta.json` (state init, review/auto, source, started/updated).
- Записать **`facts.json`** - единый источник истины (v4). Из брифа/inputs:
  ```json
  { "jur": {"entity":"<ООО/ИП + назв>", "brand_face":"<имя/роль в продающей части>", "requisites":{"inn":"","ogrn":"","address":""}},
    "product_guarantee": {"what":"<точная формулировка>", "guarantee":"<финальная согласованная>", "deadlines":"", "prices":"<из прайса или [ЗАПОЛНИТЬ]>"},
    "numbers": [ {"label":"лет на рынке","value":"","publish":"as-is|alt|no"} ],
    "opsec_restricted": [],
    "lexicon": {
      "locked":    [ {"phrase": "<дословная формулировка заказчика>", "source": "<откуда: бриф / созвон 14.03 / правка круга 2>"} ],
      "translate": [ {"internal": "<как называет заказчик>", "public": "<как называют клиенты>", "why": "<почему внутренний>"} ],
      "canonical": [ {"thought": "<какая мысль>", "wording": "<единственная формулировка>", "where": "все страницы | страницы услуг"} ]
    } }
  ```
  **`opsec_restricted` по умолчанию ПУСТОЙ массив.** Заполняется ТОЛЬКО для деликатных ниш (оборонка, медицина, опасные производства) и только теми категориями, которые заказчик прямо просил не публиковать (`личность`, `геолокация`, `поставщики`, `места/даты`). **Непустой массив = режим OPSEC включён:** `page-writer` вычищает эти категории из текстов, `tekst-verifier` считает их появление находкой `critical`. Обычной услуговой компании OPSEC не нужен - категории «на всякий случай» молча обезличат нормальные продающие тексты.

  **`lexicon` - словарь проекта. Ключ необязательный: нет его - писатель, копи-аудитор и кросс-страничный контролёр работают как раньше** (деградация отсутствием данных, ADR-031). Пишет словарь оркестратор (по ходу интейка и гейтов), агенты его только читают - файл у них и так в обязательном чтении, ничего нового читать не нужно. Три списка:
  - **`locked` - дословные слова заказчика.** Не режутся, не перефразируются и не «улучшаются» НИКЕМ - ни писателем, ни аудитором, ни кросс-страничным контролёром, - даже если формально нарушают правила стиля, длину слота или запрет противопоставлений. Заказчик важнее свода: утверждённая им фраза выигрывает у нормы объёма.
  - **`translate` - внутренний операционный термин исполнителя.** Обычные русские слова, которыми заказчик называет свой процесс («связка», «межрегиональная сделка», «сопровождение»): читателю они либо непонятны, либо понятны неправильно. Признаки - заказчик произносит термин свободно и без пояснения, как само собой разумеющееся, и термина нет ни в одной цитате аудитории (`audience.json` summary.quotes). На сайт термин идёт только расшифрованным, и В ПЕРВЫЙ РАЗ - словами аудитории, а не своими. **Таблица задаёт ЛЕКСЕМУ, а не готовый якорь замены:** грамматическая форма подгоняется под предложение («во сколько они обошлись» -> «какой была их стоимость»). Поэтому словарь - вход для агента, а не механическая замена в скрипте.
  - **`canonical` - одна мысль, одна формулировка.** Повторяется на всех страницах ДОСЛОВНО. Синонимическая вариативность «чтобы не повторяться» запрещена - именно она делает сайт лоскутным. Появилась новая формулировка - сначала строка в `canonical`, потом тираж. Область действия - все носители текста: тексты блоков, H1/H2, title, description, alt, подписи кнопок; правка только в одном месте оставляет сайт лоскутным.

  Чего нет - `[ЗАПОЛНИТЬ]`/«требует уточнения», не сочинять. **Все цифры на сайте тянутся ТОЛЬКО отсюда; изменение факта - правка здесь, не по месту. Никакой арифметики на лету** (NPS->%, годовой÷12). offer-strategist/page-writer/faq-builder берут числа из facts.json.
- **Для `--from-brief` два предыдущих пункта откладываются до шага 2a** (см. 1c, п.4): сейчас пишутся только стаб `inputs.json` и `meta.json` (state `init`), `facts.json` не создаётся.

**Что нового в `strategy.json`** (старые ключи на месте, обратная совместимость):
- **`decisions.register` - пятое смысловое решение, РЕГИСТР текста.** Три варианта - это три готовых **первых экрана** (заказчик выбирает текст, а не ярлык), у каждого служебное поле `axes` с координатами: ось А (кто кого выбирает) `продающий|деловой|отбирающий`, ось Б (образность) `функциональный|умеренный|образный`, ось В (дистанция) `официальный|деловой-человеческий|фамильярный`. Координаты считает стратег - оркестратор их не пересчитывает и не выводит заказчику ярлыками.
- **`selling_theses` размечены метками:** выгода покупателя / гигиена (ожидаемый минимум, за него не хвалят) / гордость продавца. Тезис-гордость идёт в текст **только переупакованным** в выгоду покупателя.
- **`proof_inventory` - инвентарь доказательств с уровнями:** 1 - проверяемое третьей стороной, 2 - конкретика с деталями, 3 - утверждение компании. **Третий уровень допустим только в связке с первым или вторым**, сам по себе - пустой звук.
- **`canonical_wordings`** - формулировки, которые обязаны стоять одинаково везде; оркестратор переносит их в `facts.json.lexicon.canonical` (ADR-033) до шага 6b - **кроме строк-плейсхолдеров** (`[ЗАПОЛНИТЬ` / «требует уточнения»), см. 5(б).
- **Обязательный минимум запроса материалов** - что нужно получить от заказчика, чтобы доказательства не остались декларацией. Идёт в секцию «Что нужно от вас для текстов» документа согласования (шаг 5).

Регистра в `strategy.json` нет (старая задача, `--resume`) - всё ниже по цепочке работает как раньше, по умолчанию как деловой.

Завершить ход. На ответе пользователя:
- **выбор + «согласовано»** -> записать выбор в `strategy.json`: для каждого `decisions.<key>.chosen` = индекс варианта (0-based) или строка-свой-текст; что заказчик не уточнил - оставить `null` (page-writer возьмёт `recommended`). Затем `update-meta.sh <texts_dir> approved`, к шагу 6.
  - **Регистр (`decisions.register`).** Выбран НОМЕР -> `chosen` = индекс, и этим же выбраны координаты: ось А/Б/В берутся из `decisions.register.axes[<индекс>]`. Оркестратор ничего не считает и не интерпретирует - координаты уже посчитал стратег на шаге 4. Заказчик отдельно попросил сохранить формулировку из варианта **дословно** -> записать её в `facts.json.lexicon.locked` (`source: "выбор регистра"`); без такой записи писатель штатно пишет первый экран заново по `offer_formula_recipe` в выбранной манере - это не потеря, а объявленное на гейте поведение.
  - Заказчик прислал **СВОЙ текст первого экрана** (строка вместо индекса) -> координаты неизвестны. Записать `chosen` строкой, добавить новое поле `decisions.register.axes_from` = индекс (0-based) того из трёх вариантов, который ближе всего по манере к присланному тексту, и пометить в `decisions.register.notes`, что регистр определяется по ближайшему варианту. Без `axes_from` нижестоящие шаги не узнают ось А и уедут в дефолт.
- **факты, полученные на гейте** -> дописать в `facts.json` (числа, реквизиты, гарантия, материалы; дословные формулировки заказчика - параллельно в `lexicon`, см. ниже) **ДО шага 6a**. Это жёсткий порядок: block-planner отрабатывает facts-gate по `facts.json` и снимет блоки, под которые факты уже пришли, если внести их позже.
  - **Реквизиты пишутся в ДВА места, одним ходом.** `facts.json.jur` (`entity` + `requisites.inn/ogrn/address`) - источник истины, И legal-блок `inputs.json` (`company, inn, ogrn, address, domain, email, phone, date` + `schedule`) - **именно оттуда их берёт `prototype-builder` -> `build-prototype.mjs`** (футер, cookie-баннер, юр-страницы, `tel:`-ссылка). Записал реквизит только в `facts.json` - в прототип он НЕ попадёт: в футере останется `[ИНН - требует уточнения]`, а телефон выродится в заглушку `+7 (000) 000-00-00`. Пропущенные `domain` и `date` не менее заметны: в футере получится «© » без домена и «Редакция от » без даты, а в политике конфиденциальности - «Используя сайт , Пользователь...». **Расхождение между двумя местами недопустимо:** правишь реквизит - правишь оба файла в один заход, иначе тексты и прототип разъедутся по юр-данным.
  - **Материалы с гейта пишутся в `strategy.json`, а НЕ в `facts.json`** (слота под материалы там нет). Кейсы, сертификаты, фото объектов и команды, логотипы, видео: закрытый пункт перенести из `strategy.materials_missing` в `strategy.materials_have` дословно (из `missing` удалить), объём к запуску дописать туда же. Срок тот же жёсткий - **ДО шага 6a**: materials-gate планировщика читает `materials_have`, и внесённое позже уже не спасёт блок от `mode:"шаблон"` (пустая витрина с `[ЗАПОЛНИТЬ]` в каждом значении). Цифры внутри кейса идут в `facts.json.numbers` как обычно - два файла, один заход. Незакрытое остаётся в `materials_missing`: оттуда собираются «Чего ждём от заказчика» в `HANDOFF.md` и секция «Что нужно от вас» в пересобранном Analysis, поэтому устаревший список = повторный запрос присланного.
  - **Mode B: цифры, которые уже стоят на сайте заказчика.** Свести `own_page.facts_seen` из всех `recon/<slug>.json` в список `значение | формулировка | где | страница` и спросить на гейте: «Эти цифры сейчас на вашем сайте - актуальны? Подтвердите, поправьте или скажите снять». Подтверждённые - в `facts.json.numbers` **ДО шага 6a**; формулировку, которую просят сохранить, - в `lexicon.locked` (`source: "живая страница <url>"`). Неподтверждённые остаются `[ЗАПОЛНИТЬ]`. Без этого писатель отбраковывает собственные цифры заказчика как «нет в facts», а верификатор считает их чужими. В mode A шага нет.
  - **Ревизия `facts.json` перед 6a (обязательна).** Файл собран руками, а ошибка в нём тиражируется во все документы разом: ниже по конвейеру её не поймает НИКТО (писателю и аудитору запрещено брать числа со стороны, верификатор сверяет тексты ПРОТИВ этого файла). По каждому изменённому факту: (1) имена и названия юрлиц - по буквам против источника; (2) формулировки заказчика - дословно («аккуратная формулировка вместо корявой» это потеря факта); (3) разрешение и запрет не перепутаны местами (`publish`, `not_in_assortment`, `forbidden_wordings`, `opsec_restricted`); (4) у каждой опорной цифры видно, **к чему она привязана** («3 дня» - от чего до чего). Сомнение - не факт: строка уходит в `[ЗАПОЛНИТЬ]` и в вопрос заказчику.
- **«на ваше усмотрение»** -> оставить все `chosen:null` (берётся `recommended`), `approved`.
- **правки** -> применить (точечно в audience.json/strategy.json или пере-делегировать нужного агента), пересобрать docx, пере-загрузить (новая ревизия в `share.json`), снова пауза. Цикл до approved.
- **правка СОСТАВА страниц** (только brief-источник): поправить `pages_draft.json`, пере-собрать `pages.json` (`read-tekst-input.mjs --from-brief`), затем по диффу:
  - **добавленные** страницы - прогнать по ним `direction-scanner` (шаг 2c) точечно; `audience.json` не пере-собирать, дописать новые slug в `page_links` подходящих портретов (нет подходящего - `page-writer` штатно возьмёт ближайшие, см. его промт);
  - **снятые** - удалить их `recon/<slug>.json`, `blueprints/<slug>.draft.json` и `blueprints/<slug>.json`, если уже созданы;
  - лидеры (`leader_blocks.json`) при изменении состава не пере-считываются - матрица покрытия по ТИПАМ страниц от добавления одной страницы того же типа не меняется. Появился НОВЫЙ тип страницы - прогнать 2b заново.
  Затем пересобрать docx и продолжить цикл гейта.

**Словарь по ходу гейта (все источники, каждый круг правок).** Ответы и правки заказчика - основной материал для `facts.json.lexicon` (схема и правила - шаг 1c): дословная фраза -> `locked` (`source` - `правка круга 2`); его собственный термин, которого нет у клиентов, -> `translate`; формулировка, обязанная стоять одинаково везде, -> `canonical`. Записывает оркестратор ДО шага 6a - позже писатели её уже не увидят.

**Сборка словаря - обязательная работа оркестратора на этом шаге (ВСЕ источники, до шага 6a).** Словарь состоит из двух половин, и **ни один агент их не спаривает**: «как называет заказчик» даёт `intake-analyst` (только `--from-brief`), «как называет то же самое аудитория» - `audience-analyst` полем `audience.json.audience_wordings[]` (`phrase` / `means` / `from`) во всех источниках. Спаривает оркестратор, здесь и вручную:
- **(а) `translate`** - пройти по `audience_wordings[]` и для каждой строки найти, каким словом ТО ЖЕ явление (`means`) называет заказчик. Термины заказчика брать: интейк был (`--from-brief`) - из `intake.json.facts[]`, факты с `field` = `internal_terms` / `client_wordings` / `client_metaphors` / `client_life_before_after` (сам термин в `value`, опора в `quote`; ключей верхнего уровня с такими именами в файле НЕТ); интейка не было (структура/таблица/анализ) - из брифа, `ЗАКАЗЧИК.md` и ответов заказчика на этом гейте. Совпало - строка `{internal: "<слово заказчика>", public: "<phrase аудитории>", why: "<почему термин внутренний>"}`. Пары нет - строка просто не попадает в словарь; подбирать «похожее» слово заказчика самому нельзя.
- **(б) `canonical`** - перенести `strategy.json.canonical_wordings` в `facts.json.lexicon.canonical` (`{thought, wording, where}`). Перенос механический: что должно звучать одинаково везде, стратег уже решил на шаге 4. **Исключение - строка, у которой `wording` содержит `[ЗАПОЛНИТЬ` или «требует уточнения»: её НЕ переносить.** Канон тиражируется дословно на всех страницах и неприкосновенен для аудитора и кросс-страничного контролёра - плейсхолдер в этой роли размножит скобку по всему сайту и заменит собой живую формулировку. Дыра фактуры и так уходит заказчику в секции «Что нужно от вас для текстов»; закрыл её на этом или следующем круге - вписать реальную формулировку в `canonical` тогда же.
- **(в) `locked`** - дословные формулировки заказчика из его ответов на гейте (плюс факты с `field: "client_wordings"` из `intake.json.facts[]`, если интейк был) -> `{phrase, source}`, где `source` - откуда фраза (`бриф` / `гейт состава` / `правка круга 2`). Одну и ту же мысль не заводить и в `locked`, и в `canonical` - две неприкосновенные строки про одно разъедутся.

Все три пусты - ключа `lexicon` нет, всё работает как раньше (ADR-031). Но **пропустить сам шаг нельзя ни в одном источнике**: `audience_wordings` собираются всегда, и без спаривания половина словаря сгорает молча.

### 6a. Блок-план всех страниц (state == approved)
**Guard (resume-идемпотентность):** если ФИНАЛЬНЫЙ `blueprints/<page-slug>.json` уже есть для КАЖДОЙ страницы pages.json - шаг пропустить целиком (`update-meta.sh <texts_dir> blueprints-ready`, к 6b): готовые blueprints не перегенерировать, под них могли быть написаны page.json. Есть только черновики `<page-slug>.draft.json` - выполняется одна вторая половина, 6a2.

**Шаг двухчастный - решения отдельно от механики.** `block-planner` решает, ЧТО стоит на странице и в каком порядке (6a1); `slot-mapper` механически разворачивает принятый состав в слоты и лимиты (6a2). Промежуточного state нет: признак прогресса - файлы (`<slug>.draft.json` -> `<slug>.json`), `blueprints-ready` ставится один раз в конце 6a2.
**Перед вызовом убедиться, что `strategy.json.materials_have/materials_missing` отражают ответы гейта** (шаг 5) - иначе materials-gate снимет в «шаблон» блоки, под которые материалы уже пришли.

**6a1. Состав и порядок блоков (`block-planner`).** Делегировать: `texts_dir`, `project_root`, `mode`. Он читает BLOCKS.md + leader_blocks.json + recon/*.json + pages.json + strategy + facts + audience.summary и пишет на каждую страницу **черновик** `blueprints/<page-slug>.draft.json`: набор и порядок блоков, функция каждого (Р/Д/К/В + `function_why`, ADR-032), цели и боли, режим блока (`рабочий`/`шаблон`/`заглушка`, ADR-035), `page_rules`. Слотов и char-лимитов в черновике нет - это не его половина. В mode B учитывает `own_page` из recon.
- **<= 12 страниц:** один вызов; маркер `.claude/tmp/expected-block-planner-<run_id>.txt = <texts_dir>/blueprints/` (хук проверяет непустоту папки).
- **> 12 страниц:** несколько вызовов пачками по 8-10, ГРУППИРУЯ ПО ТИПУ страницы (anti-duplication внутри типа сохраняется); каждому - `pages_subset` = список slug. Маркер при нескольких вызовах НЕ ставить (single-marker hook на веере даёт ложные отказы).

**Регистр меняет состав блоков.** block-planner читает выбранный заказчиком регистр (`strategy.json.decisions.register`; индекс варианта - `chosen`, если это число, иначе `axes_from` (заказчик прислал свой текст первого экрана), иначе `recommended` (заказчик сказал «на ваше усмотрение»); координаты - `axes[<индекс>]`) и по **оси А** задаёт: сколько мест на странице несут CTA, какой вариант формы (сколько полей, что обещает кнопка), как подаётся цена, допустима ли срочность и появляется ли блок «кому мы не подойдём». **Ось Б** задаёт допустимость метафоры (функциональный - метафор нет, образный - разрешена сквозная). Регистра нет (старая задача, `--resume`: ключа `decisions.register` нет либо индекс не определяется ни одной из трёх ступеней) - работает как раньше, по умолчанию как деловой.
Регистр **расширяет разрешённое, но не сужает запрещённое**: стоп-листы `forbidden_wordings`, тест ФАС, запрет манипуляций и правило «все числа только из facts.json» действуют в любом регистре одинаково.

**Проверка полноты 6a1:** черновик есть на каждую страницу из pages.json; недостающие - пере-делегировать `block-planner` с `pages_subset` = недостающие slug (до 2). С неполным составом к 6a2 не переходить.

**6a2. Слоты и лимиты (`slot-mapper`).** Делегировать: `texts_dir`, `project_root` (при >12 страницах - теми же пачками по 8-10 с `pages_subset`). Он читает черновики + fragments-manifest + BLOCKS.md и пишет **финальный** `blueprints/<page-slug>.json`: тот же список блоков в том же порядке, дополненный `slots` (по форме фрагмента), `limits` (char-метрики) и `rules` (правила формы); поля черновика переносит без изменений. **Состав он не меняет:** добавить, снять или переставить блок может только 6a1 - иначе решение и механика снова слипаются в одном агенте. Маркер: одиночный вызов - `.claude/tmp/expected-slot-mapper-<run_id>.txt = <texts_dir>/blueprints/`; при нескольких вызовах маркер НЕ ставить. Хук тут проверяет только непустоту папки, а в ней уже лежат черновики - поэтому настоящая проверка не маркер, а сверка по файлам ниже.

**Проверка полноты 6a2:** финальный `<slug>.json` есть на каждую страницу, и набор с порядком блоков в нём совпадает с черновиком. Недостающие или разъехавшиеся - пере-делегировать `slot-mapper` с `pages_subset` (до 2). Затем удалить остаточные `.claude/tmp/expected-block-planner-*.txt` и `expected-slot-mapper-*.txt` и `update-meta.sh <texts_dir> blueprints-ready`.
**Писатели каталоги не читают - только свой финальный blueprint** (диета контекста, ADR-020); черновик служебный, ниже по конвейеру его не читает никто.

### 6b. Тексты - веер писателей (state == blueprints-ready)
Прочитать `pages.json`. Делегировать `page-writer` **на каждую страницу, пачками по 6-8** (несколько вызовов Agent в одном сообщении). Параллельные писатели **НЕ пишут expected-маркеры** (полноту проверит шаг 8 + наличие page.json; single-marker hook на веере даёт ложные отказы - см. ADR-015/ADR-012).
Промт каждому: `texts_dir`, `project_root`, `page_slug`, `mode`, (mode B) `page_url`.
После всех: проверить, что у каждой страницы есть `pages/<slug>/page.json`; отсутствующие - пере-делегировать (до 2 раз). `update-meta.sh <texts_dir> texts-written`.

**Служебные пометки не текут заказчику.** В `page.json` два разных поля: `fill_notes` - **только реальные дыры фактуры** строками `[ЗАПОЛНИТЬ: ...]` (их видит заказчик: Texts.docx, HANDOFF.md, подсветка прототипа); `notes_internal` - служебное между агентами («срезан хвост», «перепроверить после ответа по гарантии»), в клиентские документы не выводится ничем. Заметка о процессе в `fill_notes` читается заказчиком как требование к НЕМУ; дыра фактуры в `notes_internal` тихо теряется. Оба поля необязательные - нет их (старая задача) - работает как раньше.

### 6c. Редактор продающего текста - шлюз перед HTML (state == texts-written)
Отдельный проход качества свежими глазами.

**Сначала - механический прогон, потом редактор.** По каждой странице:
```
.claude\scripts\_node.cmd .claude\scripts\verify-copy.mjs texts/NNN/pages/<slug>/
```
и **передать аудитору весь вывод по его странице - и нарушения, и предупреждения**. Предупреждения (`!`/`~`) - механическая часть правил COPY-AUDIT.md, решение по каждому принимает редактор; по коду возврата их не видно (при exit 0 они тоже бывают), не передашь - чинить их некому.

Делегировать `copy-auditor` **на каждую страницу веером** (6-8): читает page.json + COPY-AUDIT.md + facts.json + blueprint + переданный список, **чинит** нарушения на месте по приоритету - **смысл и грамотность первым** (преувеличения/кривые связки/самопротиворечия), затем удар в боль ЦА, затем чистота (утечка кухни Сургай/кастдев, жаргон, штампы, манипуляции, повторы, лимиты). Анти-ИИ-детект НЕ делает (ADR-022). Служебные пометки о своих правках он кладёт в `notes_internal`, а `fill_notes` оставляет под дыры фактуры (см. 6b).

Затем `verify-copy.mjs` по каждой странице ещё раз - уже как гейт:
- **Exit 2 с pre-flight «в page.json нет блоков из blueprint»** - не работа редактора: дописать блок он не может по определению (его контракт - тот же набор блоков). Пере-делегировать `page-writer` как в 6b (до 2), затем по странице copy-auditor + verify-copy. Иначе три круга впустую, и недописанные блоки уедут в `accepted_violations` как «ложное срабатывание».
- **Exit 2 по прочим механическим нарушениям** - `copy-auditor` этой страницы со списком (до 2).
- **Exit 1** (нет page.json) - `page-writer` как в 6b (до 2), затем по странице copy-auditor + verify-copy.

Аналог post-валидатора HTML, но для копирайта: не прошёл - правим ТЕКСТ, прототип не собираем. Пока идёт цикл правок state остаётся `texts-written`; когда verify-copy.mjs прошёл по всем страницам - `update-meta.sh <texts_dir> copy-audited`.

**Аварийный выход из цикла (обязателен).** Третья неудача подряд по одной странице - НЕ тупик и не повод дать аудитору «дочинить» до зелёного: валидатор может ошибаться (законный отраслевой термин, честный дедлайн с датой), и тогда цикл заставляет портить корректный текст. Записать в `meta.json` массив `accepted_violations: [{page, rule, why}]` (что именно осталось и почему это сочтено ложным срабатыванием), вывести их в финальной сводке отдельной строкой и **идти дальше**. Решение о ложном срабатывании принимает человек, а не цикл.

### 6d. Кросс-страничный аудит сайта (state == copy-audited)
То, что не видно на одной странице: сайт из 10 страниц, написанных под копирку одними фразами, читается лениво и подрывает доверие. Маркер: `.claude/tmp/expected-site-reviewer-<run_id>.txt = <texts_dir>/site_audit.json`. Делегировать `site-reviewer` (один вызов на проект): `texts_dir`. Он читает ВСЕ pages/*/page.json + VOICE.md + decisions + facts.json + точечно blueprints (limits/covers) и inputs (forbidden_wordings) и: межстраничные самоповторы **пояснительной прозы** -> переписывает по делу страницы; H1/Title - уникальность; consistency decisions; конфликты цифр между страницами -> по facts.json; сквозной проход по утечке кухни/сленгу/перегибу. **Канон (строки facts.json, включая `lexicon.locked` и `lexicon.canonical`, тексты decisions, дословные слова заказчика, формула H1) он повторяет дословно и НЕ перефразирует** - дословный повтор факта между страницами это признак цельного сайта, а не дефект ([ADR-033](../../../docs/adr/033-project-lexicon.md)).
После его правок - **строго в этом порядке, механический гейт последним** (site-reviewer правит текст, и всё, что ловит только скрипт - тире, буква ё, лимиты H1/Description, ложная срочность, - иначе уедет мимо шлюза прямо в Texts.docx):
1. **по `site_audit.json.touched[]`** пере-прогнать `copy-auditor` на каждой странице, где он что-то менял (не только при нарушениях): валидатор не видит ни преувеличений, ни штампов, ни счёта метафор, а site-reviewer - последний, кто трогает текст. `touched` пуст -> пункт пропускается;
2. `verify-copy.mjs` по затронутым страницам - последним (exit 2 -> copy-auditor этой страницы со списком, до 1 раза, затем скрипт снова);
3. **разобрать `unfixed[]`:** строки «кандидат в canonical: "<мысль>" -> "<формулировка>"» перенести в `facts.json.lexicon.canonical` (`{thought, wording, where}`) **до 6e** - страницы он выровнял, но прав писать в `facts.json` у него нет, и без переноса канон не увидят ни верификатор, ни `HANDOFF.md`, ни следующий `/seo-tekst-fix`. Плейсхолдеры не переносить (5(б)). Остальное `unfixed[]` - в сводку.
`update-meta.sh <texts_dir> site-reviewed`.

### 6e. Независимая вычитка - верификатор (state == site-reviewed)
Слой суждения по [ADR-025](../../../docs/adr/025-final-verifiers.md): `copy-auditor` и `site-reviewer` **чинят**, а смешение вердикта и правки прячет ошибку. Верификатор ничего не чинит - он выносит вердикт и оставляет запись.

Маркер: `.claude/tmp/expected-tekst-verifier-<run_id>.txt = <texts_dir>/verify_report.json`. Делегировать `tekst-verifier` (один вызов на проект): `texts_dir`, `project_root`. Он сверяет функции и баланс блоков (ADR-032), все числа против `facts.json` (включая `publish:"no"`), соблюдение словаря `lexicon` (ADR-033), выдержанность `decisions` включая регистр (ADR-034), чистоту клиентского текста и полноту (у каждого блока blueprint есть текст, метатеги заполнены).

**Ветвиться по машинным полям `verify_report.json`** - `verdict`, `counters`, `owner` у каждой находки. Русских подписей («блокирующие», «есть замечания», «ok») в отчёте НЕТ, это подписи для заказчика - по ним не ветвиться.
- **`verdict: "fail"`** - структурный дефект (у страницы из pages.json нет `page.json`, `page.json` пуст или без блоков, blueprint без блоков). Прототипы не собирать, `verified` не ставить: чинить по `owner` (ниже), затем перезапустить верификатор. Два круга без выхода из `fail` - стоп, отчёт человеку.
- **`verdict: "needs-fix"`** (`counters.critical` и/или `counters.important` > 0, тексты целы) - раздать находки **по полю `owner` каждой находки** (до 2 кругов, затем перезапуск верификатора):
  - `owner: "copy-auditor"` - пере-делегировать `copy-auditor` страниц из `issue.page` со списком находок (локальная чистота, `kind: "textual"`/`lexicon`);
  - `owner: "page-writer"` - блок переписывается целиком: пере-делегировать `page-writer` этой страницы как в 6b, затем по ней `copy-auditor` + `verify-copy.mjs` (как в 6c);
  - `owner: "block-planner"` - это **возврат к блок-плану, а не правка текста** (`kind: "structural"`: нет блока Р или Д, перекос В, блок без `function`). Пере-делегировать `block-planner` (6a1) с `pages_subset` = затронутые slug, затем `slot-mapper` (6a2) по тем же страницам, затем 6b -> 6c. Переписыванием слов перекос состава не лечится.
    **Но сначала прочитать `fix_hint`: «материалов нет» перепланированием не лечится.** Находка «нет доказательства (Д), нужны кейсы/сертификаты/фото» - это запрос к заказчику, а не задача агенту: планировщик не имеет права добить страницу возражениями, а переписывание уничтожит уже вычищенный и выровненный текст. Такую - в `meta.json.accepted_violations` («нет материалов, запрошены у заказчика») и в сводку; в перепланирование идут только находки, где материалы ЕСТЬ, а состав собран неверно;
  - `owner: "оркестратор"` - чинишь сам, агентов не звать: `facts.json` (число, реквизит, `publish`, `opsec_restricted`), `facts.json.lexicon`, `strategy.json.decisions`.
  - Находки с `needs_human: true` и находки, пережившие 2 круга, насильно не дочинивать (валидатор мог ошибиться): записать в `meta.json.accepted_violations` как в 6c, вывести в финальной сводке и идти дальше.
- **`verdict: "pass"`** (`counters.critical == 0` и `counters.important == 0`) - дальше. Оставшиеся `counters.minor` не блокируют: вынести списком в финальную сводку и в текст сообщения заказчику при `--review`.
`update-meta.sh <texts_dir> verified`.

### 8. Прототипы - веер сборщиков (state == texts-shared)
Делегировать `prototype-builder` **на каждую страницу, пачками по 6-8**. Промт: `texts_dir`, `project_root`, `page_slug`, `theme` (**по умолчанию `wireframe`** - ч/б согласование текста; цветную из strategy.design_theme передавать только если задан `--theme` или заказчик попросил). Каждый сам гоняет `build-prototype.mjs` + `verify-prototype.mjs` и чинит.
После всех: для контроля прогнать `verify-prototype.mjs` по каждой `pages/<slug>/` (или довериться сводкам сборщиков); отсутствующие prototype.html - пере-делегировать (до 2).
**Сборщик тронул `page.json`** (пустое состояние, текст заглушки, переписанный слот - видно по его сводке) -> пересобрать `build-tekst-docx.mjs` и перезалить новой ревизией в `share.json.texts`: иначе Google Doc с шага 7 разойдётся с прототипом, который заказчик получит на шаге 9. Этот текст не видели ни site-reviewer, ни верификатор - отметить строкой в сводке.

**Документ передачи (обязательно, [ADR-035](../../../docs/adr/035-prototype-handoff-and-modes.md)):**
```
.claude\scripts\_node.cmd .claude\scripts\build-handoff.mjs <texts_dir>
```
Собирает `HANDOFF.md` рядом с прототипами: что сохранить дословно (порядок блоков с обоснованием через функцию Р/Д/К/В, тексты, цифры, формулировки из `lexicon`), что переопределяется дизайном, чего в прототипе намеренно нет (блоки в режиме «шаблон»/«заглушка», недостающие материалы), открытые `[ЗАПОЛНИТЬ]` и правила заполнения. Контракт «это прототип, а не макет» вшит и в сам HTML - комментарием в `<head>`, машинным маркером `prototype-contract` и видимой плашкой в `<body>` (проверяется `verify-prototype.mjs`).
**HANDOFF пересобирается при КАЖДОЙ новой версии прототипов** (в том числе после `/seo-tekst-fix`): порядок блоков меняется, и устаревший документ уведёт дизайн не туда.

## Параллельная работа
Несколько прогонов - каждый в своём worktree, состояния не пересекаются. Внутри прогона:
- **Фаза разведки (2b+2c+3)** - параллельно одним сообщением, без маркеров (см. выше).
- Вееры идут пачками: direction-scanner 4-6, page-writer / copy-auditor / prototype-builder 6-8 (cap против overload).
- Expected-маркер только у одиночного агента, запущенного БЕЗ параллельных соседей (intake-analyst, pages-planner, offer-strategist, block-planner и slot-mapper одним вызовом, site-reviewer); любые одновременные запуски - без маркеров, полноту проверяет оркестратор по файлам.
- 6a1 и 6a2 идут строго последовательно (второй читает файлы первого) - параллельно их не запускать, поэтому маркер у каждого ставится штатно, если вызов один.
- Шаги 1.5 и 2a (`--from-brief`) идут строго последовательно и до всех вееров - там нечего распараллеливать, а гейт состава обязан отработать раньше любых затрат.

## Запреты
- НЕ пиши в корень/общие файлы - только в `texts/<NNN>/`, `.claude/tmp/`. Pre-commit отклонит.
- НЕ редактируй kit (`.claude/skills/seo-tekst/assets/`) во время задачи - read-only.
- НЕ пиши FAQ/SEO-блоки/плитку тегов/перелинковку - это /seo-faq.
- НЕ пропускай клиентский гейт (шаг 5) - заказчик должен согласовать анализ. Для `--from-brief` так же обязателен гейт состава (шаг 2a) - без него тексты пишутся вслепую.
- **НЕ выбирай регистр за заказчика** и не предлагай отбирающий тон без подтверждённого ограничения в `facts.json` (реальный лимит загрузки, ценз, порог входа) - иначе это ложный дефицит, который вскроется на первом же звонке.
- **НЕ ветви пишущих агентов по источнику (ADR-031).** `block-planner`, `slot-mapper`, `page-writer`, `copy-auditor`, `site-reviewer`, `prototype-builder` не должны знать, что автономный источник существует: нехватка данных выражается ТОЛЬКО их отсутствием (`нет leader_blocks` / `нет recon`), никогда - флагом режима в промте. Любой `если источник brief` внутри пишущего агента означает, что качество копирайта начало форкаться.
- В `--from-brief` НЕ добывай поисковые данные (частотности, кластеризацию, позиции) - режим к SEO отношения не имеет. `direction-scanner` (разведка контента конкурентов) исключением НЕ является: он не меряет спрос. Нужна семантика - это другая услуга (`/seo-struktura`), а не этот скил.
- НЕ ставь expected-маркеры на веера (direction-scanner / писатели / аудиторы / сборщики / block-planner и slot-mapper при >12 стр.) - ломает hook. Одиночные вызовы (audience-analyst, offer-strategist, block-planner и slot-mapper одним вызовом, site-reviewer) - маркер ставится.
- НЕ выводи `notes_internal` заказчику и не перекладывай в `fill_notes`: это служебный канал между агентами. В клиентские документы идут только `[ЗАПОЛНИТЬ: ...]`.
- НЕ выдумывай цифры/отзывы/реквизиты - плейсхолдеры `[ЗАПОЛНИТЬ: ...]` / `[... - требует уточнения]`.
- Длинное/среднее тире (— –) запрещено - только дефис (-).
- НЕ используй букву ё - всегда пиши е. Правило для всех клиентских текстов и метатегов (как и запрет тире).
- НЕ запускай другие скилы (/seo-struktura, /seo-statya, ...) из этой сессии.
