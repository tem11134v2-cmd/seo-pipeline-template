# KIT-SPEC - контракт сборки HTML-прототипа (v2, ADR-039)

> Внутренний спек для `build-prototype.mjs` v2, `assemble-prototype.mjs`, `verify-prototype.mjs` v2 и набора ассетов (kit).
> Источник истины для слотов фрагментов, токенов темы, маркеров shell и разметки одно-файлового документа.
> Менять синхронно: `build-prototype.mjs` <-> `assemble-prototype.mjs` <-> `fragments/*` <-> `fragments-manifest.json` <-> `PROTOTYPE-MASTER.html` <-> `prototype.js`/`prototype.css`.

Сборка **двухфазная и детерминированная** (LLM пишет ТЕКСТ и принимает решения - какой блок, какой фрагмент; скрипты занимаются шаблонизацией, CSS/JS никогда не редактируются LLM):

1. **`node build-prototype.mjs <page_dir>`** - рендер ОДНОЙ страницы: из `pages/<slug>/manifest.json` + фрагментов кита пишет `pages/<slug>/render.html` - только отрендеренные блоки страницы. БЕЗ shell, без legal/footer/cookie, без попапов (их больше нет вовсе), БЕЗ normYoFinal/bindHanging - финальную нормализацию делает ассемблер по всему документу. Режима полного per-page prototype.html больше нет.
2. **`node assemble-prototype.mjs <texts_dir> [out.html]`** (дефолт `<texts_dir>/prototype.html`) - сборка ВСЕГО сайта одним self-contained html: shell из `PROTOTYPE-MASTER.html` + `site_manifest.json` + все `pages/<slug>/render.html`. Документ-уровневые данные (legal с phone-placeholder логикой, титул/мета, тема wireframe, логотип/график) берет из `manifest.json` страницы `main_slug`.
3. **`node verify-prototype.mjs <texts_dir>`** - POST-FLIGHT по собранному документу и всем манифестам (см. §7).

## 1. Файлы kit (все в `assets/`)

```
PROTOTYPE-MASTER.html       # shell-каркас документа (head + body + legal/thanks секции + #ptBackbar)
prototype.css               # компонентный CSS (токены темы, без transition - анимации удалены, ADR-039)
prototype.js                # интерактивность: формы (чекбокс-гейт per-form), FAQ, бургер, cookie,
                            #   hash-роутер v2 по window.PT_ROUTES (#p/<slug>, #__back, сервисные якоря)
arrow.svg                   # SVG-стрелка-загогулина к кнопке Hero
fragments-manifest.json     # карта тип-блока -> файл фрагмента + слоты + repeatables + опции
fragments/<type>.html       # HTML-фрагмент одного блока со слотами
themes/theme-wireframe.css  # ЕДИНСТВЕННАЯ тема (ч/б wireframe): :root{} токены + шрифт
legal/footer.html           # футер с реквизитами + ссылками на юр-страницы
legal/cookie-banner.html    # баннер cookie
legal/page-privacy.html     # секция «Политика конфиденциальности» (роутится по #privacy)
legal/page-consent.html     # секция «Согласие на обработку ПДн» (#person-data-consent)
legal/page-cookie.html      # секция «Политика cookie» (#cookie)
legal/page-thanks.html      # секция «Спасибо» (#thanks)
```

Возврат из юр-страниц - ссылка `href="#__back"` (роутер возвращает на последнюю активную страничную секцию, а не на «главную» - страниц в документе много). Ссылок `#mainContent` в ките и в контенте быть не должно.

## 2. Входы сборки: manifest.json + site_manifest.json

**Один манифест = одна страница = одна СЕКЦИЯ итогового документа.** Прототип всего сайта - ОДИН файл `texts/NNN/prototype.html`: служебная стартовая страница-список + все страницы секциями + плашка возврата (ADR-039). Пер-страничных prototype.html больше не существует.

### 2.1 `pages/<slug>/manifest.json` (вход build-prototype.mjs, готовит `prototype-builder`)

```json
{
  "meta": {
    "project": "akva-spb",
    "slug": "ustanovka-septikov",
    "page_type": "Услуга",
    "title": "Установка септиков в СПб - монтаж под ключ за 1 день",
    "description": "<= 160 символов для <meta description>"
  },
  "legal": {
    "company": "ООО Аква-Сервис",
    "brand": "Аква (опц.: бренд шапки, если он не равен юрлицу подвала)",
    "inn": "[ИНН - требует уточнения]",
    "ogrn": "[ОГРН - требует уточнения]",
    "address": "[ЮР_АДРЕС - требует уточнения]",
    "domain": "akva-spb.ru",
    "email": "info@akva-spb.ru",
    "phone": "+7 (812) 000-00-00",
    "date": "06.06.2026"
  },
  "blocks": [
    {
      "type": "hero",
      "fragment": "hero",
      "h2": null,
      "slots": { "h1": "...", "subhead": "...", "cta_label": "Рассчитать стоимость",
                 "bonus": "+ выезд замерщика бесплатно",
                 "plates": [ {"title":"...","text":"..."}, {"title":"...","text":"..."}, {"title":"...","text":"..."} ] },
      "opts": { "arrow": true },
      "fill_notes": []
    },
    {
      "type": "advantages",
      "fragment": "cards",
      "h2": "Почему монтаж под ключ выгоднее",
      "slots": { "items": [ {"title":"...","text":"..."}, {"title":"...","text":"..."}, {"title":"...","text":"..."} ] },
      "opts": { "cols": 3 },
      "fill_notes": []
    }
  ]
}
```

Правила:
- `blocks[].type` - смысловой тип блока (из BLOCKS.md). `blocks[].fragment` - какой HTML-фрагмент рендерить (обычно совпадает или из fragments-manifest).
- `slots` - значения для `{{...}}` плейсхолдеров фрагмента. Массивы -> repeatable-регионы.
- `opts` - модификаторы (варианты верстки/классы): `cols` (3/4), `arrow` (bool), `inverted` (bool, темный блок - только cta-mid, максимум 1-2), `filter` (bool, рейл фильтров product-listing).
- Выделенный тариф - boolean `tariffs[i].featured`: **true ровно у одного тарифа** (это слот, не opt). verify v2 проверяет «ровно один», а не «максимум один»: без выделения блок теряет якорь выбора, с двумя выделение перестает быть выделением.
- `fill_notes` - список пометок для согласования: сборщик и валидатор их только считают (сводка в лог), в docx они выводятся отдельным списком. В HTML сам этот список не рендерится - подсвечиваются вхождения `[ЗАПОЛНИТЬ: ...]` в текстах слотов (см. §3).
- `meta.title` - метатег: **целевая длина 60 символов, потолок 70**. Перенос из `page.json` дословный: сборщик берет title и description от писателя и НЕ сочиняет и НЕ укорачивает их сам (канон текстов один - `page.json`, сборка его не правит). Длиннее потолка - вернуть писателю, а не резать на сборке. `<title>` документа собирается из manifest ГЛАВНОЙ страницы (`main_slug`); title остальных страниц живут в их manifest (для docx и проверок).
- `blocks[].empty_state` - строка из blueprint (что видит человек при нуле элементов в блоке-шаблоне). Сборщик отдает ее фрагменту как `{{empty_state}}` и переносит в HANDOFF.md. **В `subhead` (или любой другой слот писателя) ее класть нельзя:** slots - согласованный текст канона page.json, и подмененный текст не проходил копи-шлюз.
- **Ровно одна форма захвата на страницу** (`type:"form"` встречается 1 раз; в документе - ровно один `id="<slug>__leadForm"` НА СЕКЦИЮ). Pre-footer = микро-конверсия, не дубль формы.
- `legal` - реквизиты заказчика; в shell документа печатается legal из manifest ГЛАВНОЙ (`main_slug`), в манифестах остальных страниц блок дублируется как есть (источник - inputs.json, один на задачу). Выдумывать реквизиты нельзя: нет реквизита - оставь поле пустым или напиши `"[ИНН - требует уточнения]"`, ассемблер обрабатывает оба написания одинаково (пустые ИНН/ОГРН/адрес просто не печатаются). **Телефон - отдельный случай:** он несет `href="tel:"`, а пустая tel-ссылка - намеренное нарушение в `verify-prototype.mjs` (мертвая ссылка в футере хуже отсутствия). Поэтому при пустом `legal.phone` И при пометке-заглушке (строка без 5 цифр подряд) подставляется одна и та же маска `+7 (000) 000-00-00`: ссылка живая, номер заведомо нерабочий, в лог сборки и в предупреждения валидатора идет строка «телефон не заполнен». Руками номер не придумывать ни в каком виде. Полный состав legal - 8 полей: `company, inn, ogrn, address, domain, email, phone, date` (без `domain` в футере остается «© », без `date` - «Редакция от »).
- График работы в шапке: `meta.schedule` -> `legal.schedule` -> **пусто, блок не печатается**. Дефолтной строки нет намеренно: у проекта без офлайна любые часы работы в шапке - выдумка, а проверить ее нечем (верификаторы смотрят `page.json`, оболочку не смотрит никто).
- **`legal.phone_absent: true`** - третье состояние телефона: у заказчика телефонного канала нет вовсе. Пустое поле означает «реквизит не закрыт» и честно печатается маской; решение «телефона нет» снимает блок в шапке, бургере, мобильной панели и футере, и правило `verify-prototype` «нет кликабельного телефона» на такой задаче переворачивается (телефона быть НЕ должно). Ставит оркестратор в legal-блок `inputs.json` по ответу заказчика - эвристикой эти два состояния не различить.
- **`legal.inn_verified` / `legal.ogrn_verified`** (bool) - снимают проверку формата реквизита у `verify-prototype`. Нужны только если реквизит верен, а проверка все же встала; по умолчанию их нет.
- Полей `theme` и `popups` в манифесте v2 НЕТ: тема всегда wireframe, попапы удалены полностью (ADR-039).

`page.json` (вход для docx-сборки, готовит `page-writer`) - то же `blocks[]` с текстом; `fragment` и `opts` уже перенесены из blueprint, но БЕЗ `meta/legal`. В `page.json` есть и `page.description` - метатег Description (<=160) от писателя. `prototype-builder` переносит blocks как есть, meta title/description берет из page.json (от page-writer, сам не сочиняет) и дополняет до `manifest.json` (meta, legal).

### 2.2 `site_manifest.json` (корень `texts/NNN/`, пишет оркестратор - вход assemble-prototype.mjs)

```json
{ "pages": [ { "slug": "main", "title": "Название для списка", "type": "Главная", "order": 1,
               "url": "/uslugi/", "parent": "catalog", "nav": false } ],
  "start": "__index", "main_slug": "main" }
```

- `pages[]` - состав и порядок секций документа; `title` попадает в стартовый список, в плашку возврата и в МЕНЮ сайта; `type` - русский словарь (`Главная | Услуга | Категория | Товар | Инфо`), по нему verify v2 требует обязательные каталожные блоки.
- `url` (опц.) - адрес страницы на живом сайте. По нему ассемблер переводит относительные ссылки из текстов (`href="/arhitektura/"`) в маршруты роутера `#p/<slug>`: в одностраничном документе относительный адрес уводит из файла, поэтому неразрешенный адрес - нарушение verify v2.
- `parent` (опц.) - slug родительской страницы: меню второго уровня. Фолбэк - `dir_slug` (если страница с таким слагом есть), затем плоский список. `nav: false` (опц.) убирает страницу из меню.
- `main_slug` - слаг главной; при ее отсутствии - первая страница по `order`. Из ее manifest ассемблер берет документ-уровень: `<title>`/`<meta description>`, legal (футер, cookie, юр-страницы, телефон в шапке), логотип, график.
- Читают: `assemble-prototype.mjs`, `verify-prototype.mjs` v2. Тон-превью (ADR-038) использует тот же формат: `tone/site_manifest.json` со списком вариантов -> `tone/tone-preview.html`.

### 2.3 Файлы прототипа (итог)

```
pages/<slug>/render.html   - веер prototype-builder (блоки без shell)
pages/<slug>/manifest.json - как раньше (источник истины страницы)
site_manifest.json         - оркестратор (состав, порядок, main_slug)
prototype.html             - assemble-prototype.mjs (весь сайт одним файлом)
```

## 3. Синтаксис фрагмента

Простой mini-template (реализован в build-prototype.mjs, без зависимостей):

| Конструкция | Значение |
|---|---|
| `{{slot}}` | подстановка скалярного слота (HTML-escape по умолчанию) |
| `{{{slot}}}` | подстановка без escape (для уже готового HTML, напр. ссылки) |
| `<!--REPEAT:items-->...{{item.title}}...<!--/REPEAT:items-->` | повтор региона по массиву `slots.items`, внутри `{{item.<field>}}` |
| `<!--IF:opts.arrow-->...<!--/IF:opts.arrow-->` | условный регион по truthy `opts.arrow` |
| `<!--CLASS:cols-->` | подставит `cols-3`/`cols-4` из `opts.cols` (хелпер для вариативных классов). `opts` со значением `true` дает класс БЕЗ значения: `opts.slider = true` -> `slider` |
| `{{@index}}` | порядковый индекс внутри REPEAT (с 1) |

**Дефолты слотов (`slot_defaults` в fragments-manifest.json).** Сборщик подставляет их в ПУСТОЙ слот перед рендером. Ключ вида `items[].url` - поле каждого элемента повторяемого региона. Зачем: адрес ссылки во фрагментах был зашит намертво (`href="#lead"`), и требование «кнопка Подробнее ведет на подстраницу конкретного товара» выполнить было нечем - писатели складывали адреса в `notes_internal`, откуда их никто не подставлял. Дефолт держит прежнее поведение: слот пуст - ссылка ведет на форму своей страницы. Слоты адресов: `hero.cta_href`, `cta-mid.cta_href`, `product-card.items[].url`, `cards.items[].url`, `portfolio.items[].url`, `tag-tiles.items[].url`.

Неизвестный слот -> пустая строка + предупреждение в лог (не падать). После рендера всех блоков build-prototype проходит по собранному render.html и оборачивает каждое вхождение подстроки `[ЗАПОЛНИТЬ: ...]` (из текста любого слота, независимо от `fill_notes`) в `<span class="nx-fill" data-fill>[ЗАПОЛНИТЬ: ...]</span>` - класс `.nx-fill` стилизован в `prototype.css` как пунктирный стикер, чтобы заказчик видел, что надо дозаполнить.

Нормализации е-с-точками (`normYoFinal`) и висячих предлогов (`bindHanging`) в render.html НЕТ - их выполняет ассемблер по ИТОГОВОМУ документу (см. §6), чтобы стартовая секция, плашка и shell тоже были покрыты, а неразрывные пробелы не расставлялись дважды.

## 4. Полный пример фрагмента: `fragments/hero.html`

```html
<section class="pt-hero" id="hero">
  <div class="container pt-hero__grid">
    <div class="pt-hero__text">
      <h1 class="pt-hero__h1">{{h1}}</h1>
      <p class="pt-hero__sub">{{subhead}}</p>
      <div class="pt-hero__cta-wrap">
        <a href="#lead" class="btn btn--primary pt-hero__cta">{{cta_label}}</a>
        <!--IF:opts.arrow--><span class="pt-arrow" aria-hidden="true"><!--ARROW_SVG--></span><!--/IF:opts.arrow-->
      </div>
      <!--IF:bonus--><p class="pt-hero__bonus">{{bonus}}</p><!--/IF:bonus-->
    </div>
    <div class="pt-hero__plates">
      <!--REPEAT:plates-->
      <div class="pt-plate">
        <div class="pt-plate__title">{{item.title}}</div>
        <div class="pt-plate__text">{{item.text}}</div>
      </div>
      <!--/REPEAT:plates-->
    </div>
  </div>
</section>
```

Фрагменты пишутся с «голыми» id и якорями (`id="hero"`, `href="#lead"`) - неймспейс по слагу страницы наводит ассемблер (§6). В фрагментах допустимы только `id` и `href="#..."`/`label for="..."` как ссылки на id; aria-атрибутов с id в ките нет и заводить их нельзя без правки неймспейсера.

Соответствующая запись `fragments-manifest.json`:

```json
{
  "hero": {
    "file": "hero.html",
    "scalars": ["h1", "subhead", "cta_label", "bonus"],
    "repeatables": { "plates": ["title", "text"] },
    "opts": ["arrow"],
    "notes": "1 кнопка (не 2), SVG-стрелка, 3 плашки title+1 строка. H1 44px. Без дисклеймеров."
  }
}
```

## 5. Тема: wireframe-only (`themes/theme-wireframe.css`)

Тема ОДНА - ч/б wireframe; дизайн на этапе прототипа не проектируется вовсе (ADR-039, ранее ADR-021 дефолтом). Шесть цветных ниш-тем удалены с диска (история в git), поля `manifest.theme` / `strategy.design_theme` и флаг `--theme` не существуют. Ассемблер инлайнит `theme-wireframe.css` в `<head>` ПЕРЕД `prototype.css`.

Файл темы - только `:root{}` блок + шрифт, единый словарь токенов (prototype.css работает только с ними):

```css
:root{
  --font: -apple-system, "Segoe UI", Roboto, Helvetica, Arial, sans-serif;
  --bg:#ffffff; --bg-alt:#f6f8fb; --bg-invert:#0f172a;
  --text-primary:#0f172a; --text-secondary:#5b6b80; --text-invert:#ffffff;
  --accent-primary:#1f6feb; --accent-secondary:#0b3d91;
  --border:#e3e8ef; --radius:14px; --shadow:0 6px 24px rgba(15,23,42,.08);
}
```

## 6. Shell (`PROTOTYPE-MASTER.html`) - маркеры и разметка документа

Маркеры-комментарии shell заменяет **assemble-prototype.mjs** (в v1 это делал build-prototype; в v2 build-prototype пишет только render.html и маркеров shell не видит):

| Маркер | Чем заменяется | Источник |
|---|---|---|
| `<!--META_TITLE-->` | `<title>` + og | manifest главной (`main_slug`) |
| `<!--META_DESC-->` | `<meta name=description>` | manifest главной |
| `<!--THEME_CSS-->` | `<style>` содержимое `theme-wireframe.css` (инлайн, self-contained) | кит |
| `<!--PROTOTYPE_CSS-->` | `<style>` содержимое prototype.css | кит |
| `<!--LOGO-->` | БРЕНД в шапке: `legal.brand` -> `meta.brand` -> `legal.company` -> `meta.project` -> "Компания" (escape). Бренд шапки и юрлицо подвала - разные поля: «в шапке Save, реквизиты остаются реквизитами ИП» | manifest главной |
| `<!--SHELL_CTA-->` | надпись кнопки оболочки (шапка, бургер x2, мобильная панель): `meta.cta_label` -> `legal.cta_label` -> "Оставить заявку". Формулировку кнопки заказчик вправе запретить - раньше она была зашита в shell трижды | manifest главной |
| `<!--NAV-->` | меню сайта (в шапке и в бургере): пункты из `site_manifest.pages[].title`, вложенность по `parent` (фолбэк `dir_slug`), `nav: false` исключает. Нет страниц - пусто, шапка как раньше | site_manifest |
| `<!--PHONE-->` | `legal.phone`, в шапке и бургер-меню (escape). Пусто или пометка-заглушка -> маска "+7 (000) 000-00-00" (см. §2); `legal.phone_absent: true` -> блок не печатается вовсе | manifest главной |
| `<!--PHONE_RAW-->` | телефон без всех символов кроме цифр и `+` - для `href="tel:..."` | manifest главной |
| `<!--SCHEDULE-->` | график работы: `meta.schedule` -> `legal.schedule` -> **пусто** (дефолта нет: выдуманные часы работы - такой же сочиненный факт, как выдуманное число) | manifest главной |

**Условные куски shell** (снимает ассемблер; у shell нет scope, поэтому это не `<!--IF:...-->` фрагментов, а плоские маркеры):

| Маркер | Блок печатается, когда |
|---|---|
| `<!--IF_PHONE--> ... <!--/IF_PHONE-->` | телефон заполнен и не снят решением заказчика (`legal.phone_absent` не стоит) |
| `<!--IF_SCHEDULE--> ... <!--/IF_SCHEDULE-->` | `meta.schedule` или `legal.schedule` непусты |
| `<!--IF_CONTACTS--> ... <!--/IF_CONTACTS-->` | есть хотя бы одно из двух (обертка `.pt-phone-block` в шапке) |

Правило одно на оба реквизита: **чего нет в манифесте, того нет в документе**. Дефолт-строка в коде сборки - это факт, вписанный движком от себя, и он переживает все проверки текста: верификаторы читают `page.json`, а оболочку не читает никто.
| `<!--PAGES-->` | внутри `<main id="ptPages">`: стартовая секция `__index` + секции всех страниц по `order` (см. ниже) | site_manifest + render.html |
| `<!--FOOTER-->` | legal/footer.html со слотами реквизитов (пустые ИНН/ОГРН не печатаются - см. LEGAL.md) | manifest главной |
| `<!--LEGAL_PAGES-->` | legal/page-*.html секции (роутятся по hash; возврат - `#__back`) | кит + manifest главной |
| `<!--COOKIE_BANNER-->` | legal/cookie-banner.html | кит + manifest главной |
| `<!--ROUTES_SCRIPT-->` | `<script>window.PT_ROUTES = {"pages":[{"slug":"...","title":"..."}],"start":"__index"}</script>` - строго ПЕРЕД подключением prototype.js | site_manifest |
| `<!--PROTOTYPE_JS-->` | `<script>` содержимое prototype.js | кит |
| `<!--ARROW_SVG-->` | содержимое arrow.svg (внутри hero, если opts.arrow) - единственный маркер, который подставляет build-prototype при рендере фрагмента | кит |

POPUP_*-маркеров больше нет: оба попапа (#popupTime/#popupExit) удалены из shell, prototype.js, prototype.css и манифеста (ADR-039). `transition` в prototype.css отсутствуют, `@keyframes` нет и не появляется.

### 6.0 Разметка страниц, неймспейс и роутер

**Секции.** Внутри `<main id="ptPages">` первой стоит служебная стартовая секция
`<section class="pt-page pt-index" data-page="__index">` - список всех страниц (тип, название, ссылка `href="#p/<slug>"`). Затем по `order` - секции страниц `<section class="pt-page" data-page="<slug>" hidden>` с содержимым `render.html`. Служебные секции thanks/privacy/person-data-consent/cookie - по одной на документ, вне страничных секций.

**Неймспейс id.** Внутри каждой страничной секции ассемблер префиксует ВСЕ id -> `<slug>__<id>` и переписывает ссылки на них: `href="#..."` И `label for="..."` (aria-атрибутов с id в ките нет). ЗАКРЫТЫЙ список якорей БЕЗ префикса: `privacy`, `person-data-consent`, `cookie`, `thanks` - они ведут на сервисные секции документа и остаются глобальными. Ссылок `#mainContent` в контенте быть не должно (юр-страницы правлены на `#__back`).

**Роутер (prototype.js v2, карта - window.PT_ROUTES).** Маршруты `#p/<slug>` (+ `#p/__index`) показывают свою секцию (hidden у остальных); сервисные якоря (thanks/privacy/person-data-consent/cookie) показывают свою служебную секцию; ЛЮБОЙ другой hash (например `#main__lead`) секцию НЕ переключает - штатный скролл браузера по якорю; `#__back` возвращает на последнюю активную страничную секцию (или на старт). Роутер запоминает lastPage.

**Плашка возврата.** В shell над header один элемент
`<div id="ptBackbar" hidden><a href="#p/__index">К списку страниц</a><span id="ptBackbarTitle"></span></div>`;
роутер показывает ее на страничных секциях (кроме стартовой) и подставляет title из PT_ROUTES.

**CTA самого shell** (шапка, бургер, мобильная фикс-панель - раньше `href="#lead"`): класс `pt-shell-cta` и `href="#"`; prototype.js по клику скроллит к форме АКТИВНОЙ секции (`id <activeSlug>__lead`), на стартовой секции - к списку страниц. Формы: чекбокс-гейт в prototype.js per-form (`querySelectorAll('form')`); submit-обработчик ведет на `#thanks` (сервисный, без префикса).

**Пост-обработка ассемблера** (финальный шаг по ВСЕМУ документу, после всех подстановок): `normYoFinal` (е-с-точками -> е) + `bindHanging` (неразрывные пробелы у висячих предлогов, с самопроверкой «менялись только пробелы, иначе шаг пропущен»). Реализации перенесены из build-prototype.mjs; в render.html этих проходов нет.

Итог - **один self-contained .html** (инлайн `<style>`+`<script>`, без внешних запросов, без фреймворков) - совместим с Tilda Zero Block / WordPress.

### 6.1 Контракт передачи в самом файле (два обязательных места, по ОДНОМУ на документ)

Прототип уходит дальше в непредсказуемом виде: файлом, скриншотом в чате, куском текста в ТЗ. Поэтому контракт «это карта СОДЕРЖАНИЯ, а не макет» вшит прямо в shell, в двух местах. Вставляет их ассемблер - по одному на весь документ, в render.html их нет.

**1. Комментарий-контракт - сразу ПОСЛЕ `<meta charset>`, первым содержательным элементом `<head>`.** Порядок именно такой и переставлять его нельзя: окно предсканирования кодировки у браузеров - первые 1024 байта документа, а комментарий-контракт длиннее. Поставишь комментарий выше - объявление кодировки уедет за это окно, и кириллица во ВСЕХ прототипах поедет заказчику кракозябрами. Та же причина записана в самом shell (`PROTOTYPE-MASTER.html`, первые строки), а `verify-prototype.mjs` v2 проверяет окно машинно (charset в первых 1024 байтах). Машинный маркер сразу за комментарием: `<meta name="prototype-contract" content="content-map-not-layout">`. Адресат - тот, кто откроет исходник (дизайнер, верстальщик, разработчик). Состав: что сохранить дословно (порядок блоков как воронка, тексты, цифры, один главный CTA на блок), что можно и нужно переопределить (композиция и сетка внутри блока, число колонок, размеры карточек, типографика, палитра, шрифты, иконки, иллюстрации, объединение или разбиение соседних блоков), и прямой запрет копировать служебную композицию файла.

**2. Видимая закрываемая плашка `.pt-contract` - первым элементом `<body>`, до шапки.** Адресат сразу двое: заказчик (управление ожиданиями - ч/б каркас без предупреждения дает «а почему так уныло», и обсуждение уезжает в визуал вместо содержания) и дизайн-этап (та же инструкция, но словами для человека). Закрывается крестиком: `onclick="this.closest('.pt-contract').remove()"` - inline-обработчик, как остальные интерактивы кита; элемент удаляется целиком, остальное не съезжает. Стили - в `prototype.css`, только токены темы (`--bg-alt`, `--border`, `--text-secondary`, `--text-primary`, `--radius`). Служебная по статусу: мелкий кегль, `@media print { display: none }`, первым экраном как контент не считается.

**Жесткое правило: оба места присутствуют в КАЖДОМ собираемом документе дословно и ровно по одному разу.** Их нельзя выпиливать «чтобы было чище», «заказчик и так в курсе» или «на скриншоте некрасиво» - именно на этих двух местах держится граница между содержанием и дизайном. Текст правится только здесь, в shell, и только вместе с этим спеком.

Ограничение по тексту то же, что и везде: в комментарии и в плашке нет длинных/средних тире и е-с-точками - иначе `verify-prototype.mjs` завернет каждый собранный документ на ровном месте.

### 6.2 HANDOFF.md рядом с прототипом

Полный контракт передачи живет отдельным документом `HANDOFF.md` в корне `texts/NNN-slug/` - его собирает `build-handoff.mjs` (см. ADR-035), прикладывается к .html при отдаче дизайнеру/разработчику. Состав файлов v2: один `prototype.html` на сайт + `render.html`/`page.json` на страницу. Комментарий и плашка внутри файла - короткая версия на случай, если .html поедет дальше в одиночку.

**HANDOFF пересобирается при КАЖДОЙ новой версии прототипа** (в том числе после `/seo-tekst-fix`): порядок блоков в новой версии отличается от старой, и устаревший handoff уведет дизайн не туда.

## 7. POST-FLIGHT ассерты (verify-prototype.mjs v2)

Вход - `texts_dir`. Фатально (exit 1): нет `prototype.html`, нет/битый/пустой `site_manifest.json`. Exit 2 - есть нарушения, exit 0 - ok.

Проверки двух уровней:

**Глобальные (по документу):**
- контракт передачи: `<meta name="prototype-contract">`, РОВНО одна плашка `.pt-contract` (первым элементом body - предупреждение), комментарий-контракт в `<head>`, `<meta charset>` в первых 1024 байтах;
- стартовая секция `__index` существует и ссылается (`#p/<slug>`) на ВСЕ страницы site_manifest; на каждую страницу есть секция `data-page="<slug>"` (hidden - предупреждение);
- `PT_ROUTES`-скрипт присутствует, разбирается и покрывает все страницы; `<main id="ptPages">` есть;
- нет голых дублей id по документу;
- нет попапов (#popupTime/#popupExit) и `transition` в инлайн-CSS (ADR-039);
- нет голых `href="#lead"` (shell-CTA обязаны быть `pt-shell-cta href="#"`) и `href="#mainContent"` (возврат = `#__back`); наличие `#ptBackbar` и `pt-shell-cta` - предупреждения;
- **нет мертвых якорей**: каждый `href="#..."` ведет либо на существующий id документа, либо на маршрут роутера `#p/<slug>` существующей страницы, либо на сервисный якорь (`privacy`, `person-data-consent`, `cookie`, `thanks`, `__back`). Мотив: сцепка двух корректных по отдельности правил (жесткий якорь `#lead` в ките + законное снятие формы по waiver F3) давала страницу, где ВСЕ кнопки ведут в никуда. Ассемблер чинит это сам (перевод на `pt-shell-cta`), сюда доезжает только то, что требует решения человека;
- **нет относительных адресов**: `href="/razdel/"` в одностраничном документе уводит из файла. Ассемблер переводит их в `#p/<slug>` по `site_manifest.pages[].url`; чего нет в карте - нарушение;
- тире/е-с-точками по всему документу (канарейка е-с-точками указывает на assemble-prototype.mjs: normYoFinal живет там);
- непустой `tel:` (заглушка +7 (000) 000-00-00 - предупреждение). При `legal.phone_absent` правило переворачивается: tel-ссылка в документе - нарушение;
- формат реквизитов из manifest главной: ИНН 10 или 12 цифр, ОГРН 13 или 15, контрольная цифра ИНН по алгоритму ФНС. Мерится ТОЛЬКО строка из чистых цифр - пустое поле и пометка «[ИНН - требует уточнения]» законны; снимается флагом `legal.<поле>_verified: true`. Мотив: реквизит уезжает в подвал живого сайта и в HANDOFF, а до этой проверки его формат не смотрел никто на всем конвейере;
- `<header>`, `<footer>`, cookie-баннер - ровно по одному; юр-страницы присутствуют (предупреждение);
- фреймворк/CDN-детект (react/vue/angular/tilda/external-cdn);
- `legal.domain`/`legal.date` из manifest главной (предупреждения).

**Пер-страничные (каждый `pages/<slug>/manifest.json` против его секции):**
- manifest разбирается (битый - нарушение по странице);
- ровно 1 форма НА СЕКЦИЮ (`id="<slug>__leadForm"`), чекбокс `<slug>__f-agree`, submit `<slug>__f-submit` disabled (предупреждение). **Ноль форм - нарушение, КРОМЕ страницы с валидным waiver F3** (`meta.json.selling_floor_waivers`, непустой `source`): снятие формы решением заказчика законно, и валидатор обязан о нем знать - иначе два наших механизма воюют друг с другом, а отчет с заведомо ложным нарушением перестают читать целиком;
- все id секции с префиксом `<slug>__` (голый id = неймспейс не отработал);
- стоп-формулы (COPY-AUDIT.md П.5); pricing: features - непустые массивы строк, featured - boolean и ровно у одного; product-listing: filters[].options - непустые массивы строк;
- каждый `blocks[].fragment` существует в `fragments-manifest.json`;
- обязательные блоки каталожных типов (типы из `site_manifest.pages[].type`): Категория -> `product-listing` с `opts.filter=true`; Товар -> `product-gallery` (ADR-039 п.3);
- H1 присутствует (hero или product-gallery) и содержит маркер (предупреждения); лимиты: title <= 70, H1 <= 60, H2 <= 70 (предупреждения);
- fill_notes собираются в сводку по всем страницам.

## 8. MOBILE-FLIGHT - рендер-проверка КИТА (инструмент разработчика шаблона)

`verify-prototype.mjs` читает КОД (грепом по html и манифестам). Греп не видит горизонтального скролла, обрезанной справа цены, поля ввода с кеглем 14px (iOS зумит страницу при фокусе) и ползунка высотой 2px - по коду это все проходит с идеальным результатом. Меряет это `verify-prototype-mobile.mjs`: открывает собранную страницу в chromium на 320/360/390/430 px и считает реальные боксы.

**Это проверка КИТА, а не клиентской страницы.** Кит фиксированный: одни и те же фрагменты и один и тот же `prototype.css` на каждой странице каждого клиента. Значит горизонтальный скролл, мелкие зоны нажатия и мелкий кегль - свойства кита; на клиентском прогоне результат будет один и тот же, а playwright пришлось бы тащить в зависимости шаблона, который клонируется в десятки клиентских папок. Поэтому:

- **в клиентский конвейер `/seo-tekst` проверка НЕ встроена** и в `package.json` playwright не значится - это осознанно, не забыли;
- **живет она в наборе `.claude/tests/kit-mobile/`** (эталонная страница из типовых фрагментов + канарейка «заведомо сломанная страница обязана ловиться»);
- **без playwright набор остается зеленым:** `verify-prototype-mobile.mjs` выходит с кодом 2 («нет инструмента», не «провал верстки»), рендер-тесты помечаются SKIP.

Установка и запуск (разово, у разработчика шаблона):

```
npm i -D playwright
npx playwright install chromium
.claude\scripts\_node.cmd .claude\tests\kit-mobile\run.mjs
```

**Когда разработчик шаблона ОБЯЗАН прогнать набор:** после любой правки `prototype.css`, `PROTOTYPE-MASTER.html`, любого файла `fragments/*.html` или темы `themes/theme-wireframe.css`. Эти точки - единственные, где может завестись переполнение по ширине; тексты страницы на него не влияют. Прогон без установленного playwright засчитывать нельзя: он не проверил ничего, он пропустил.

**Правило причины (главное).** Горизонтальный скролл чинится поиском виновного элемента (`max-width:100%`, `min-width:0` во flex/grid-ячейке, `word-break`, перенос сетки в одну колонку), а НЕ `overflow-x: hidden` на body. Скрытая полоса прокрутки не сужает блок - она прячет обрезанный край от нас, но не от заказчика: справа отрежется цена, кнопка или половина таблицы, и узнают об этом на сдаче. Поэтому скрипт печатает не только факт переполнения, но и элементы, чей правый край вышел за вьюпорт. То же и с остальным: мелкий кегль лечится кеглем, мелкая кнопка - размером кнопки, а не отключением проверки.

## Известные дефекты кита (мобильный рендер, замер 2026-08-20)

Первый реальный прогон `verify-prototype-mobile.mjs` по эталонной странице кита нашел дефекты,
которые жили в ките до программы улучшения текстов. Они зафиксированы базовой линией в наборе
`.claude/tests/kit-mobile/` - набор ловит РЕГРЕСС (новые находки), известные прогон не роняют.

| Что | Находок | Суть |
|---|---|---|
| Кегль меньше 12px | 20 | служебные подписи (`pt-schedule`, номера шагов `pt-card__ico`) - 11px |
| Зона нажатия меньше 42px | 49 | крестики плашек и бургера, кнопка бургера: 26x26, 28x40, 15x33 |
| Кегль полей формы | 16 | `input`/`textarea` 14px - **iOS зумит форму при фокусе**, самый заметный из трех |

Чинится правкой `prototype.css` (отдельная задача, не смешивать с правками текстов).
Починил - опусти числа базовой линии в `.claude/tests/kit-mobile/run.mjs`.
