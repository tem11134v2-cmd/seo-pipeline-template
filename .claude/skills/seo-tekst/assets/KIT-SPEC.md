# KIT-SPEC - контракт сборки HTML-прототипа

> Внутренний спек для `build-prototype.mjs` и набора ассетов (kit).
> Источник истины для слотов фрагментов, токенов темы и маркеров shell.
> Менять синхронно: `build-prototype.mjs` <-> `fragments/*` <-> `fragments-manifest.json` <-> `PROTOTYPE-MASTER.html`.

Прототип собирается **детерминированно** скриптом `build-prototype.mjs` из:
- `manifest.json` (что собрать: тема + блоки с текстом + опции) - его готовит агент `prototype-builder`
- набора **ассетов** (как собрать: shell + css + js + фрагменты + темы) - этот kit

LLM пишет ТЕКСТ и принимает решения (какой блок, какой фрагмент, какая тема).
Скрипт занимается ШАБЛОНИЗАЦИЕЙ. CSS/JS никогда не редактируются LLM.

## 1. Файлы kit (всё в `assets/`)

```
PROTOTYPE-MASTER.html       # shell-каркас всего документа (head+body+legal/thanks секции)
prototype.css               # компонентный CSS (использует токены темы, без хардкода брендовых цветов)
prototype.js                # вся интерактивность (формы, FAQ, бургер, попапы, cookie, hash-router)
arrow.svg                   # SVG-стрелка-загогулина к кнопке Hero
fragments-manifest.json     # карта тип-блока -> файл фрагмента + слоты + repeatables + опции
fragments/<type>.html       # HTML-фрагмент одного блока со слотами
themes/theme-<niche>.css    # :root{} токены палитры + шрифт под нишу
legal/footer.html           # футер с реквизитами + ссылками на юр-страницы
legal/cookie-banner.html    # баннер cookie
legal/page-privacy.html     # секция «Политика конфиденциальности» (роутится по #privacy)
legal/page-consent.html     # секция «Согласие на обработку ПДн» (#person-data-consent)
legal/page-cookie.html      # секция «Политика cookie» (#cookie)
legal/page-thanks.html      # секция «Спасибо» (#thanks)
```

## 2. manifest.json (вход build-prototype.mjs)

Готовит `prototype-builder`. Один манифест = одна страница = один прототип.

```json
{
  "meta": {
    "project": "akva-spb",
    "slug": "ustanovka-septikov",
    "page_type": "Услуга",
    "title": "Установка септиков в СПб - монтаж под ключ за 1 день",
    "description": "<= 160 символов для <meta description>"
  },
  "theme": "b2b",
  "legal": {
    "company": "ООО Аква-Сервис",
    "inn": "[ИНН - требует уточнения]",
    "ogrn": "[ОГРН - требует уточнения]",
    "address": "[ЮР_АДРЕС - требует уточнения]",
    "domain": "akva-spb.ru",
    "email": "info@akva-spb.ru",
    "phone": "+7 (812) 000-00-00",
    "date": "06.06.2026"
  },
  "blocks": [
    {
      "type": "hero",
      "fragment": "hero",
      "h2": null,
      "slots": { "h1": "...", "subhead": "...", "cta_label": "Рассчитать стоимость",
                 "bonus": "+ выезд замерщика бесплатно",
                 "plates": [ {"title":"...","text":"..."}, {"title":"...","text":"..."}, {"title":"...","text":"..."} ] },
      "opts": { "arrow": true },
      "fill_notes": []
    },
    {
      "type": "advantages",
      "fragment": "cards",
      "h2": "Почему монтаж под ключ выгоднее",
      "slots": { "items": [ {"title":"...","text":"..."}, {"title":"...","text":"..."}, {"title":"...","text":"..."} ] },
      "opts": { "cols": 3 },
      "fill_notes": []
    }
  ]
}
```

Правила:
- `blocks[].type` - смысловой тип блока (из BLOCKS.md). `blocks[].fragment` - какой HTML-фрагмент рендерить (обычно совпадает или из fragments-manifest).
- `slots` - значения для `{{...}}` плейсхолдеров фрагмента. Массивы -> repeatable-регионы.
- `opts` - модификаторы (варианты вёрстки/классы): `cols` (3/4), `arrow` (bool), `inverted` (bool, тёмный блок - только cta-mid, максимум 1-2).
- Выделенный тариф - boolean `tariffs[i].featured`: true ровно у одного тарифа (это слот, не opt).
- `fill_notes` - список пометок для согласования: сборщик и валидатор их только считают (сводка в лог), в docx они выводятся отдельным списком. В HTML сам этот список не рендерится - подсвечиваются вхождения `[ЗАПОЛНИТЬ: ...]` в текстах слотов (см. §3).
- `meta.title` - метатег: **целевая длина 60 символов, потолок 70**. Перенос из `page.json` дословный: сборщик берёт title и description от писателя и НЕ сочиняет и НЕ укорачивает их сам (иначе `<title>` прототипа разойдётся с Texts.docx, который собран из того же `page.json`). Длиннее потолка - вернуть писателю, а не резать на сборке.
- `blocks[].empty_state` - строка из blueprint (что видит человек при нуле элементов в блоке-шаблоне). Сборщик отдаёт её фрагменту как `{{empty_state}}` и переносит в HANDOFF.md. **В `subhead` (или любой другой слот писателя) её класть нельзя:** slots - согласованный текст, подмена расходит прототип с Texts.docx, и подменённый текст не проходил копи-шлюз.
- **Ровно одна форма захвата в финале** (`type:"form"` встречается 1 раз). Pre-footer = микро-конверсия, не дубль формы.
- `legal` - реквизиты заказчика. Выдумывать их нельзя: нет реквизита - оставь поле пустым или напиши `"[ИНН - требует уточнения]"`, сборщик обрабатывает оба написания одинаково (пустые ИНН/ОГРН/адрес просто не печатаются). **Телефон - отдельный случай:** он несёт `href="tel:"`, а пустая tel-ссылка - намеренное нарушение в `verify-prototype.mjs` (мёртвая ссылка в футере хуже отсутствия). Поэтому при пустом `legal.phone` И при пометке-заглушке (строка без 5 цифр подряд) сборщик подставляет одну и ту же маску `+7 (000) 000-00-00`: ссылка живая, номер заведомо нерабочий, в лог сборки и в предупреждения валидатора идёт строка «телефон не заполнен». Руками номер не придумывать ни в каком виде. Полный состав legal - 8 полей: `company, inn, ogrn, address, domain, email, phone, date` (без `domain` в футере остаётся «© », без `date` - «Редакция от »).
- Опциональные поля манифеста: `popups` (тексты попапов по таймеру/exit - ключи см. маркеры §6) и `meta.schedule`/`legal.schedule` (график работы в шапке); не заданы - сборщик подставит дефолты.

`page.json` (вход для docx-сборки, готовит `page-writer`) - то же `blocks[]` с текстом; `fragment` и `opts` уже перенесены из blueprint, но БЕЗ `meta/theme/legal/popups`. В `page.json` есть и `page.description` - метатег Description (<=160) от писателя. `prototype-builder` переносит blocks как есть, meta title/description берёт из page.json (от page-writer, сам не сочиняет) и дополняет до `manifest.json` (meta, theme, legal, popups).

## 3. Синтаксис фрагмента

Простой mini-template (реализован в build-prototype.mjs, без зависимостей):

| Конструкция | Значение |
|---|---|
| `{{slot}}` | подстановка скалярного слота (HTML-escape по умолчанию) |
| `{{{slot}}}` | подстановка без escape (для уже готового HTML, напр. ссылки) |
| `<!--REPEAT:items-->...{{item.title}}...<!--/REPEAT:items-->` | повтор региона по массиву `slots.items`, внутри `{{item.<field>}}` |
| `<!--IF:opts.arrow-->...<!--/IF:opts.arrow-->` | условный регион по truthy `opts.arrow` |
| `<!--CLASS:cols-->` | подставит `cols-3`/`cols-4` из `opts.cols` (хелпер для вариативных классов) |
| `{{@index}}` | порядковый индекс внутри REPEAT (с 1) |

Неизвестный слот -> пустая строка + предупреждение в лог (не падать). После рендера всех блоков сборщик проходит по собранному HTML и оборачивает каждое вхождение подстроки `[ЗАПОЛНИТЬ: ...]` (из текста любого слота, независимо от `fill_notes`) в `<span class="nx-fill" data-fill>[ЗАПОЛНИТЬ: ...]</span>` - класс `.nx-fill` стилизован в `prototype.css` как пунктирный стикер, чтобы заказчик видел, что надо дозаполнить.

## 4. Полный пример фрагмента: `fragments/hero.html`

```html
<section class="pt-hero" id="hero">
  <div class="container pt-hero__grid">
    <div class="pt-hero__text">
      <h1 class="pt-hero__h1">{{h1}}</h1>
      <p class="pt-hero__sub">{{subhead}}</p>
      <div class="pt-hero__cta-wrap">
        <a href="#lead" class="btn btn--primary pt-hero__cta">{{cta_label}}</a>
        <!--IF:opts.arrow--><span class="pt-arrow" aria-hidden="true"><!--ARROW_SVG--></span><!--/IF:opts.arrow-->
      </div>
      <!--IF:bonus--><p class="pt-hero__bonus">{{bonus}}</p><!--/IF:bonus-->
    </div>
    <div class="pt-hero__plates">
      <!--REPEAT:plates-->
      <div class="pt-plate">
        <div class="pt-plate__title">{{item.title}}</div>
        <div class="pt-plate__text">{{item.text}}</div>
      </div>
      <!--/REPEAT:plates-->
    </div>
  </div>
</section>
```

Соответствующая запись `fragments-manifest.json`:

```json
{
  "hero": {
    "file": "hero.html",
    "scalars": ["h1", "subhead", "cta_label", "bonus"],
    "repeatables": { "plates": ["title", "text"] },
    "opts": ["arrow"],
    "notes": "1 кнопка (не 2), SVG-стрелка, 3 плашки title+1 строка. H1 44px. Без дисклеймеров."
  }
}
```

## 5. Токены темы (`themes/theme-<niche>.css`)

Каждая тема - только `:root{}` блок + шрифт. Единый словарь токенов (одинаковый во всех темах, чтобы `prototype.css` работал с любой):

```css
:root{
  --font: -apple-system, "Segoe UI", Roboto, Helvetica, Arial, sans-serif;
  --bg:#ffffff; --bg-alt:#f6f8fb; --bg-invert:#0f172a;
  --text-primary:#0f172a; --text-secondary:#5b6b80; --text-invert:#ffffff;
  --accent-primary:#1f6feb; --accent-secondary:#0b3d91;
  --border:#e3e8ef; --radius:14px; --shadow:0 6px 24px rgba(15,23,42,.08);
}
```

Ниши (6): `premium`, `b2b`, `mass-services`, `ecommerce`, `saas`, `military-dark`. Значения - из DESIGN-SYSTEMS источника. build-prototype.mjs линкует `themes/theme-<manifest.theme>.css` в `<head>` ПЕРЕД `prototype.css`.

## 6. Shell (`PROTOTYPE-MASTER.html`) - маркеры

build-prototype.mjs заменяет HTML-комментарии-маркеры:

| Маркер | Чем заменяется |
|---|---|
| `<!--META_TITLE-->` | `<title>` + og |
| `<!--META_DESC-->` | `<meta name=description>` |
| `<!--THEME_CSS-->` | `<style>` содержимое выбранной темы (инлайнится, чтобы файл был self-contained) |
| `<!--PROTOTYPE_CSS-->` | `<style>` содержимое prototype.css |
| `<!--LOGO-->` | название компании в шапке: `legal.company` -> `meta.project` -> "Компания" (escape) |
| `<!--PHONE-->` | `legal.phone`, в шапке и бургер-меню (escape). Пусто или пометка-заглушка -> маска "+7 (000) 000-00-00" (см. §2) |
| `<!--PHONE_RAW-->` | `legal.phone` без всех символов кроме цифр и `+` - для `href="tel:..."` |
| `<!--SCHEDULE-->` | график работы: `meta.schedule` -> `legal.schedule` -> "Пн-Пт 9:00-19:00" |
| `<!--POPUP_TIME_TITLE/SUB/CTA-->` | тексты попапа по таймеру: `manifest.popups.time_title/time_sub/time_cta`, дефолты "Не нашли что искали?" / "Оставьте телефон - перезвоним и ответим на вопросы" / "Жду звонка" |
| `<!--POPUP_EXIT_TITLE/SUB/CTA-->` | тексты exit-попапа: `manifest.popups.exit_title/exit_sub/exit_cta`, дефолты "Уже уходите?" / "Заберите расчет стоимости - пришлем в мессенджер" / "Получить расчет" |
| `<!--BLOCKS-->` | конкатенация отрендеренных фрагментов блоков по порядку |
| `<!--FOOTER-->` | legal/footer.html со слотами реквизитов (пустые ИНН/ОГРН не печатаются - см. LEGAL.md) |
| `<!--LEGAL_PAGES-->` | legal/page-*.html секции (роутятся по hash) |
| `<!--COOKIE_BANNER-->` | legal/cookie-banner.html |
| `<!--PROTOTYPE_JS-->` | `<script>` содержимое prototype.js |
| `<!--ARROW_SVG-->` | содержимое arrow.svg (внутри hero, если opts.arrow) |

Итог - **один self-contained .html** (инлайн `<style>`+`<script>`, без внешних запросов, без фреймворков) - совместим с Tilda Zero Block / WordPress.

### 6.1 Контракт передачи в самом файле (два обязательных места)

Прототип уходит дальше в непредсказуемом виде: файлом, скриншотом в чате, куском текста в ТЗ. Поэтому контракт «это карта СОДЕРЖАНИЯ, а не макет» вшит прямо в shell, в двух местах.

**1. Комментарий-контракт - сразу ПОСЛЕ `<meta charset>`, первым содержательным элементом `<head>`.** Порядок именно такой и переставлять его нельзя: окно предсканирования кодировки у браузеров - первые 1024 байта документа, а комментарий-контракт длиннее. Поставишь комментарий выше - объявление кодировки уедет за это окно, и кириллица во ВСЕХ прототипах поедет заказчику кракозябрами. Та же причина записана в самом shell (`PROTOTYPE-MASTER.html`, первые строки) и в `verify-prototype.mjs` (комментарий ищется в пределах `<head>`, а не сразу за открывающим тегом). Машинный маркер сразу за комментарием: `<meta name="prototype-contract" content="content-map-not-layout">`. Адресат - тот, кто откроет исходник (дизайнер, верстальщик, разработчик). Состав: что сохранить дословно (порядок блоков как воронка, тексты, цифры, один главный CTA на блок), что можно и нужно переопределить (композиция и сетка внутри блока, число колонок, размеры карточек, типографика, палитра, шрифты, иконки, иллюстрации, объединение или разбиение соседних блоков), и прямой запрет копировать служебную композицию файла.

**2. Видимая закрываемая плашка `.pt-contract` - первым элементом `<body>`, до шапки.** Адресат сразу двое: заказчик (управление ожиданиями - ч/б каркас без предупреждения даёт «а почему так уныло», и обсуждение уезжает в визуал вместо содержания) и дизайн-этап (та же инструкция, но словами для человека). Закрывается крестиком: `onclick="this.closest('.pt-contract').remove()"` - inline-обработчик, как остальные интерактивы кита; элемент удаляется целиком, остальное не съезжает. Стили - в `prototype.css`, только токены темы (`--bg-alt`, `--border`, `--text-secondary`, `--text-primary`, `--radius`), без цветов вне палитры, иначе плашка ломает wireframe и цветные темы. Служебная по статусу: мелкий кегль, `@media print { display: none }`, первым экраном как контент не считается.

**Жёсткое правило: оба места копируются в КАЖДЫЙ собираемый прототип дословно.** Их нельзя выпиливать «чтобы было чище», «заказчик и так в курсе» или «на скриншоте некрасиво» - именно на этих двух местах держится граница между содержанием и дизайном. Текст правится только здесь, в shell, и только вместе с этим спеком.

Ограничение по тексту то же, что и везде: в комментарии и в плашке нет длинных/средних тире и буквы ё - иначе `verify-prototype.mjs` завернёт каждый собранный прототип (тире) на ровном месте.

### 6.2 HANDOFF.md рядом с прототипами

Полный контракт передачи живёт отдельным документом `HANDOFF.md` в корне `texts/NNN-slug/` - его собирает `build-handoff.mjs` (см. ADR-035), прикладывается к .html при отдаче дизайнеру/разработчику. Комментарий и плашка внутри файла - короткая версия на случай, если .html поедет дальше в одиночку.

**HANDOFF пересобирается при КАЖДОЙ новой версии прототипов** (в том числе после `/seo-tekst-fix`): порядок блоков в новой версии отличается от старой, и устаревший handoff уведёт дизайн не туда.

## 7. POST-FLIGHT ассерты (в verify-prototype.mjs)

Нарушение (exit 2, сборку надо чинить):
- есть `<header>`, ровно один `<form>` (финал), `<footer>`, непустая `tel:`-ссылка, cookie-баннер;
- нет фреймворковых атрибутов (`class="...react"`, `v-`, `ng-`, `data-tilda`);
- **каждый `blocks[].fragment` существует в `fragments-manifest.json`.** Неизвестное имя - блокер, а не предупреждение: сборщик подставляет фолбэк `cards` и рендерит его слотами чужого фрагмента, на странице остаётся заголовок и пустая сетка под ним - блок, обещанный структурой, исчезает молча. Чинится в `manifest.json`: взять имя из манифеста кита либо перевести блок на существующую форму;
- `manifest.json` разбирается (битый JSON - нарушение, а не «контентных проверок не было»);
- нет длинного/среднего тире (— –), только дефис;
- стоп-формулы (COPY-AUDIT.md П.5, таблица замен штампов) не встречаются;
- буква ё - формально нарушение, но на выходе штатной сборки недостижимо: `build-prototype.mjs` нормализует ё->е по всему документу перед записью. Сработало - значит собирали в обход сборщика; чинить сборку, а не HTML руками.

Предупреждение (exit 0, но глазами посмотреть):
- бюджеты символов блоков контролирует copy-auditor pre-flight (COPY-AUDIT П.11 «Лимиты длины», по blueprint, допуск ±15%); verify-prototype лишь мягко предупреждает об экстремальных длинах H1/H2;
- submit формы `disabled` по умолчанию + чекбокс согласия (`#f-agree`) - короткая формулировка (v4: одна строка, без дублирования надписи кнопки);
- телефон-заглушка `+7 (000) 000-00-00` в документе (`legal.phone` не заполнен, см. §2);
- пустые `legal.domain` / `legal.date` - в футере остаётся «© » и «Редакция от » без значения;
- H1 содержит маркер; все `fill_notes` собраны в отчёт.

Чего verify-prototype **не** проверяет (и не должен): вёрстку на узких экранах - это свойство кита, а не клиентской страницы, см. §8.

## 8. MOBILE-FLIGHT - рендер-проверка КИТА (инструмент разработчика шаблона)

`verify-prototype.mjs` читает КОД (грепом по html и manifest). Греп не видит горизонтального скролла, обрезанной справа цены, поля ввода с кеглем 14px (iOS зумит страницу при фокусе) и ползунка высотой 2px - по коду это всё проходит с идеальным результатом. Меряет это `verify-prototype-mobile.mjs`: открывает собранную страницу в chromium на 320/360/390/430 px и считает реальные боксы.

**Это проверка КИТА, а не клиентской страницы.** Кит фиксированный: одни и те же фрагменты и один и тот же `prototype.css` на каждой странице каждого клиента. Значит горизонтальный скролл, мелкие зоны нажатия и мелкий кегль - свойства кита; на клиентском прогоне результат будет один и тот же, а playwright пришлось бы тащить в зависимости шаблона, который клонируется в десятки клиентских папок. Поэтому:

- **в клиентский конвейер `/seo-tekst` проверка НЕ встроена** и в `package.json` playwright не значится - это осознанно, не забыли;
- **живёт она в наборе `.claude/tests/kit-mobile/`** (эталонная страница из 6 типовых фрагментов + канарейка «заведомо сломанная страница обязана ловиться»);
- **без playwright набор остаётся зелёным:** `verify-prototype-mobile.mjs` выходит с кодом 2 («нет инструмента», не «провал вёрстки»), рендер-тесты помечаются SKIP.

Установка и запуск (разово, у разработчика шаблона):

```
npm i -D playwright
npx playwright install chromium
.claude\scripts\_node.cmd .claude\tests\kit-mobile\run.mjs
```

Отдельно по одной странице: `.claude\scripts\_node.cmd .claude\scripts\verify-prototype-mobile.mjs <page_dir> [--widths 320,360,390,430]`.

**Когда разработчик шаблона ОБЯЗАН прогнать набор:** после любой правки `prototype.css`, `PROTOTYPE-MASTER.html`, любого файла `fragments/*.html` или темы `themes/theme-*.css`. Эти четыре точки - единственные, где может завестись переполнение по ширине; тексты страницы на него не влияют. Прогон без установленного playwright засчитывать нельзя: он не проверил ничего, он пропустил.

**Правило причины (главное).** Горизонтальный скролл чинится поиском виновного элемента (`max-width:100%`, `min-width:0` во flex/grid-ячейке, `word-break`, перенос сетки в одну колонку), а НЕ `overflow-x: hidden` на body. Скрытая полоса прокрутки не сужает блок - она прячет обрезанный край от нас, но не от заказчика: справа отрежется цена, кнопка или половина таблицы, и узнают об этом на сдаче. Поэтому скрипт печатает не только факт переполнения, но и элементы, чей правый край вышел за вьюпорт. То же и с остальным: мелкий кегль лечится кеглем, мелкая кнопка - размером кнопки, а не отключением проверки.

## Известные дефекты кита (мобильный рендер, замер 2026-08-20)

Первый реальный прогон `verify-prototype-mobile.mjs` по эталонной странице кита нашёл дефекты,
которые жили в ките до программы улучшения текстов. Они зафиксированы базовой линией в наборе
`.claude/tests/kit-mobile/` - набор ловит РЕГРЕСС (новые находки), известные прогон не роняют.

| Что | Находок | Суть |
|---|---|---|
| Кегль меньше 12px | 20 | служебные подписи (`pt-schedule`, номера шагов `pt-card__ico`) - 11px |

| Кегль полей формы | 16 | `input`/`textarea` 14px - **iOS зумит форму при фокусе**, самый заметный из трёх |

Чинится правкой `prototype.css` (отдельная задача, не смешивать с правками текстов).
