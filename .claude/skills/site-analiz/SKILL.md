# site analiz

Предпроектный анализ v8. Запускается в worktree-сессии. Выход - один машинный файл
`project.json` (единственный вход `/site proto`) и два документа заказчику.

## Чего этот скил НЕ делает

- не пишет тексты страниц, метатеги и прототип - это `/site proto`;
- не пишет статьи;
- не строит структуру сайта и не согласовывает скелеты: состав страницы выводится
  арифметикой из замера лидеров, согласовывать нечего;
- не трогает `/seo-faq` - согласованная работающая машинерия, в v8 не переписывается;
- не выдумывает. У проверяемого утверждения есть источник (бриф, созвон, документ, сайт).
  Источника нет - предложение не пишется вовсе, вопрос уходит в документ 2.

## Раскладка

```
sites/NNN-<slug>/
├── queue.json            # раскладка, три ответа оператора, гейт, журнал исключений
├── input/                # вводная от заказчика плюс operator.md, если вход был пуст
├── parts/facts.json      # шаг 1  фактура, у каждой строки источник, плюс вопросы gaps[]
├── parts/market.json     # шаг 2  смыслы и разведка: сводка ЦА, оффер, лексикон, конкуренты
├── project.json          # шаг 3  контракт по project.schema.json
├── docs/understood.html  # шаг 4  документ 1 «Что мы поняли о вашем бизнесе»
├── docs/ask.html         # шаг 4  документ 2 «Что нам от вас нужно»
└── answers.txt           # шаг 5  ответы заказчика
```

## Состояние выводится из содержимого

Списка состояний нет, хранить его негде и незачем. Следующий шаг печатает скрипт:

```
node .claude/scripts/site/queue.mjs state
```

| чего нет | шаг |
|---|---|
| каталога и `queue.json` | 0 init |
| `tier`, `type`, `site_kind` в queue.json | 0b три вопроса оператору |
| `parts/facts.json` | 1 фактура |
| `parts/market.json` | 2 смыслы и разведка |
| `project.json` | 3 сборка контракта |
| `docs/understood.html`, `docs/ask.html` и ссылок в queue.json | 4 документы и Drive |
| отметки гейта | 5 ответы заказчика |

Единственное, что физически не выводится из файлов, - факт согласования с человеком.
Его ставит `queue.mjs gate --by "<кто>"`, и только после дифф-листа.

## Шаг 0. init

```
node .claude/scripts/site/queue.mjs init <slug> [--tier seo] [--type services] [--kind multipage]
```

Создает каталог, `parts/`, `docs/` и `queue.json`. Повторный запуск ничего не ломает -
печатает состояние существующего проекта.

## Шаг 0b. Три вопроса оператору

Тридцать секунд, **оператору, не заказчику**. Заказчик про блоки, тиры и типы страниц
не спрашивается вообще - все снимает конвейер сам.

1. SEO куплено? -> `tier`: `basic` либо `seo`.
2. Услуги, магазин или и то и другое? -> `business.type`: `services`, `shop`, `both`.
   Это единственный переключатель режима: `shop` и `both` включают каталожный справочник
   в `/site proto`, `services` не подгружает его вовсе.
3. Лендинг или многостраничник? -> `business.site_kind`: `landing` либо `multipage`.

Ответы переданы флагами `init` и лежат в `queue.json`. Оттуда их и берет сборка контракта:
ответ оператора старше догадки агента, расхождение печатается строкой отчета.

**Если вводной папки нет вовсе**, спрашивает оператора этот скил, а не субагент: у субагента
диалога нет, его сообщение вернется только по завершении прохода. Три вопроса одним
сообщением, дословные ответы пишутся в `input/operator.md`, и только после этого запускается
`site-intake`. Вопросы:

1. Что продаем, кому и в каком городе.
2. Что уже есть: сайт, прайс, лицензии, фото работ, отзывы.
3. Телефон и юрлицо, ИНН и ОГРН, если под рукой.

Ответа нет - работаем тем, что есть, и это законный проход: в `source[]` встает
`operator_guess`, недостающее уезжает вопросами в документ 2.

## Шаг 1. Фактура - агент `site-intake`

Читает бриф, расшифровку созвона, присланные документы, `input/operator.md` и текущий сайт.
Кладет `parts/facts.json`: до 40 строк-кандидатов, у каждой `label`, `value`, `src`, при
наличии `artifact`, и `q[]` - id блоков, которым факт нужен. `publish` при засеве **всегда**
`no`. Строк без источника не бывает: вместо них тот же агент заводит `gaps[]` - вопросы
документа 2. Он единственный, кто видит, чего не хватило.

Фактов меньше 15 - предупреждение отчета, а не брак: 15 придуманных строк хуже 9 настоящих.

## Шаг 2. Смыслы и разведка - агент `site-market`

Кладет `parts/market.json`: сводка аудитории (2-4 сегмента, у каждого 2-3 боли, 1-2 страха,
2-3 возражения с готовым ответом, 2-3 критерия выбора), оффер, лексикон и разведка
конкурентов. Отдельного шага разведки в конвейере нет - ее снимает этот же агент, потому
что глубина замера зависит от тех же полей, что и сводка.

Глубина задается `site_kind`:

- `landing` - **минимум**: 2-3 лидера, один тип страницы. У лендингов блоки однородны,
  мерить нечего, кроме цифр рынка и набора обещаний;
- `multipage` - **полная**: по каждому типу страниц (home, service, при `type` shop либо both
  еще category и product) 5-8 лидеров, снимается состав блоков.

Глубина по деньгам задается `tier`: при `basic` платные инструменты не вызываются вовсе -
только открытый просмотр страниц лидеров. Платные замеры частот и топа разрешены при `seo`.

`market.must_have[]` - id блоков из `pages.yml`, которые стоят у большинства лидеров; из него
считается состав страницы. Имена блоков и признаков ниши берутся из `pages.yml`, свои
не изобретаются.

Основной источник портретов, болей и возражений - **рассуждение агента по промту**. Парсинг
отзывов, форумов и вопросных запросов не обязателен и условием прохождения не является:
агент вправе не ходить никуда. Внешние данные вторичны и умеют сделать хуже.

Развернутое досье (пять портретов на пять страхов и так далее) - рабочее рассуждение,
которое порождает сводку и умирает. В `project.json`, тем более в документ заказчику, едет
только сводка.

`words[].src` - ярлык, а не ворота: `persona` штатно, дефектом не считается, ни один
валидатор его не штрафует. Единственное следствие: в кавычках на сайте стоит только
реальная цитата (`forum` либо `client`); реконструкция дает смысл, но не прямую речь.

## Шаг 3. Сборка контракта

```
node .claude/scripts/site/build-project.mjs <каталог>
node .claude/scripts/site/verify-data.mjs <каталог> --seed
```

Склейка двух `parts/` в `project.json` по белому списку полей. Шаг механический: новых
смыслов тут не рождается. `gates`, `facts[].q`, `directions[].serves`, `sig` и
`gaps[].weight` считает скрипт - агент их не проставляет.

Сборщик берет раздел оттуда, где он есть: `audience`, `offer`, `lexicon` и `competitors` -
из `market.json`, `business`, `facts`, `constraints` и `gaps` - из `facts.json`. Перед
записью контракт проходит ту же проверку схемы, что и валидатор: то, что записано, валидатор
примет.

Exit 2 - нарушения, файл не записан. Exit 1 - предупреждения. После пройденного гейта
пересборка отказывает: она стерла бы согласованные решения. Нужна правка - `--force`
и новый гейт.

`gates.ready=false` браком не является: значит тексты будут короче, а недостающее уехало
в `gaps[]`.

## Шаг 4. Два документа и Drive

```
node .claude/scripts/site/build-doc.mjs <каталог>
node .claude/scripts/site/queue.mjs docs --understood <url> --ask <url>
```

**Документ 1 «Что мы поняли о вашем бизнесе»** - полный и пригодный к работе. Ни одного
плейсхолдера, ни одного открытого вопроса: с ним идем дальше, даже если заказчик не ответит
ничего. Смысловые решения печатаются как принятые с объявленным дефолтом: «Мы исходим из
того, что ... Если это не так - скажите сейчас, пока не написаны тексты». У каждого решения
стоит код `d1`-`d8`: по нему ответ возвращается ровно в то поле, откуда взят. У каждого
проверяемого утверждения виден источник. Последняя строка: «Если вы ничего не поправите,
мы работаем по этому документу».

Документ полон не потому, что придумали больше, а потому, что говорим меньше и все
сказанное - правда. Причина без доказательства в документ не попадает вовсе - она становится
вопросом.

**Документ 2 «Что нам от вас нужно»** - одна страница, **не больше 10 вопросов**, только
фактура и настоящие развилки. Вопрос - одна строка: что спрашиваем, понятная форма ответа
и приписка, что именно это добавит в документ 1. Порядок машинный - по `gaps[].weight`
(число блоков, ждущих факт), считает и сортирует скрипт, а не агент. Последняя строка:
«Ответите на первые три - тексты станут заметно сильнее. Не ответите - сайт все равно
будет, просто короче».

Объем документа сверх порога - предупреждение с именем самого толстого раздела. Режется
контракт, а не документ: документ, который не записан, не читает никто.

Оба документа заливаются в Drive, ссылки пишутся в `queue.json` (`docs.understood`, `docs.ask`).

## Шаг 5. Гейт: ответы заказчика

Основной путь возврата - короткий лист с галочками (`answers.txt`). Штатный второй путь -
свободная проза, комментарии в документе и голосовые: их разбирает агент и раскладывает в тот
же `answers.txt`, дословную фразу заказчика ставит после `<<`.

```
node .claude/scripts/site/apply-answers.mjs <каталог>           # дифф-лист, файл не тронут
node .claude/scripts/site/apply-answers.mjs <каталог> --apply   # тот же дифф-лист и запись
node .claude/scripts/site/verify-data.mjs <каталог>
node .claude/scripts/site/queue.mjs gate --by "<кто согласовал>"
```

**Прямой записи в контракт без дифф-листа не бывает.** Дифф-лист печатает по каждому
изменению: поле, было, стало, на основании какой фразы заказчика.

Восемь смысловых решений возвращаются каждое ровно в одно поле; молчание по решению -
принятие рекомендованного, и это записывается явно строкой журнала. Молчание по фактуре -
факт остается с `publish="no"`, а вопрос уходит в `gaps[]`. У факта, выросшего из ответа,
источник `ответ`, а не бриф: заказчику показывают настоящее происхождение строки.

После гейта `/site proto` читает `project.json` и `pages.yml`. Этот скил дальше не идет.

## Журнал исключений

Одно место на все отступления, каждая запись с непустым основанием:

```
node .claude/scripts/site/queue.mjs log waiver "цены не публикуем" --ground "запрет заказчика на созвоне"
node .claude/scripts/site/queue.mjs journal
```

Виды: `waiver` (отступили сознательно), `violation` (нарушили и знаем), `gap` (данных нет),
`dropped` (выбросили входящее). Без `--ground` запись не принимается.

## Инварианты

- `project.json`: 15000 знаков - предупреждение, 26000 - ошибка. Толстый массив называет скрипт.
- Полей-обоснований в файлах нет: `rationale`, `why`, `note`, `confidence`, `evidence`,
  `status`, `function_why`, `client_why`. Решение печатается без защиты.
- Длинное и среднее тире запрещены - только дефис. Буква е-с-точками запрещена - всегда е.
- Пустая фактура - законное состояние. Минимумов на количество в схеме нет: недобор дает
  более короткий сайт и вопрос заказчику, а не команду выдумывать.
- Страница из плейсхолдеров валидной не бывает: блок без факта снимается или идет по своему
  FALLBACK из `pages.yml`.
