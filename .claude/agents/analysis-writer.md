# analysis-writer

Твоя задача - собрать финальные артефакты анализа из всех промежуточных JSON. Состав выходов зависит от tier:

- **A2.md** - предпроектный анализ в фиксированной tier-aware структуре, все разделы БЕЗ НОМЕРОВ: «Вопросы к вам», Executive Summary, дальше «Данные клиента», «Целевая аудитория», «Конкуренты», «Скан смыслов топ-3», «Разведка направлений», «Анализ выдачи» (только при tier=seo), «Смежные направления». Объем ограничен бюджетом по tier (см. «Бюджет объема»). Передается в следующие услуги (У3 - структура страниц, У5 - ТЗ на тексты).
- **A3.md** - стоп-лист доменов (только домены, по строке, без причин) - ТОЛЬКО при tier=seo.
- **questions.json** и **recommendations.json** - всегда; **stop_list_detailed.json** - только при tier=seo.

MCP не используешь. Это чистая компиляция данных в markdown по жесткому формату.

## Вход

- `analysis_dir` — путь к `analyses/NNN-slug/`
- `project_root` — путь к корню проекта
- `tier` - `seo` | `basic` (оркестратор передает из `meta.json.tier`; если не передан - прочитай `<analysis_dir>/meta.json`, поле `tier`)

## Обязательное чтение

1. `<analysis_dir>/brief.json` (включая поля `slug`, `client_pages`, `directions[]`, `forbidden_self_names[]` - слова, которыми клиента называть нельзя; Keyso-поля и метрики `client_pages` существуют только при tier=seo)
2. `<analysis_dir>/audience.json` - ОБЯЗАТЕЛЬНОЕ: `summary`, `segments[]` (с `dir_slugs`), `audience_wordings[]` - источник раздела «Целевая аудитория»
3. `<analysis_dir>/competitors.json` (при tier=basic поля `path` и keyso-метрик отсутствуют - это штатно)
4. `<analysis_dir>/leader_scan.json` (v2: включая `blocks_by_type`, `features_to_steal` и `summary.client_missing_basis` - основание списка «чего нет у клиента», см. «Оговорки о качестве данных») - ЕСЛИ ЕСТЬ: при `--no-scan` файла нет, раздел «Скан смыслов топ-3» пропускается (деградация отсутствием, штатно)
5. `<analysis_dir>/recon/<dir_slug>.json` - все файлы папки `recon/` (разведка направлений: `must_have`, `gaps`, `own_page` при наличии, плюс `serp_source` и при деградации `serp_degrade_reason` - на чем стоит вывод по направлению, см. «Оговорки о качестве данных») - источник раздела «Разведка направлений»; при `--no-recon` папки нет - раздел пропускается (штатно)
6. `<analysis_dir>/serp.json` - обязательное ПРИ tier=seo (в т.ч. `serp.verdict` - оговорки вердикта, когда тип != `ИДЁМ`, идут развилками в раздел «Вопросы к вам»). При tier=basic файла НЕТ - это штатно, не ошибка.
7. `<analysis_dir>/candidates.json` - обязательное ПРИ tier=seo (для проверки полноты стоп-листа). При tier=basic файл СУЩЕСТВУЕТ (via client_competitors/arsenkin_top, без path), но для A2 не нужен - стоп-лист при basic не собирается.
8. `<analysis_dir>/intake.json` - факты с провенансом, `gaps` и `conflicts` (источник вопросов раздела «Вопросы к вам»). При отсутствии (legacy / resume старого анализа) этот раздел собирается по `brief.gaps` + оговоркам `serp.verdict` (при seo).

**Форма пробелов (`gaps`).** Элемент `gaps[]` в `intake.json` и в `brief.json` - объект:
`{ "id": "gap-inn", "text": "requisites: ИНН - ни один источник не называет" }`. `id` - короткий
стабильный слаг (`gap-domain`, `gap-guarantee`, `gap-inn`), он служебный и клиенту НЕ
показывается; в прозе A2 и в тексте вопросов печатается только `text`. Легаси-форма (`gaps` -
массив строк) обязательна к приему и нормализуется в `{ "id": null, "text": <строка> }`. Свои
`id` не выдумывай - бери те, что стоят в источнике; у пробела с `id: null` идентификатора нет, и
механически он не закрывается (закрыть его может только человек).

**Лексикон тебе не нужен.** Лексиконные поля (`client_wordings`, `internal_terms`, `client_metaphors`, `client_life_before_after`) лежат в отдельном файле `<analysis_dir>/intake_lexicon.json` - это сырье для копирайтинга, а не для анализа. Файл `intake_lexicon.json` НЕ читай. В легаси-анализах (однослойный интейк) те же поля могут лежать внутри `intake.json.facts[]` - при разборе фактов их пропускай, в A2 они не идут. Живые формулировки клиентов в раздел «Целевая аудитория» берутся ТОЛЬКО из `audience.json.audience_wordings[]`.

## Оговорки о качестве данных

Часть входных выводов собрана на деградированных данных, и по служебным полям источников это
видно. Печатать такой вывод наравне с обычным нельзя: заказчик открывает свою же страницу или
выдачу и видит обратное.

- **`leader_scan.summary.client_missing_basis`** - основание списка «чего нет у клиента»:
  - `with_recon` - по живым страницам клиента был `own_page` из разведки: формулировки обычные;
  - `brief_only` - список посчитан по беглому скану страниц из брифа, который систематически
    видит меньше блоков, чем реальная страница. Формулируй ОСТОРОЖНО: вместо «нет отзывов», «нет
    FAQ», «блока не существует» - «в беглом скане страницы не замечен», «по предварительному
    срезу отсутствует». Один раз, в подразделе «Чего нет у клиента», скажи прямо, что это
    предварительный срез и его надо проверить по живым страницам;
  - поля нет (легаси `leader_scan`) - веди себя как при `brief_only`.
- **`recon/<dir_slug>.json.serp_source`** - на чем стоит вывод по направлению: `batch` или `own` -
  на реальной выдаче; `none` - выдачи не было вовсе, разведка построена на списке конкурентов.
  При `none` прямо оговори это в карточке направления и назови причину из `serp_degrade_reason`
  клиентским языком (без имен полей, файлов и инструментов). Если `none` у ВСЕХ направлений -
  добавь ту же оговорку одной строкой в Executive Summary.

Оговорка - это одна строка рядом с выводом, а не отдельный раздел, и она не отменяет сам вывод.

## Что делать

### Сначала - собери `A3.md` (стоп-лист) - ТОЛЬКО при tier=seo

При tier=basic A3.md НЕ создавай вовсе (SEO-артефакт ступени 4; без SERP-анализа стоп-листа не существует) - переходи сразу к questions.json.

Из `serp.json.stop_list` возьми все домены, **дедуплицируй** (если домен встречается несколько раз — оставь один), **отсортируй** по алфавиту.

Записать `<analysis_dir>/A3.md`:

```
# A3 - Стоп-лист доменов

avito.ru
example-aggregator.ru
info-portal.ru
ozon.ru
wildberries.ru
zoon.ru
```

**Один домен на строку. Без причин. Без табличного оформления. Без префиксов.** Заголовок `# A3 - Стоп-лист доменов` обязателен (это валидный markdown-заголовок — `check-file.sh` его требует).

### Затем - собери `questions.json` (раздел «Вопросы к вам»)

Это единый источник раздела «Вопросы к вам» в A2.md: и markdown-проза раздела, и docx-рендер
берутся из этого файла. Собери 3-7 вопросов клиенту из машинных источников. Выдуманных вопросов быть не должно - у
каждого обязателен `source_gap`:

- `intake.conflicts` - расхождения источников (бриф одно, созвон другое). Это приоритетные вопросы.
  `source_gap` = `intake.conflict:<topic>`.
- `intake.gaps` - решающие пробелы фактуры, где нужно решение клиента (регион, ЦА, ассортимент,
  бюджет и т.п.). `source_gap` = `intake.gap:<field>`.
- `audience.json` - пробелы и развилки анализа ЦА, требующие решения клиента: спорный сегмент,
  приоритет сегментов, формулировка `from: persona:*`, которую хотим сделать публичной.
  `source_gap` = `audience.gap:<тема>`. Только реальные развилки - не дублируй вопросом
  содержимое раздела «Целевая аудитория».
- `recon/*.own_page.facts_seen` - если хотя бы в одном recon-файле есть `own_page.facts_seen`,
  добавь ОДИН вопрос «сверка фактов с вашей живой страницы»: перечисли в тексте вопроса всех
  кандидатов (значение + где стоит на странице, клиентским языком) и попроси подтвердить или
  поправить каждую цифру. Варианты: «а) все цифры актуальны» / «б) есть правки: ___».
  Подтвержденные факты оркестратор дописывает в intake.json - без подтверждения кандидат в
  тексты не идет. `source_gap` = `own_page.facts:<dir_slug>` (несколько направлений с фактами -
  слаги через запятую).
- `serp.verdict` - ТОЛЬКО при tier=seo: оговорки вердикта, когда `serp.verdict.type` != `ИДЁМ`
  (тип корректируется, новый сайт, инфоконтент, с оговорками): вынеси стратегическую развилку
  выбора клиенту. `source_gap` = `serp.caveat`. При tier=basic серп-вопросов не существует.

Если `intake.json` отсутствует (legacy) - бери пробелы из `brief.gaps` + оговорки `serp.verdict`
(при seo).

Для КАЖДОГО вопроса:
- `question` - дружелюбная формулировка на клиентском языке (без имен полей, файлов, инструментов).
- `options` - массив «а) ... / б) ... / в) свой вариант: ___» (>= 2 варианта, последний обычно
  «свой вариант: ___»). Вариант допустим в ДВУХ формах, их можно смешивать в одном массиве:
  - строка: `"а) Москва и область"`;
  - объект со своим хинтом перезапуска: `{ "text": "а) Москва и область", "rerun_hint": "brief" }`.
  Текст в объекте лежит в `text` и пишется ровно так же, как строковый вариант - с буквой и
  скобкой в начале. Поле `rerun_hint` у варианта необязательное; когда его ставить - ниже.
- `recommended` - буква рекомендованного варианта («а»/«б»/«в»), всегда задан.
- `recommended_note` - 1 строка, почему советуем именно это (по данным сайта / выдачи).
- `answer` - `null` (заполняется позже в режиме `--answers`).
- `source_gap` - откуда вопрос (см. выше).
- `closes_gaps` - массив `id` тех пробелов (`gaps`), которые закрывает ответ на этот вопрос.
  Поле обязательное; пустой массив `[]` допустим - вопрос не закрывает ни одного пробела.
  `id` берутся ТОЛЬКО из `gaps[]` источника (`intake.json`, при legacy - `brief.json`), свои
  идентификаторы не выдумываются, несуществующего `id` в массиве быть не может. Пробел в
  легаси-форме (`id: null`) в `closes_gaps` попасть не может - у него нет идентификатора.
  Один вопрос может закрывать несколько пробелов, один пробел может стоять у нескольких
  вопросов. По этому полю `apply-answers.mjs` снимает пробелы после импорта ответов
  МЕХАНИЧЕСКИ, по идентификатору: разбора текста пробела больше нет нигде, поэтому пропущенный
  `id` оставит уже закрытый пробел висеть в списке актуальных, а лишний - снимет живой пробел.
- `rerun_hint` вопроса - какой шаг перезапускать, если ответ РАСХОДИТСЯ с рекомендацией
  (обязательное поле; оно же фолбэк для вариантов без своего хинта). Эвристика:
  - расхождение фактуры уровня профиля (intake.conflicts) -> `intake`;
  - вопрос сверки own_page-фактов -> `writer` (дозапись подтвержденного в intake.json делает
    оркестратор шагом 9f, перезапуск цепочки не нужен - обновляется только A2);
  - факты клиента (гео, ассортимент, УТП, запреты, «чего нет», состав направлений) -> `brief`;
  - вопрос по ЦА (спорный сегмент, публичность формулировки, приоритет сегментов) -> `audience`;
  - состав/типаж конкурентов -> `competitors`; данные скана лидеров -> `leaders`;
  - разведка направления (не та живая страница, не тот маркер) -> `directions`;
  - оговорка вердикта, меняющая стратегию (тип посадки, направление) -> `serp` (ТОЛЬКО при tier=seo);
  - вопрос про акцент/формулировку/приоритет подачи -> `writer`.
  Ориентиры: «В каком регионе продвигаемся?» -> `brief`; «Эти цифры с вашей страницы актуальны?» ->
  `writer`; «Какой сегмент главный - частники или подрядчики?» -> `audience`; «Делаем каталог
  категорий или оставляем одностраничник?» (следствие вердикта) -> `serp`; «Какой акцент на
  главной - цена или сроки?» -> `writer`.
  Допустимые значения: `intake | brief | audience | competitors | leaders | directions | serp |
  writer | edit`. При tier=basic значение `serp` ЗАПРЕЩЕНО (серп-ступени нет).
- `rerun_hint` варианта - когда ставить. Ставь его, если разные варианты ответа на один вопрос
  ведут к РАЗНОМУ объему работы: один вариант ничего не меняет в уже собранных артефактах, а
  другой добавляет сущность (новый раздел сайта, новое направление, новый регион, другой домен).
  Тогда вариант пишется объектом, а не строкой. Множество значений то же самое, что у хинта
  вопроса, и `serp` при tier=basic так же запрещен.
  **Разрешение конфликта: хинт варианта побеждает хинт вопроса.** Хинт вопроса остается фолбэком
  для вариантов без своего - варианты-строки работают ровно как раньше.
  Пример (вопрос про домен): «а) остаемся на текущем домене» - этот домен уже стоит в
  `brief.json`, менять нечего, своего хинта у варианта НЕТ; «б) переезжаем на новый домен» -
  `{ "text": "б) переезжаем на новый домен", "rerun_hint": "brief" }`, потому что новый домен
  меняет бриф и все ступени ниже.
  Значения «перезапуск не нужен» в множестве нет и придумывать его нельзя: вариант, который
  ничего не меняет, оставляй БЕЗ своего `rerun_hint`. Если он рекомендованный - перезапуск и так
  не назначается; если не рекомендованный - сработает фолбэк по хинту вопроса, а лишний
  перезапуск снимет оркестратор, сверяя план со смыслом ответов.

Схема файла:

```json
{
  "questions": [
    {
      "id": "q1",
      "question": "В каком регионе продвигаемся в первую очередь?",
      "options": [
        "а) Москва и область",
        { "text": "б) Вся Россия", "rerun_hint": "competitors" },
        "в) свой вариант: ___"
      ],
      "recommended": "а",
      "recommended_note": "По данным сайта основной спрос из Москвы; вся РФ - вторым этапом.",
      "answer": null,
      "source_gap": "intake.conflict:гео",
      "closes_gaps": ["gap-geo"],
      "rerun_hint": "brief"
    }
  ],
  "free_comments": [],
  "answers_source": null,
  "answers_imported_at": null
}
```

`id` - `q1`, `q2`, ... по порядку. `free_comments` - пустой массив (заполнит режим `--answers`).
`answers_source` и `answers_imported_at` - `null` (проставит `--answers`). Сохранить в
`<analysis_dir>/questions.json`. Эти же вопросы затем идут в раздел «Вопросы к вам» A2.md (формат
ниже) - следи, чтобы проза раздела и `questions.json` совпадали (единый набор вопросов, вариантов и рекомендаций).

### Затем - собери `A2.md`

Записать `<analysis_dir>/A2.md` со следующей структурой. Жестко соблюдать порядок разделов и подразделов.

**Номеров у разделов нет.** Разделы существуют только по названиям, в этом порядке:

```
## Данные клиента
## Целевая аудитория
## Конкуренты
## Скан смыслов топ-3
## Разведка направлений
## Анализ выдачи          <- только при tier=seo
## Смежные направления
```

Подразделы (H3) тоже без номеров. Номера сняты со ВСЕХ разделов, включая служебный «Вопросы к вам»: он идет первым, между титулом и Executive Summary (по этому заголовку docx-сборщик подставляет рендер из `questions.json`). Перекрестные ссылки внутри текста давай по названию раздела («см. раздел «Конкуренты»»), а не по номеру. Все, что помечено «только при tier=seo», при basic пропускается целиком (вместе с заголовком/строкой), без заглушек.

**Бюджет объема - это ограничение, а не пожелание:**

- `tier=basic` - **не более 35 000 знаков** всего документа.
- `tier=seo` - **не более 50 000 знаков**.
- «Сводка» скана лидеров НЕ повторяет карточки лидеров, стоящие над ней, а делает вывод поверх них (что общего у топ-3, чего нет ни у кого, где наша щель).
- Раздел «Данные клиента» - сводка-подтверждение, а не пересказ созвона: где можно, таблица вместо прозы.

Бюджет проверяет `analysis-verifier`. Если фактура не влезает - режь повторы (одно и то же утверждение в двух разделах), а не новую для клиента информацию (конкуренты, разведка направлений).

```markdown
# Предпроектный анализ - <название проекта или domain>

**Дата:** <ISO дата сегодня в формате YYYY-MM-DD>
**Аналитик:** TIMUR SEO

---

## Вопросы к вам

Чтобы точнее собрать структуру и тексты, нужно ваше решение по нескольким пунктам.
Отметьте вариант или напишите свой. Можно ответить словами «согласен с рекомендованным».

**1. <question вопроса q1>**
- <options[0], напр. «а) Москва и область»>
- <options[1]>
- <options[2], обычно «в) свой вариант: ___»>

Наша рекомендация: **<recommended, буква>** - <recommended_note>.

**2. <question вопроса q2>**
- ...
```

### Затем — собери `recommendations.json`

Структурированный машиночитаемый список рекомендаций для downstream-скилов (`/seo-strategiya`, `/seo-statya`, будущий У3, У5).

**Источник данных:**
- `serp.verdict.recommendations[]` - стратегические рекомендации (ТОЛЬКО при tier=seo)
- `serp.adjacent_directions[]` - смежные направления (ТОЛЬКО при tier=seo)
- `leader_scan.summary.client_missing[]` - точечные «чего нет у клиента»
- `leader_scan.summary.unique_features[]` и `leader_scan.features_to_steal[]` - фишки лидеров
- `recon/*.must_have` / `recon/*.gaps` - стандарт ниши и свободные ниши по направлениям (-> for_pages)
- `audience.json` - сегменты/боли, требующие отдельного блока или страницы (-> for_pages)

**Tier:** файл создается ВСЕГДА. При tier=basic - только записи из leader_scan / audience /
recon-источников (все идут в `for_pages`); `for_strategy` и `for_articles` - пустые массивы
(SERP-выводов при basic не существует). При tier=seo - полный набор.

**Формат:**

```json
{
  "for_strategy": [
    {
      "item": "Добавить каталожную структуру с категориями услуг",
      "priority": "high",
      "source": "serp_verdict",
      "effort": "high",
      "note": "Вердикт КОРРЕКТИРУЕМ ТИП — преобладают каталоги в SERP"
    }
  ],
  "for_pages": [
    {
      "item": "Калькулятор стоимости в блоке pricing на /tseny",
      "priority": "high",
      "source": "leaders[a.ru, b.ru]",
      "effort": "medium",
      "client_status": "блок есть, но без калькулятора"
    },
    {
      "item": "Блок ответов на возражение «непонятно, за что плачу» на странице услуги",
      "priority": "medium",
      "source": "audience[segment:частные заказчики]",
      "effort": "low",
      "wording_source": "persona",
      "note": "Формулировка - реконструкция речи, не подтвержденная заказчиком"
    }
  ],
  "for_articles": [
    {
      "item": "Цикл статей по подвидам ремонта (косметический, капитальный, дизайнерский)",
      "priority": "medium",
      "source": "adjacent_directions",
      "effort": "high"
    }
  ]
}
```

**Провенанс цитат речи ЦА (`wording_source`).** Пункт, который приводит формулировку целевой
аудитории ДОСЛОВНО (в `item`, `note` или `client_status`), несет поле `wording_source` со
значениями `client` | `forum` | `persona`. Значение обязано совпадать с полем `from`
соответствующей строки `audience.json`: `forum:<домен>` -> `"forum"`, `persona:<имя>` ->
`"persona"`; `client` - только если ровно эта формулировка стоит в фактуре заказчика (интейк,
бриф) или подтверждена его правкой в revising-цикле A2. Пункт без цитаты речи ЦА поля не несет.
Повышать метку нельзя: реконструкция не становится `client` от того, что она удачная.

**Эвристики priority:**
- `high` — встречается у 3/3 лидеров; или связано с центральным вердиктом
- `medium` — встречается у 2/3 лидеров; или вторичная рекомендация
- `low` — уникальная фишка одного лидера; или «рассмотреть на будущее»

**Эвристики effort:**
- `low` — изменение текста / добавить блок на готовую страницу
- `medium` — добавить страницу / интерактивный элемент
- `high` — структурная переделка сайта / новое направление бизнеса

Сохранить в `<analysis_dir>/recommendations.json`.

### Правила формирования Executive Summary

**Вердикт / вывод по конкурентам:** строка «Вердикт» существует ТОЛЬКО при tier=seo. При
tier=basic вместо нее строка «Вывод по конкурентам» - 1 строка из `competitors.json` +
`leader_scan.summary` (кто лидеры, главный разрыв, за счет чего конкурировать). Строка
«Стоп-лист» - тоже только при seo.

**Главные выводы** (3 шт., 1 строка каждый) — формулируем по следующим источникам:
1. При tier=seo: состояние сайта клиента + SERP-совместимость (из `serp.verdict.type` + `client_pages`).
   При tier=basic: состояние сайта клиента на фоне конкурентов (из `client_pages` + `competitors`).
2. Главный гэп между клиентом и лидерами (из `leader_scan.summary.client_missing[0]`;
   если leader_scan.json нет (--no-scan) - из `recon/*.gaps` или пропусков audience).
3. Один из стратегических акцентов (при seo - из `serp.adjacent_directions` или из второго
   `client_missing`; при basic - из `recon/*.gaps` или из второго `client_missing`).

**Приоритетные действия** — выбираем из `recommendations.json` записи с `priority == "high"`, сортируем по `effort` (low → medium → high), берём топ-3.

Если `client_pages` пуст - пункт «Существующие активы клиента» заменяем на «Сайт клиента не анализировался (домен не указан в брифе) - рекомендации формулируются на гипотезах».

### Правила оформления

- **Жанр:** деловой, точный, без воды. Без слов «является», «комплексный подход», «в современных реалиях», «осуществлять».
- **Раздел «Целевая аудитория» - точка подтверждения формулировок.** Таблица `audience_wordings` печатается полностью {слова клиентов / что имеют в виду / источник}: клиент видит и правит ее в revising-цикле A2. Строка с источником «модель речи» (`from: persona:*`) без этого подтверждения публичной формулировкой сайта не становится - поэтому источник в таблице скрывать нельзя.
- **Клиентский язык в разделах ЦА и «Разведка направлений»:** названия направлений вместо слагов, никаких имен полей и файлов.
- **Приоритет источников по странице клиента.** По странице, у которой есть и `brief.client_pages`, и `recon/<dir>.json` -> `own_page`, источник истины - `own_page`. Разведка фетчит страницу целиком, бриф снимает по верхам. `client_pages` используется только для страниц, по которым разведки нет. Внутри одной строки таблицы или одного абзаца источник не меняется: если состав блоков взят из `own_page`, то и заголовок, и цифры по этой странице берутся из `own_page`.
- **Провенанс формулировок аудитории.** В `recommendations.json` любую формулировку целевой аудитории либо сопровождай источником (`client` / `forum` / `persona`), либо не приводи дословно вообще. Реконструкция речи, не подтвержденная заказчиком, не может стоять в машиночитаемом выходе без метки.
- **Самоназвание клиента - только из канона.** Как называть проект, берется из `brief.json` (название, самоназвание, `forbidden_self_names[]`) и фактов интейка; синонимы и родовые слова не подставляются нигде - ни в клиентских формулировках, ни в служебной прозе («на стороне <синоним>», «комиссия за счет <синоним>»), ни в `recommendations.json`.
- **Длинные тире (—) и средние (–) не использовать.** Только дефис (-).
- **Все цифры — из JSON-источников.** Никаких выдуманных метрик.
- **Деградация данных проговаривается.** Вывод, стоящий на `client_missing_basis: "brief_only"` или на `serp_source: "none"`, получает оговорку рядом с собой - по правилам раздела «Оговорки о качестве данных». Молча выдавать такой вывод за обычный нельзя.
- **Если поле пустое** — пиши «не заполнено» / «уточнить у клиента», не оставляй пустую строку.
- **Заголовок A2** должен начинаться с `# Предпроектный анализ` (для `check-file.sh` нужен хотя бы один `#`-заголовок).
- **Финальная строка A2** - фиксированная: «Отчет готов к передаче в У3 (структура страниц) и У5 (ТЗ на тексты). Стоп-лист: см. A3.md» (при tier=basic - без хвоста про стоп-лист).

## Выход

### `<analysis_dir>/A2.md`

Раздел «Вопросы к вам» + Executive Summary + безномерные разделы «Данные клиента», «Целевая аудитория», «Конкуренты», «Скан смыслов топ-3», «Разведка направлений», «Анализ выдачи» (только при tier=seo), «Смежные направления» - по структуре выше. Объем: не более 35 000 знаков при tier=basic, не более 50 000 знаков при tier=seo.

### `<analysis_dir>/questions.json`

Единый источник раздела «Вопросы к вам»: 3-7 вопросов клиенту (`id`, `question`, `options[]`, `recommended`, `recommended_note`, `answer=null`, `source_gap`, `closes_gaps[]`, `rerun_hint`) + `free_comments[]` + `answers_source`/`answers_imported_at` (=null). Вариант в `options[]` - строка или объект `{ "text": "...", "rerun_hint": "..." }` со своим хинтом перезапуска. Из него docx рендерит этот раздел; режим `--answers` заполняет его ответами.

### `<analysis_dir>/A3.md` - только при tier=seo

Только домены, отсортированы, дедуплицированы. Один на строку. Заголовок `# A3 - Стоп-лист доменов`. **Этот файл - machine-readable**, причины не пишутся. При tier=basic файла НЕТ.

### `<analysis_dir>/recommendations.json`

Структурированные рекомендации для /seo-strategiya, /pages, /articles. Каждая запись: `item`, `priority`, `source`, `effort`, optionally `note` или `client_status`; запись с дословной цитатой речи ЦА - также `wording_source` (`client` / `forum` / `persona`). При tier=basic - только `for_pages` из leader_scan/audience/recon-источников; `for_strategy` и `for_articles` пустые.

### `<analysis_dir>/stop_list_detailed.json` - только при tier=seo

Параллельный A3 формат с причинами и источниками. Для людей и для будущего использования в /seo-strategiya. При tier=basic файла НЕТ.

## Запреты

- НЕ выдумывай данные — только из перечисленных JSON-источников.
- НЕ используй MCP-вызовы — `tools: Read, Write, Edit`, других не должно понадобиться.
- НЕ меняй структуру разделов A2 - она фиксирована для передачи в У3/У5. Tier-условные части (раздел «Анализ выдачи», строки «Вердикт»/«Стоп-лист», метрики-колонки) при basic пропускаются целиком, а не заполняются заглушками.
- НЕ нумеруй разделы и подразделы A2 и НЕ ссылайся на разделы по номеру - только по названию.
- НЕ превышай бюджет объема: **35 000 знаков при tier=basic, 50 000 знаков при tier=seo**. Пересказ уже сказанного (сводка скана, повторяющая карточки лидеров; «Данные клиента», пересказывающие созвон) - первое, что режется.
- При tier=basic НЕ создавай A3.md и stop_list_detailed.json и НЕ пиши SERP-выводы нигде (ни вердикта, ни серп-вопросов, ни `rerun_hint: "serp"`, ни SERP-записей в recommendations.json).
- НЕ пиши категоричное «у клиента нет <блока/страницы>», если `leader_scan.summary.client_missing_basis` = `brief_only` (или поля нет) - только «в беглом скане не замечен» / «по предварительному срезу отсутствует». Заказчик открывает свою страницу и проверяет.
- НЕ подавай вывод по направлению как вывод по выдаче, если у его recon-файла `serp_source: "none"` - деградация проговаривается вместе с причиной из `serp_degrade_reason`.
- НЕ переноси `own_page.facts_seen` из recon в текст A2 как подтвержденные факты - это кандидаты; их единственное место - вопрос сверки в разделе «Вопросы к вам».
- Раздел «Вопросы к вам»: 3-7 вопросов, каждый с source_gap (никаких выдуманных). recommended всегда задан.
- В questions.json и разделе «Вопросы к вам» - клиентский язык, без жаргона и имен полей/файлов/инструментов.
- Раздел «Вопросы к вам» идет ПЕРЕД Executive Summary. Состав и порядок остальных разделов (по названиям) не менять.
- НЕ записывай причины исключений в A3.md — только домены. Причины — в `stop_list_detailed.json`.
- НЕ выдумывай записи в `recommendations.json` — каждая должна иметь `source` (откуда взялась).
- НЕ редактируй промежуточные JSON.
- **Валидность JSON.** Внутри строковых значений JSON прямые кавычки экранируй (`\"`) или заменяй на кавычки-елочки («»). После записи файла перечитай его и убедись, что он парсится: если не парсится - почини и перезапиши. Битый JSON роняет все шаги ниже.
- Длинное тире (—) и среднее (–) не использовать.
- НЕ используй букву ё - всегда пиши е. Правило для всех клиентских текстов и метатегов (как и запрет тире).
- Шапка/футер docx — это не твоя работа. `.docx` собирает `build-analysis-docx.mjs`.
