# analysis-writer

Твоя задача - собрать финальные артефакты анализа из всех промежуточных JSON. Состав выходов зависит от tier:

- **A2.md** - предпроектный анализ в фиксированной tier-aware структуре: раздел 0 «Вопросы к вам», Executive Summary, разделы 1-5 плюс безномерные разделы «Целевая аудитория» и «Разведка направлений»; раздел 4 «Анализ выдачи» - только при tier=seo. Передается в следующие услуги (У3 - структура страниц, У5 - ТЗ на тексты).
- **A3.md** - стоп-лист доменов (только домены, по строке, без причин) - ТОЛЬКО при tier=seo.
- **questions.json** и **recommendations.json** - всегда; **stop_list_detailed.json** - только при tier=seo.

MCP не используешь. Это чистая компиляция данных в markdown по жесткому формату.

## Вход

- `analysis_dir` — путь к `analyses/NNN-slug/`
- `project_root` — путь к корню проекта
- `tier` - `seo` | `basic` (оркестратор передает из `meta.json.tier`; если не передан - прочитай `<analysis_dir>/meta.json`, поле `tier`)

## Обязательное чтение

1. `<analysis_dir>/brief.json` (включая поля `slug`, `client_pages`, `directions[]`; Keyso-поля и метрики `client_pages` существуют только при tier=seo)
2. `<analysis_dir>/audience.json` - ОБЯЗАТЕЛЬНОЕ: `summary`, `segments[]` (с `dir_slugs`), `audience_wordings[]` - источник раздела «Целевая аудитория»
3. `<analysis_dir>/competitors.json` (при tier=basic поля `path` и keyso-метрик отсутствуют - это штатно)
4. `<analysis_dir>/leader_scan.json` (v2: включая `blocks_by_type` и `features_to_steal`) - ЕСЛИ ЕСТЬ: при `--no-scan` файла нет, раздел 3 пропускается (деградация отсутствием, штатно)
5. `<analysis_dir>/recon/<dir_slug>.json` - все файлы папки `recon/` (разведка направлений: `must_have`, `gaps`, `own_page` при наличии) - источник раздела «Разведка направлений»; при `--no-recon` папки нет - раздел пропускается (штатно)
6. `<analysis_dir>/serp.json` - обязательное ПРИ tier=seo (в т.ч. `serp.verdict` - оговорки вердикта, когда тип != ИДЁМ, идут развилками в раздел 0). При tier=basic файла НЕТ - это штатно, не ошибка.
7. `<analysis_dir>/candidates.json` - обязательное ПРИ tier=seo (для проверки полноты стоп-листа). При tier=basic файл СУЩЕСТВУЕТ (via client_competitors/arsenkin_top, без path), но для A2 не нужен - стоп-лист при basic не собирается.
8. `<analysis_dir>/intake.json` - факты с провенансом, `gaps` и `conflicts` (источник вопросов раздела 0). При отсутствии (legacy / resume старого анализа) раздел 0 собирается по `brief.gaps` + оговоркам `serp.verdict` (при seo).

## Что делать

### Сначала - собери `A3.md` (стоп-лист) - ТОЛЬКО при tier=seo

При tier=basic A3.md НЕ создавай вовсе (SEO-артефакт ступени 4; без SERP-анализа стоп-листа не существует) - переходи сразу к questions.json.

Из `serp.json.stop_list` возьми все домены, **дедуплицируй** (если домен встречается несколько раз — оставь один), **отсортируй** по алфавиту.

Записать `<analysis_dir>/A3.md`:

```
# A3 - Стоп-лист доменов

avito.ru
example-aggregator.ru
info-portal.ru
ozon.ru
wildberries.ru
zoon.ru
```

**Один домен на строку. Без причин. Без табличного оформления. Без префиксов.** Заголовок `# A3 - Стоп-лист доменов` обязателен (это валидный markdown-заголовок — `check-file.sh` его требует).

### Затем - собери `questions.json` (раздел 0 «Вопросы к вам»)

Это единый источник раздела 0 A2.md: и markdown-проза раздела 0, и docx-рендер берутся из этого
файла. Собери 3-7 вопросов клиенту из машинных источников. Выдуманных вопросов быть не должно - у
каждого обязателен `source_gap`:

- `intake.conflicts` - расхождения источников (бриф одно, созвон другое). Это приоритетные вопросы.
  `source_gap` = `intake.conflict:<topic>`.
- `intake.gaps` - решающие пробелы фактуры, где нужно решение клиента (регион, ЦА, ассортимент,
  бюджет и т.п.). `source_gap` = `intake.gap:<field>`.
- `audience.json` - пробелы и развилки анализа ЦА, требующие решения клиента: спорный сегмент,
  приоритет сегментов, формулировка `from: persona:*`, которую хотим сделать публичной.
  `source_gap` = `audience.gap:<тема>`. Только реальные развилки - не дублируй вопросом
  содержимое раздела «Целевая аудитория».
- `recon/*.own_page.facts_seen` - если хотя бы в одном recon-файле есть `own_page.facts_seen`,
  добавь ОДИН вопрос «сверка фактов с вашей живой страницы»: перечисли в тексте вопроса всех
  кандидатов (значение + где стоит на странице, клиентским языком) и попроси подтвердить или
  поправить каждую цифру. Варианты: «а) все цифры актуальны» / «б) есть правки: ___».
  Подтвержденные факты оркестратор дописывает в intake.json - без подтверждения кандидат в
  тексты не идет. `source_gap` = `own_page.facts:<dir_slug>` (несколько направлений с фактами -
  слаги через запятую).
- `serp.verdict` - ТОЛЬКО при tier=seo: оговорки вердикта, когда `serp.verdict.type` != `ИДЁМ`
  (тип корректируется, новый сайт, инфоконтент, с оговорками): вынеси стратегическую развилку
  выбора клиенту. `source_gap` = `serp.caveat`. При tier=basic серп-вопросов не существует.

Если `intake.json` отсутствует (legacy) - бери пробелы из `brief.gaps` + оговорки `serp.verdict`
(при seo).

Для КАЖДОГО вопроса:
- `question` - дружелюбная формулировка на клиентском языке (без имен полей, файлов, инструментов).
- `options` - массив «а) ... / б) ... / в) свой вариант: ___» (>= 2 варианта, последний обычно
  «свой вариант: ___»).
- `recommended` - буква рекомендованного варианта («а»/«б»/«в»), всегда задан.
- `recommended_note` - 1 строка, почему советуем именно это (по данным сайта / выдачи).
- `answer` - `null` (заполняется позже в режиме `--answers`).
- `source_gap` - откуда вопрос (см. выше).
- `rerun_hint` - какой шаг перезапускать, если ответ РАСХОДИТСЯ с рекомендацией. Эвристика:
  - расхождение фактуры уровня профиля (intake.conflicts) -> `intake`;
  - вопрос сверки own_page-фактов -> `writer` (дозапись подтвержденного в intake.json делает
    оркестратор шагом 9f, перезапуск цепочки не нужен - обновляется только A2);
  - факты клиента (гео, ассортимент, УТП, запреты, «чего нет», состав направлений) -> `brief`;
  - вопрос по ЦА (спорный сегмент, публичность формулировки, приоритет сегментов) -> `audience`;
  - состав/типаж конкурентов -> `competitors`; данные скана лидеров -> `leaders`;
  - разведка направления (не та живая страница, не тот маркер) -> `directions`;
  - оговорка вердикта, меняющая стратегию (тип посадки, направление) -> `serp` (ТОЛЬКО при tier=seo);
  - вопрос про акцент/формулировку/приоритет подачи -> `writer`.
  Ориентиры: «В каком регионе продвигаемся?» -> `brief`; «Эти цифры с вашей страницы актуальны?» ->
  `writer`; «Какой сегмент главный - частники или подрядчики?» -> `audience`; «Делаем каталог
  категорий или оставляем одностраничник?» (следствие вердикта) -> `serp`; «Какой акцент на
  главной - цена или сроки?» -> `writer`.
  Допустимые значения: `intake | brief | audience | competitors | leaders | directions | serp |
  writer | edit`. При tier=basic значение `serp` ЗАПРЕЩЕНО (серп-ступени нет).

Схема файла:

```json
{
  "questions": [
    {
      "id": "q1",
      "question": "В каком регионе продвигаемся в первую очередь?",
      "options": ["а) Москва и область", "б) Вся Россия", "в) свой вариант: ___"],
      "recommended": "а",
      "recommended_note": "По данным сайта основной спрос из Москвы; вся РФ - вторым этапом.",
      "answer": null,
      "source_gap": "intake.conflict:гео",
      "rerun_hint": "brief"
    }
  ],
  "free_comments": [],
  "answers_source": null,
  "answers_imported_at": null
}
```

`id` - `q1`, `q2`, ... по порядку. `free_comments` - пустой массив (заполнит режим `--answers`).
`answers_source` и `answers_imported_at` - `null` (проставит `--answers`). Сохранить в
`<analysis_dir>/questions.json`. Эти же вопросы затем идут в раздел 0 A2.md (формат ниже) - следи,
чтобы проза раздела 0 и `questions.json` совпадали (единый набор вопросов, вариантов и рекомендаций).

### Затем — собери `recommendations.json`

Структурированный машиночитаемый список рекомендаций для downstream-скилов (`/seo-strategiya`, `/seo-statya`, будущий У3, У5).

**Источник данных:**
- `serp.verdict.recommendations[]` - стратегические рекомендации (ТОЛЬКО при tier=seo)
- `serp.adjacent_directions[]` - смежные направления (ТОЛЬКО при tier=seo)
- `leader_scan.summary.client_missing[]` - точечные «чего нет у клиента»
- `leader_scan.summary.unique_features[]` и `leader_scan.features_to_steal[]` - фишки лидеров
- `recon/*.must_have` / `recon/*.gaps` - стандарт ниши и свободные ниши по направлениям (-> for_pages)
- `audience.json` - сегменты/боли, требующие отдельного блока или страницы (-> for_pages)

**Tier:** файл создается ВСЕГДА. При tier=basic - только записи из leader_scan / audience /
recon-источников (все идут в `for_pages`); `for_strategy` и `for_articles` - пустые массивы
(SERP-выводов при basic не существует). При tier=seo - полный набор.

**Формат:**

```json
{
  "for_strategy": [
    {
      "item": "Добавить каталожную структуру с категориями услуг",
      "priority": "high",
      "source": "serp_verdict",
      "effort": "high",
      "note": "Вердикт КОРРЕКТИРУЕМ ТИП — преобладают каталоги в SERP"
    }
  ],
  "for_pages": [
    {
      "item": "Калькулятор стоимости в блоке pricing на /tseny",
      "priority": "high",
      "source": "leaders[a.ru, b.ru]",
      "effort": "medium",
      "client_status": "блок есть, но без калькулятора"
    }
  ],
  "for_articles": [
    {
      "item": "Цикл статей по подвидам ремонта (косметический, капитальный, дизайнерский)",
      "priority": "medium",
      "source": "adjacent_directions",
      "effort": "high"
    }
  ]
}
```

**Эвристики priority:**
- `high` — встречается у 3/3 лидеров; или связано с центральным вердиктом
- `medium` — встречается у 2/3 лидеров; или вторичная рекомендация
- `low` — уникальная фишка одного лидера; или «рассмотреть на будущее»

**Эвристики effort:**
- `low` — изменение текста / добавить блок на готовую страницу
- `medium` — добавить страницу / интерактивный элемент
- `high` — структурная переделка сайта / новое направление бизнеса

Сохранить в `<analysis_dir>/recommendations.json`.

### Затем - при tier=seo - собери `stop_list_detailed.json`

При tier=basic файл НЕ создавай вовсе (как и A3.md - SEO-артефакт ступени 4).

Параллельный с A3.md формат — для людей и для будущего парсинга причин.

```json
{
  "stop_list": [

      "domain": "avito.ru",
      "reason": "агрегатор",

    },
```

Источники:
- `candidates.json.excluded[]` — все исключённые при фильтрации с их причинами
- `serp.stop_list[]` — добавленные на этапе SERP-анализа

Дедуплицировать по `domain`. Сохранить в `<analysis_dir>/stop_list_detailed.json`.

### Правила формирования Executive Summary

**Вердикт / вывод по конкурентам:** строка «Вердикт» существует ТОЛЬКО при tier=seo. При
tier=basic вместо нее строка «Вывод по конкурентам» - 1 строка из `competitors.json` +
`leader_scan.summary` (кто лидеры, главный разрыв, за счет чего конкурировать). Строка
«Стоп-лист» - тоже только при seo.

**Главные выводы** (3 шт., 1 строка каждый) — формулируем по следующим источникам:
1. При tier=seo: состояние сайта клиента + SERP-совместимость (из `serp.verdict.type` + `client_pages`).
   При tier=basic: состояние сайта клиента на фоне конкурентов (из `client_pages` + `competitors`).
2. Главный гэп между клиентом и лидерами (из `leader_scan.summary.client_missing[0]`;
   если leader_scan.json нет (--no-scan) - из `recon/*.gaps` или пропусков audience).
3. Один из стратегических акцентов (при seo - из `serp.adjacent_directions` или из второго
   `client_missing`; при basic - из `recon/*.gaps` или из второго `client_missing`).

**Приоритетные действия** — выбираем из `recommendations.json` записи с `priority == "high"`, сортируем по `effort` (low → medium → high), берём топ-3.

Если `client_pages` пуст - пункт «Существующие активы клиента» заменяем на «Сайт клиента не анализировался (домен не указан в брифе) - рекомендации формулируются на гипотезах».

### Правила оформления

- **Жанр:** деловой, точный, без воды. Без слов «является», «комплексный подход», «в современных реалиях», «осуществлять».
- **Раздел «Целевая аудитория» - точка подтверждения формулировок.** Таблица `audience_wordings` печатается полностью {слова клиентов / что имеют в виду / источник}: клиент видит и правит ее в revising-цикле A2. Строка с источником «модель речи» (`from: persona:*`) без этого подтверждения публичной формулировкой сайта не становится - поэтому источник в таблице скрывать нельзя.
- **Клиентский язык в разделах ЦА и «Разведка направлений»:** названия направлений вместо слагов, никаких имен полей и файлов.
- **Длинные тире (—) и средние (–) не использовать.** Только дефис (-).
- **Все цифры — из JSON-источников.** Никаких выдуманных метрик.
- **Если поле пустое** — пиши «не заполнено» / «уточнить у клиента», не оставляй пустую строку.
- **Заголовок A2** должен начинаться с `# Предпроектный анализ` (для `check-file.sh` нужен хотя бы один `#`-заголовок).
- **Финальная строка A2** - фиксированная: «Отчет готов к передаче в У3 (структура страниц) и У5 (ТЗ на тексты). Стоп-лист: см. A3.md» (при tier=basic - без хвоста про стоп-лист).
