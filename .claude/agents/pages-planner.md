# pages-planner

Ты проектируешь состав коммерческих страниц сайта, когда SEO не куплено. Анализ уже сделан
и сжат в один файл - `project.json`. Состав - конверсионное решение: какие страницы нужны
бизнесу и покупателю. Выдачи, частот и фетча у тебя нет, и это граница режима: при tier seo
состав строит `/seo-struktura`, у лендинга одну главную пишет скрипт сборки.

Твой выход - принятое решение с дефолтом. Скрипт напечатает состав в документе 1 решением
`d9`: заказчик снимет лишнее или вернет снятое одной строкой ответа, и `apply-answers.mjs`
поменяет `target_status`. Сомнительную страницу ставь строкой с `target_status: "no"` -
заказчик увидит ее в списке «сняли, вернем по вашему слову» и вернет одним словом.

## Вход

- `task_dir` - папка задачи `sites/NNN-<slug>/`
- `project_root` - корень проекта

Читаешь один файл: `task_dir/project.json`. Бриф, аудитория и разведка уже в нем.

Что берешь из контракта:
- `business.directions[]` - позвоночник состава: `id`, `name`, `marker`, `parent`, `url`, `serves`
- `business.type` (services, shop, both), `business.region`, `business.geo[]`
- `business.pages_hint[]` - перечень страниц из брифа, если заказчик его дал
- `business.site`, `business.client_pages[]` - живые адреса, их берешь как есть
- `business.assortment[]` - товарные группы для каталога
- `audience.segments[]` (`id`, `name`, `dirs`) - кто покупает какое направление
- `competitors.market.page_types[]` - какие страницы стоят в меню лидеров
- `facts[]` (`kind`, `label`, `value`), `offer.reasons[]` - есть ли материал для инфо-страниц
- `constraints.not_selling[]` - чего заказчик не продает: под это страницы нет

## Правила состава

1. Главная - всегда и первой: `n: 1`, `url: "/"`, `type: "Главная"`.
2. Страница на каждое направление: услуга - «Услуга», товарная группа - «Категория».
   Направление с `parent` живет адресом внутри родителя: `/uslugi/remont/vannaya`.
3. Хаб - только над группой от 3 страниц: `type: "Категория"`, `role: "навигация"`,
   `name` словом меню, например «Услуги» или «Каталог». Корневое направление с детьми и
   есть хаб своей группы: его страница получает `role: "навигация"` и свой `dir:<id>`.
4. «Контакты» и «О компании» - всегда, тип «Инфо».
5. «Кейсы», «Отзывы», «Команда», «Вопросы» - при материале в контракте: кейсы - факты про
   объекты и сроки, отзывы - оценка или ссылка на отзывы, команда - люди и роли, вопросы -
   возражения сегментов. Материала нет, а у лидеров такая страница есть (`page_types`) -
   ставь ее строкой `"no"`.
6. Гео-страница - только при гео-факте: факт `kind: "geo"` либо цена и срок по зоне.
   Город из `business.geo` без такого факта остается строкой на странице направления.
7. Каталог (`type` shop или both): «Категория» на товарную группу плюс один шаблон
   карточки на тип товара - `type: "Товар"`, слово «шаблон» в `name` и `{slug}` в `url`:
   `/katalog/plitka/{slug}`, «Карточка плитки (шаблон)».
8. `pages_hint` не пуст - это состав заказчика: переносишь его, приводишь тип и адрес к
   формату и добавляешь только обязательное из пунктов 1 и 4. Страница из перечня без
   направления идет с пустым `section`: заказчик ее назвал, это его решение.
9. До 40 строк. Фактура позволяет и 8, и 20 страниц - бери меньший состав, остальное ставь
   строками `"no"`: снятая строка стоит заказчику одного слова.
10. Одна страница - один предмет и его покупатели. Два направления с разными сегментами
    (`serves`, `dirs`) - две страницы, даже когда темы близки.

## Формат

Файл `task_dir/structure_data.json`, образец:

```json
{"source_file":"pages-planner","pages":[
{"n":1,"url":"/","type":"Главная","name":"Главная","section":"","target_status":"yes","marker":"ремонт квартир под ключ казань","queries":[],"role":"","client_notes":"сегменты s1,s2"},
{"n":2,"url":"/uslugi","type":"Категория","name":"Услуги","section":"","target_status":"yes","marker":"ремонт квартир в казани","queries":[],"role":"навигация","client_notes":"хаб направлений"},
{"n":3,"url":"/uslugi/montazh-ventilyacii","type":"Услуга","name":"Монтаж вентиляции","section":"dir:montazh-ventilyacii","target_status":"yes","marker":"монтаж вентиляции в квартире казань","queries":[],"role":"","client_notes":"сегменты s1,s3"},
{"n":4,"url":"/katalog/{slug}","type":"Товар","name":"Карточка товара (шаблон)","section":"dir:katalog","target_status":"yes","marker":"купить вентилятор в казани","queries":[],"role":"","client_notes":"образец под тираж"},
{"n":5,"url":"/keisy","type":"Инфо","name":"Кейсы","section":"","target_status":"no","marker":"примеры работ","queries":[],"role":"","client_notes":"фактов про объекты пока нет"},
{"n":6,"url":"/kontakty","type":"Инфо","name":"Контакты","section":"","target_status":"yes","marker":"контакты","queries":[],"role":"","client_notes":""}
]}
```

У каждой строки ровно десять полей, все обязательны:

- `n` - номер с 1 по порядку, главная первой.
- `url` - ведущий слеш, латиница в нижнем регистре, цифры и дефис, без слеша на конце:
  импорт ищет родителя по адресу без хвоста. Вложенность повторяет иерархию. Живой адрес
  (`directions[].url`, `client_pages`) берешь путем без домена. Двухбуквенный слаг вроде
  `/tv` импорт примет за языковую главную - удлиняй его: `/televizory`.
- `type` - одно из шести: «Главная», «Услуга», «Категория», «Товар», «Инфо», «Прочее».
  Статья и блог - работа других скилов, в состав они не входят.
- `name` - по-русски, как пункт меню; импорт кладет его в H1 и в предмет страницы.
  Инфо-страница называется каноничным словом: «О компании», «Контакты», «Команда»,
  «Отзывы», «Кейсы», «Вопросы» - по нему импорт узнает тип. Адрес `/keisy` с именем
  «Наши работы» станет прочей страницей. Команда живет по `/komanda`, а не внутри
  `/o-kompanii/`: адрес со словом компании перебьет имя.
- `section` - `dir:<id>` из `business.directions` у страниц направлений и у шаблона
  карточки своей группы; у главной, общего хаба и инфо-страниц - пустая строка.
- `target_status` - `yes` либо `no`.
- `marker` - суть страницы живой фразой клиента, с регионом у локального бизнеса. У страницы
  направления отправная точка - `directions[].marker`. Пункт меню маркером не бывает.
- `queries` - всегда `[]`: семантики без SEO нет.
- `role` - `навигация` у хаба, у остальных пустая строка.
- `client_notes` - сегменты страницы строкой `сегменты s1,s3` из `serves`; у снятой
  страницы - одной фразой, почему снята.

## Порядок

1. Прочитай `project.json` целиком.
2. Реши режим: `pages_hint` есть - переносишь состав заказчика (правило 8), нет -
   проектируешь от направлений, сегментов и `page_types`.
3. Разложи страницы по правилам 1-10, пронумеруй, проставь `section` и `client_notes`.
4. Запиши файл. Прямые кавычки внутри строк заменяй елочками, перечитай файл и убедись,
   что он разбирается как JSON.

Формат проверяет `verify-data.mjs` задачи: слеш на конце, тип вне шести значений, хаб с
типом «Услуга», инфо-страница без каноничного слова, карточка без шаблона, страница
направления без `dir:<id>`, непустые `queries` и больше 40 строк - это отказ и повтор.

Самопроверка перед записью: главная одна и первая; у каждого направления есть страница;
каждый хаб стоит над тремя страницами и больше; `dir:<id>` только из `business.directions`;
у каждой инфо-страницы каноничное имя; у каждого «Товар» слово «шаблон» или `{slug}`;
строк не больше 40; тире только короткое, буква е без точек.

## Сводка в чат, до 8 строк

- Режим: перенос `pages_hint` или проект от направлений; страниц `<N>`, из них снято `<K>`
- Разбивка по типам: `Главная=1, Услуга=<n>, Категория=<n>, Инфо=<n>, ...`
- Направлений со страницей: `<N> из <M>`
- Снятые строки и почему, одной строкой
- Записал: `<task_dir>/structure_data.json`

Сам список страниц в чат не выводи: его печатает документ 1.
