# leader-scanner v2

Твоя задача - провести **быстрый скан** (НЕ полный аудит) топ-3 конкурентов и из ОДНОГО прохода по их страницам получить ДВА выхода:

1. **Скан смыслов (Э2-лайт)** - какие блоки, посылы и фишки используют лидеры; сопоставление с УТП клиента из брифа: что общее, что есть у конкурентов и нет у клиента, какие уникальные фишки.
2. **Блок-матрица** - `blocks_by_type` («блок x тип страницы» в целевом словаре BLOCKS.md) + `features_to_steal` (фишки-дифференциаторы). Это доказательная основа подбора блоков для block-planner - особенно для каталогов, где набор «почти-все-используют»-блоков сильно меняется от ниши к нише и статическая матрица его не ловит.

**Страницы лидеров фетчатся ОДИН раз** - разбор каждой страницы идет сразу в оба словаря (внутренний словарь посылов для pages[]/summary + имена BLOCKS.md для матрицы).

**Это НЕ полный Э2/КФ/КНДР-аудит.** Никаких таблиц 1/0/?, никаких баллов, никакого E-E-A-T. Только структура страниц + ключевые посылы + интересные фишки.

## Вход

- `analysis_dir` - путь к `analyses/NNN-slug/`
- `project_root` - путь к корню проекта
- `tier` - `seo | basic` (опционально; если не передан - читай поле `tier` из `<analysis_dir>/meta.json`)

## Обязательное чтение

1. `<analysis_dir>/brief.json` - `niche`, `business_type`, `utp_technical`, `utp_service`, `utp_social`, `assortment`, **`directions`** (типы страниц для добора), **`client_pages`** (если есть); при tier=seo также `keyso_base`
2. `<analysis_dir>/competitors.json` - `leaders_top3` (список из 3 доменов) + типы; Keyso-метрики есть только при tier=seo
3. `<project_root>/.claude/skills/seo-analiz/MCP_MAP.md` - карта MCP
4. `<project_root>/.claude/skills/seo-tekst/assets/fragments-manifest.json` (поле `block_to_fragment`) и оглавление `<project_root>/.claude/skills/seo-tekst/assets/BLOCKS.md` - **целевой словарь имен блоков** для матрицы (маппь увиденное в эти имена, не выдумывай новые)

## Что делать

### 1. Подобрать страницы

#### 1.1. Базовый набор: 3-4 страницы на лидера

По каждому из 3 лидеров (из `competitors.leaders_top3`):

**При tier=seo** - через Keyso (как раньше):

```
domain_pages(domain="<лидер>", base="<brief.keyso_base>", sort="it50|desc", per_page=10)
```

Выбирай страницы с **наибольшим числом запросов в ТОП-50** - они самые прокачанные и репрезентативные.

**При tier=basic** - Keyso нет: страницы бери из меню/sitemap лидера через seo_fetch (без метрик). Фетчни главную (`seo_fetch_page(url, profile="content")` - навигация/меню) и/или `/sitemap.xml`; репрезентативные URL выбирай по анкорам меню и структуре URL (раздел каталога, страница услуги, карточка товара).

Состав базового набора (оба tier):

1. **Главная страница** (всегда). Обычно URL заканчивается на `/`.
2. **2-3 ключевых подстраницы**, по типу бизнеса:
   - Для **shop** (`brief.business_type == "shop"`): 1 категория + 1 товар (или 2 категории).
   - Для **services** (`brief.business_type == "services"`): 1-2 основных услуги.
   - Для **both**: 1 категория ИМ + 1 страница услуги.

#### 1.2. Добор типовых страниц (покрытие типов для матрицы)

Из `brief.directions` и `assortment` определи, какие ТИПЫ страниц есть в нише клиента: Услуга / Категория / Товар (услуговый бизнес - Услуга; магазин - Категория и Товар; смешанный - все три).

**Правило покрытия: по каждому такому типу - хотя бы одна страница этого типа хотя бы у 2 лидеров.** Если базовый набор 1.1 уже дает такое покрытие - ничего не добирай. Если нет - добери недостающие страницы (тем же способом, что в 1.1) в пределах бюджета.

**Итого: 9-12 базовых страниц (3-4 x 3 лидера) + до 4-6 страниц добора.**

### 2. Fetch и извлечение смыслов

Каждая страница фетчится ОДИН раз; из результата извлекается все для обоих выходов.

Фетч-стек (по убыванию качества):

1. **PRIMARY - Chrome-плагин** (видит rendered-композицию, lazy-load, интерактив): `mcp__claude-in-chrome__navigate(url)` -> `read_page` / `get_page_text`. Listing/SPA-каталоги статический фетч почти не видит - тут Chrome критичен.
2. **FALLBACK - seo_fetch** (если Chrome не подключен / упал / антибот): `seo_fetch_page(url="<URL>", profile="content")`; для нескольких URL сразу удобнее веер `seo_fetch_batch(urls=["<URL1>", "<URL2>", ...], profile="content")`. Отдает основной текст/контент, JS не рендерит.
3. **Деградированный - `web_fetch(url="<URL>")`**: теряет мету/структуру/HTTP-статус, но текст обычно достает.

Если ничего не сработало за 1-2 попытки - пометь страницу `"fetch_failed": true` и иди дальше (не блокировать весь скан; такая страница в матрице не участвует).

**Каждой отсканированной странице присвой `page_type` из русского словаря: `Главная | Услуга | Категория | Товар | Инфо`.**

**Для каждой страницы зафиксируй три блока данных:**

#### 2.1. Блоки на странице

Перечисли смысловые секции (по содержанию, не по html-тегам) во внутреннем словаре:

- `hero` - первый экран с заголовком, подзаголовком, CTA
- `advantages` - преимущества / УТП
- `catalog_list` - каталог / список товаров или услуг
- `about` - о компании / о нас
- `process` - процесс работы / этапы
- `pricing` - цены / тарифы
- `portfolio` - портфолио / кейсы / примеры
- `reviews` - отзывы
- `faq` - FAQ
- `contacts` - контакты / форма обратной связи
- `cta_inline` - промежуточные CTA-блоки
- `other:<название>` - для необычных блоков (хлебные крошки, цифры, сравнение, квиз, подкатегории и т.п.)

Формат: массив строк, в порядке следования на странице (порядок нужен для `typical_order` матрицы).

#### 2.2. Ключевые посылы и смыслы

Извлеки **3-6 пунктов**:

- **Главное обещание** - H1 / hero-заголовок (одной строкой).
- **Основные аргументы** - что выделяют в преимуществах (3-5 пунктов).
- **Обработка возражений** - гарантии, возврат, сроки (1-2 пункта).
- **Эмоциональные триггеры** - страх, доверие, срочность, выгода (1-2 пункта).

Формат: объект с этими подполями.

#### 2.3. Особые фишки

Что выделяется визуально или функционально:

- Калькуляторы стоимости, квизы, конфигураторы
- Интерактивные элементы (карты, фильтры, подбор по параметрам)
- Необычные блоки (сравнение, до/после, видео, 3D-просмотр)
- Нестандартная подача (анимации, скроллителинг)

Формат: массив строк. Если ничего особенного - пустой массив.

### 3. Маппинг во внешний словарь блоков (для матрицы)

В `blocks_by_type` имена блоков - ТОЛЬКО из словаря `block_to_fragment` (fragments-manifest.json) / BLOCKS.md. Маппинг внутреннего словаря посылов в имена BLOCKS.md:

| Внутренний ключ (pages[].blocks) | Имя блока для матрицы (BLOCKS.md / block_to_fragment) |
|---|---|
| `hero` | Первый экран (Hero) |
| `advantages` | Преимущества |
| `catalog_list` | по содержанию: Услуги (список услуг-карточек) / Плитка категорий (сетка разделов каталога) / Листинг товаров (листинг с карточками и фильтрами) |
| `about` | О компании |
| `process` | Этапы |
| `pricing` | Цены |
| `portfolio` | Портфолио (кейсы/работы; до/после - тоже сюда) |
| `reviews` | Отзывы |
| `faq` | FAQ |
| `contacts` | Контакты |
| `cta_inline` | Промежуточный CTA |
| `other:<название>` | ближайшее имя из block_to_fragment (см. ниже) |

Частые `other:*` и их имена в словаре: хлебные крошки - Хлебные крошки; блок цифр/счетчиков - Цифры компании; сравнение «мы и другие» - Сравнение; форма заявки / финальная форма - Форма захвата; квиз - Квиз; калькулятор - Калькулятор; сертификаты/лицензии - Сертификаты; гарантии - Гарантии; география / зона работы - География; плитка тегов - Теги; подкатегории - Подкатегории; бренды - Бренды; верх карточки товара с галереей - Карточка товара; таблица характеристик - Характеристики; похожие/популярные товары - Похожие товары; команда - Команда; логотипы клиентов/партнеров - Логотипы клиентов.

Если увиденному блоку нет ни точного, ни близкого имени в словаре - в матрицу его НЕ включай (оставь в `pages[].blocks` как `other:<название>`, при желании упомяни в `notes` типа). Новые имена блоков не выдумывай.

### 4. Сопоставление с брифом

После анализа всех страниц - сведи паттерны.

#### 4.1. Общее у 2+ из 3 лидеров

Какие блоки встречаются у двух или трех лидеров - это «гигиена ниши», обязательное.

```json
{
  "common_blocks": ["hero", "advantages", "reviews", "contacts"],
  "common_messages": [
    "Гарантия на работы",
    "Бесплатный выезд замерщика",
    "Опыт работы > 10 лет"
  ]
}
```

#### 4.2. Совпадает с УТП клиента

Прогуляйся по `brief.utp_technical`, `brief.utp_service`, `brief.utp_social` - какие из них уже **используются конкурентами** (значит «гигиена», обязательно должно быть и на сайте клиента).

```json
{
  "client_utp_matched": [
    {"utp": "Бесплатная доставка", "category": "utp_service", "competitor_examples": ["a.ru", "b.ru"]}
  ]
}
```

#### 4.3. Чего нет у клиента, но есть у конкурентов

**Важно: сравнение страница-к-странице, а не «у клиента вообще нет».**

Логика:

1. Из `brief.client_pages` собери все блоки, типы страниц и H1, которые УЖЕ есть у клиента.
2. Из своих проанализированных страниц лидеров собери все блоки и фишки.
3. **«Не хватает»** = блок/фишка встречается у 2+ лидеров И отсутствует на ВСЕХ страницах клиента в `client_pages`.
4. Если `brief.client_pages` пуст (нет домена / fetch упал) - пометить `"comparison_basis": "utp_only"` и сравнивать с `brief.utp_*` как раньше (fallback-режим).

Конкретные пометки:

- Если у клиента ЕСТЬ страница типа `pricing` с трафиком > 0 - НЕ писать «нет страницы цен», даже если у конкурентов она центральная.
- Если у клиента ЕСТЬ блок `portfolio` хотя бы на одной странице - НЕ писать «нет портфолио», только «портфолио меньше представлено» если применимо.
- Если у клиента ЕСТЬ страница с блоком `pricing`, но конкуренты делают это лучше (квиз/калькулятор) - формулировка «есть, но без интерактивных инструментов».

```json
{
  "comparison_basis": "client_pages",
  "client_missing": [
    {
      "item": "Калькулятор стоимости в блоке pricing",
      "found_in": ["a.ru", "b.ru"],
      "client_status": "блок есть на /tseny, но без калькулятора",
      "recommendation": "Добавить калькулятор в существующий блок"
    },
    {
      "item": "Раздел кейсы с фото до/после",
      "found_in": ["b.ru", "c.ru"],
      "client_status": "отсутствует на всех 5 страницах",
      "recommendation": "Создать отдельную страницу /cases с фото"
    }
  ]
}
```

#### 4.4. Уникальные фишки конкурентов

То что есть только у одного из лидеров, но выглядит сильно:

```json
{
  "unique_features": [
    {"feature": "AR-визуализация мебели в комнате", "found_in": "c.ru", "comment": "Сложно повторить, но запомнить"}
  ]
}
```

### 5. Блок-матрица и фишки (второй выход, из тех же данных)

Ничего дополнительно не фетчь - все собирается из уже отсканированных страниц.

#### 5.1. blocks_by_type

Для каждого русского типа страницы (`Главная | Услуга | Категория | Товар | Инфо`), по которому есть хотя бы одна успешно отсканированная страница лидера:

- сгруппируй страницы этого типа по лидерам;
- по каждому блоку (в именах BLOCKS.md после маппинга п.3) посчитай:
  - `coverage` - доля лидеров, у которых блок встретился на странице этого типа, от числа лидеров с отсканированной страницей этого типа (число 0-1, округляй до 2 знаков: 2 из 3 -> 0.67);
  - `typical_order` - типичная позиция блока на странице (целое, с 1; при разбросе - медиана);
  - `notes` - кратко: варианты исполнения, фишки, оговорки («у 2 из 3 листинг с фильтром по цене»; «тип отсканирован только у 1 лидера - тонкая база»).

Типы без отсканированных страниц в `blocks_by_type` НЕ включаются (деградация отсутствием данных). Блоки, которых не видел, не включаются - coverage не выдумывается. Блок с покрытием у большинства = кандидат в обязательные (это потом использует block-planner; статическая матрица BLOCKS - пол).

#### 5.2. features_to_steal

Все фишки из `pages[].features`, которые стоит забрать клиенту (интерактив, необычные блоки, сильная подача), - плоским списком:

- `feature` - что за фишка (одной строкой);
- `seen_at` - домен лидера;
- `page_type` - русский тип страницы, где увидел.

Дубли (одна фишка у нескольких лидеров) не плоди - оставь одну запись с самым сильным исполнением.

## Сводка в чат (<= 8 строк)

- Проанализировано страниц лидеров: `<N>` (базовые + добор `<M>`; фетч: `<chrome | fetch | mixed>`)
- Базис сравнения: `<client_pages | utp_only>` (если `utp_only` - `brief.client_pages` пуст)
- Общие блоки у 2+ из 3 лидеров: `<список>`
- УТП клиента, которые уже у конкурентов: `<N>`
- Чего реально нет у клиента (с учетом `client_pages`): `<N>` пунктов (главные: `<1-2 примера>`)
- Матрица blocks_by_type: типы `<список типов>`; features_to_steal: `<N>`
- Не проверено: мобильная версия лидеров, скорость загрузки, эффективность CTA (только структура и посылы)

## Запреты

- **НЕ полный аудит.** Никаких таблиц 1/0/?, никакого балльного скоринга, никакого E-E-A-T.
- НЕ ищи новых конкурентов и не меняй топ-3 - они зафиксированы в `competitors.leaders_top3`.
- НЕ редактируй `brief.json`, `competitors.json`, `serp.json`, `meta.json` - все read-only. Пиши ТОЛЬКО `leader_scan.json`.
- НЕ копируй ТЕКСТЫ лидеров - только композицию/посылы/фишки (анализ структуры, не плагиат контента).
- Имена блоков в `blocks_by_type` - только из словаря `block_to_fragment`/BLOCKS.md; блоки, которых не видел, не выдумывай (нет данных - нет строки в матрице).
- Длинные и средние тире запрещены - только дефис (-).
- НЕ используй букву е-с-точками - всегда пиши е. Правило для всех клиентских текстов и метатегов (как и запрет тире).
- Бюджет: <= 26 MCP-вызовов суммарно (добор типовых страниц учтен). При seo: 3 `domain_pages` + 9-12 базовых фетчей + до 4-6 добора; при basic: вместо `domain_pages` - 3-6 фетчей меню/sitemap лидеров. Chrome-навигации тоже считаются. Если страница не открывается за 1-2 попытки - ставь `fetch_failed: true` и иди дальше.
