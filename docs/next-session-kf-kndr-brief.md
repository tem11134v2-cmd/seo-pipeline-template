# Бриф новой сессии: анализ КФ и КНДР в /site-tekst (05.10.2026)

Документ для агента новой сессии в шаблоне `template-project`. Прочитай его целиком до любых действий. Он
заменяет долгий контекст прошлой сессии: что уже сделано, какие решения приняты и не обсуждаются заново, где лежат
материалы владельца, как работать и что считается готовым.

## 1. Задача владельца

Прокачать этап алгоритма текстов, на котором с сайтов конкурентов снимаются блоки и элементы, - анализ **КФ**
(коммерческих факторов) и **КНДР** (коммерческих элементов и компонентов, необходимых для ранжирования).

Как владелец видит этот этап:
1. Сначала найти самых сильных конкурентов - топ-5. Желательно относительно молодые сайты: те, что набрали позиции
   качественной оптимизацией, а не держатся за счет возраста домена.
2. По этим сайтам визуально снять все элементы и блоки страниц - по типам страниц (главная, категория, товар,
   услуга и т.д.), по зонам (шапка, тело, подвал).
3. Все, что пересекается между конкурентами, должно быть у нас (в типах страниц, текстах и прототипе).
4. Результат анализа КФ и КНДР дополнительно выводить в **Google Таблицу для заказчика** - не на согласование, а чтобы
   показать проделанную работу. Ссылка на таблицу - среди итоговых файлов сдачи вместе с прототипом.
5. Весь прогон от запуска текстов до готового прототипа должен остаться **без пауз** (как сейчас), а этапы после
   анализа КФ и КНДР (стратегия, брифы, тексты, ч/б прототип-сайт) не должны сломаться или ухудшиться.

Плюс небольшой остаток по текстам (см. 3.1): отдельный агент-аудитор готового прототипа целиком.

### 3.3. `промт анализ кф.txt` (365 строк)
- Вход заполняет человек: ниша, тип страницы, регион, ссылки C1-C5 и 5 приложенных full-page скриншотов; один тип
  страницы за запуск; вывод - markdown-таблицы в чат.
- Правила P1: только наблюдаемое, сомнительное - «?», не смешивать наблюдение/сравнение/рекомендацию, нормализация и
  дедупликация названий, три зоны (ШАПКА/ТЕЛО/ПОДВАЛ), не сравнивать разные типы страниц, скриншот важнее URL.
- Этапы: извлечение по конкурентам -> нормализация -> сравнительная таблица (элемент x C1-C5 + «охват» из 5) ->
  E-E-A-T по 4 измерениям -> gap-анализ -> валидация; около 45 позиций чек-листа и 13 классов категорий.
- Выход - 7 таблиц: наблюдаемые элементы, неоднозначности, сравнение конкурентов, E-E-A-T, рекомендуемая структура
  страницы, слабые/недостающие блоки рынка, ограничения анализа.
- Чего в нем нет: выбора конкурентов, работы с текстом оферов (только наличие 1/0/?), порядка блоков внутри тела,
  мобильной версии и интерактивных состояний (меню, раскрытия), самого получения скриншотов.
- Владелец: промт подразумевал ручную подстановку адресов и скриншотов; сейчас агент может все делать сам (поиск
  конкурентов, снятие страниц и скриншотов, анализ). Идеи промта тоже оценивать критически.

## 4. Обязательные рамки (решения владельца, не пересматривать)

1. Никаких кастомных ТЗ заказчика; никакой нишевой конкретики в kit; гибкость: модули, блоки и элементы - только по
   данным проекта и наблюдениям у конкурентов; новый вид блока прототип рисует без правки кода.
2. Прогон `/site-tekst` без пауз; автостоп - только по аномалии. Заказчик видит только финал (прототип, отчет и теперь
   таблицу КФ/КНДР).
3. Правило «все, что пересекается у конкурентов, - у нас» не должно порождать выдумку: элемент берется в структуру, а
   его содержание - только из фактов проекта (инвариант опоры в `kit/CLAUDE.md`); нет данных - честная плашка
   «нужны данные» и вопрос заказчику, а не придуманный текст или цифра.
4. Расширять существующее (фазы 2-3, `site-market`/`seo-base`, отчет, прототип), а не плодить новые скилы и
   воркфлоу без нужды. Сохранить «Не делаем» обеих программ и ADR-044.
5. Стиль: без буквы «е с точками», без длинных и средних тире, кавычки-елочки.
6. Коммит, мерж в main, push и `/sync-all` - только по явному «да» владельца. Pre-commit шаблона в worktree пропускает
   только файлы клиентской задачи; для коммита машинерии шаблона владелец в прошлой сессии разрешал
   `git commit --no-verify` (с ручной проверкой, что в коммите нет клиентских артефактов) - спроси еще раз.

## 5. Как работать (процесс прошлой сессии, он себя оправдал)

1. Изучить материалы (раздел 3) и текущий код фаз 2-3 и связанных мест критически; кратко доложить владельцу
   выводы: что берем, что отбрасываем, свои идеи сильнее материалов. Настоящие развилки - вопросами владельцу
   (AskUserQuestion), очевидное решать самому.
2. Написать спецификацию `docs/upgrade-program-<дата>-kf-kndr.md`: решения, контракты данных (новые файлы и поля,
   кто пишет и кто читает), пакеты работ с закрепленными файлами, тесты, приемка.
3. Аудит спецификации агентами со скептиком на каждую серьезную находку; поправить спецификацию.
4. Реализация пакетами параллельно (у каждого свои файлы), рецензент кода на пакет и доработка; интеграция до
   зеленых 13 наборов; обновить документы (SKILL, RUNBOOK, README kit, LESSONS, ADR, guide, таблица ролей и
   `workflow-models.mjs`).
5. Приемка на реальных данных: копия задачи Goldax `C:\Users\Administrator\seo-projects\goldax_ru\texts\001-goldax\`
   (только чтение, работать в копии во временной папке) и один проект услуг; живой прогон анализа КФ/КНДР на реальных
   конкурентах; таблица для заказчика собирается; прототип собирается и проходит `check-html` и `check-site-js`.
6. Независимая проверка результата (каждый пункт спецификации - отдельный проверяющий с запуском).
Лимиты использования тесные: масштаб агентов - по задаче, без лишних кругов.
