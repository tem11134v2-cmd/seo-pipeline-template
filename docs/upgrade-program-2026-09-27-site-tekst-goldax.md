## 0. Решения владельца (обязательны)

1. **Кастомное ТЗ заказчика в алгоритм не закладываем.** Документы заказчика идут через `input/` анализа.
2. **Гибкость. Никакой нишевой конкретики в kit.** Каталог, корзина, кабинет, поиск, карта, мессенджеры - модули,
   которые включаются только по данным проекта (карта, типы блоков, catalog-spec, контакты). Сайту услуг каталог и
   корзина не нужны - их нет в файле вообще. Новый для kit блок (калькулятор, квиз, «до/после», онлайн-запись и
   любой другой) прототип обязан отрисовать без правки кода, а сделать его живым - одной записью в реестре поведений.
3. **Один прототип.** `work/output/prototype.html` выглядит как реальный сайт, строго ч/б. Визуальный эталон - site.html
   Goldax. Служебный слой (id блоков, вопросы читателя, опорные факты, подсветка утверждений без опоры, список страниц)
   скрыт и включается `?debug` или клавишей. Второго файла нет.
4. **Прогон без остановок.** От импорта анализа до готового прототипа без гейтов 1-4. Решения гейта 1 заполняет агент
   по анализу, стратегию проверяет автоматическая рецензия, тексты пишутся волнами подряд. Вопросы копятся в отчете.
   Автоматическая остановка - только по аномалии (раздел C8). Ручная пауза - флаг `--stop <map|strategy|pilot>`.
   Гейт анализа `/site-analiz` (подтверждение фактов заказчиком) не трогаем.
5. **Заказчик видит только финальный прототип.**
6. **Карточка товара.** В прототипе магазина минимум одна карточка. Есть старый сайт с товарами - реальные данные: по
   одному товару на категорию-листинг (фото скачиваем и встраиваем). Нет - одна карточка-пример на весь сайт. Выдачи
   заполняются копиями до размера страницы выдачи. Везде пометка «пример».
7. **Правки /site-analiz входят в программу** (W3b).
8. Все делается в одной сессии.

## 2. Контракты между пакетами

### C1. Карта `work/sitemap.json` (схема - W3)
- `pages[].ui_role` - необязательное, enum `search | cart | account | legal`. `legal` ставит `import-structure.mjs`
  по отдельной регулярке юридических страниц (политика, согласие на обработку, оферта, cookie); страницы
  юридические и служебные (избранное, сравнение) по-прежнему `status: skip` по текущей регулярке пропуска, но
  `ui_role: legal` получают только юридические. `search`, `cart`, `account` ставит `01-sitemap-enricher` по
  назначению страницы. Страницы с `ui_role` search/cart/account не идут в меню (только значки шапки) и не идут в
  /seo-faq (`read-faq-input.mjs` их пропускает).
- `pages[].nav_label` - необязательное, до 24 знаков, короткая подпись для меню. Ставит обогатитель. Запасной вариант
  сборщика: `subject` до « / » без скобок, обрезка по слову до 28 знаков.
- `pages[].segment: "all"` + `pages[].segments: [id]` (2+ сегмента) - у главной и хаба, у чьих детей (или направлений)
  2 и больше сегментов. Правило обогатителя «главная = сегмент с самым большим чеком» удаляется. Нет `segments` при
  `all` - потребители берут все сегменты audience.
- `pages[].wave` - устаревшее, никем не пишется и не читается (волны считает `progress.mjs`, C8).
- `pages[].listing` - `true` у страниц со списком позиций каталога (category магазина; hub каталога магазина).
  `import-structure` ставит `listing: type === 'category' && business_type !== 'services'`, обогатитель правит.
- `pages[].parent` заполнен и для адресов со слешем на конце; полные адреса `https://домен/путь` приводятся к пути.
- Плоские карты (у страниц нет parent): сборщик группирует меню по типу (виртуальные разделы с подписью типа из
  словаря интерфейса), а не выводит 20+ пунктов в строку.

### C2. Контакты и реквизиты (владелец - W3; `kit/scripts/contacts.mjs` - W3)
- Импорт заводит служебные факты с **фиксированными** id по полю (номер не сдвигается от числа полей):
  `F901`-`F903` телефоны (основной первым), `F904` почта, `F905` часы работы, `F906` адрес, `F907` юрлицо
  (название, ИНН, ОГРН одной строкой). `kind: contact` (F901-F906) или `kind: legal` (F907). `value` - как в источнике.
  `publish: yes`; реквизиты, которые заказчик не подтвердил (C2-сверка ниже), дают строку в `gaps` «контакты и
  реквизиты не сверены заказчиком». ИНН/ОГРН публикуются только при верной длине (ИНН 10/12, ОГРН 13/15). Дубли с
  контактными фактами анализа не заводятся (сверка по цифрам телефона и адресу почты). Если в анализе явно записано,
  что телефона нет (заказчик без телефона), телефон со снимка сайта не берется.
- Подтверждение: /site-analiz (W3b) выводит контакты и реквизиты в документ 1 решением с кодом; ответ «верно» или
  правка идет штатно через лист ответов. Импорт ставит `company.status: confirmed` только если решение принято.
- `facts.company` собирается из тех же данных: `brand, legal_name, inn, ogrn, address, phones[], email, hours, channels,
  status, source`. `phones` и `wording` телефонов - в одном формате `+7 (XXX) XXX-XX-XX` (только российские 10-11 цифр;
  иные - как есть; `value` факта не меняется). `channels` - объект `{ "<ключ>": { label, value, href, fact? } }`,
  `href` - полный URL со схемой (`https://wa.me/7...`, `https://t.me/+7...`, `https://t.me/<ник>`, `https://vk.com/...`)
  или `''`. Каналы - из URL (как сейчас) и из контактных фактов, в label которых назван мессенджер; ссылку по номеру
  строить только для WhatsApp и Telegram; главный телефон в мессенджер не подставлять. Читатели принимают и старую
  форму (строка-URL).
- `contacts.mjs` экспортирует `normalizePhoneRu, phoneDigits, telHref, waHref, tgHref, buildChannels, phoneFormat`.
  Автоссылки в тексте сравнивают телефоны по цифрам, а не по строке.

### C3. Стратегия (схема - W1, промты - W2)
- Объект CTA везде (`global.cta_by_type[type]`, `pages[slug].cta`): `{ main, secondary?, action?, secondary_action?,
  short? }`. `action`/`secondary_action` - необязательные, одно из: `lead` (окно заявки), `page:<slug>`,
  `anchor:<id блока типа>` (id из файла типа, например `form`, `cta-final`, не `B05-...`), `messenger`, `call`.
  `short` - до 20 знаков. Нет `action` - сборщик применяет правило по умолчанию (C10). `cta_by_type[type]` в старых
  данных - строка; все читатели принимают и строку, и объект.
- Составитель решений (W3) пишет только тексты CTA; `action` ставит глобальный стратег, и только для перехода,
  мессенджера или звонка (форму сборщик находит сам).
- `pages[slug].exclude_blocks: [id блока типа]` - блоки типа, не нужные этой странице. `hero` исключать нельзя.
- `pages[slug].block_overrides.<id блока типа>`: `{ facts?: [id], objection_ids?: [id], task?: string }`.
  Явный список (в том числе пустой) окончательный для блока. **Явный пустой `facts: []` у блока, требующего фактов
  (`limits.drop_blocks_without_facts`), означает выпадение блока** (так Goldax выключал блоки, семантика сохраняется).
- В `task` id фактов только в утвердительной форме.
- `pages[slug].segment` может быть `"all"`; список сегментов берется из карты (C1).
- `secondary_segment` из промта стратега убрать (в схеме остается необязательным).

### C4. Бриф и срезы (владелец - W1; читают промты W2, сборщик W4a)
- `brief.cta` - объект C3.
- `brief.facts[]` - `{ id, label, value, wording, kind, angle?, note?, rule?, where?, owner_block? }`. `note` - условие
  факта из facts.json. `rule`/`where` - из decisions.md §1 (C6). `owner_block` - блок, за которым факт закреплен.
- `brief.unknowns[]` - строки: открытые вопросы (`facts.gaps`), label фактов с `publish: no`, строка «Открытые пробелы,
  по которым не пишем» из §1.
- `brief.segment` для `all` имеет ту же форму, что обычный сегмент: `{ id: "all", name: "<из словаря>", portrait,
  pains, fears: [], objections, comes_with? , segments: [{id, name, comes_with}] }`; `portrait` - склейка «кто
  приходит» по сегментам, `pains` - по одной главной боли каждого сегмента, возражения - назначенные стратегом.
  Поэтому слепой читатель, селектор и турнир работают без правок.
- Срез писателя `brief/<block_id>.json`: все факты страницы (как сейчас) с `owner_block`; `unknowns`; `rule`/`note`
  фактов; сегмент целиком; заметки агрегатора (`block.notes`) - не передаются; `note` элементов - только указания
  формы. Пожелания заказчика: пункты тона (d5) и прочие без адреса-блока - во все срезы; пункты с `where` = id/тип
  блока - в срез этого блока; первый экран - еще `candidate` и `where` из `hero|positioning|cta`.
- Судья и фиксер по-прежнему читают `brief.json` (облегченного брифа нет).
- `build-briefs.mjs`: проблемы (код 1) и предупреждения (код 0) разделены; сначала проблемы целиком, затем сводка
  предупреждений по видам со счетчиками и 2-3 примерами.
- `work/briefs-report.json` - сливается по страницам (сборка одной страницы обновляет только ее запись):
  `{ pages: { slug: { excluded, dropped: [{block, reason}], objections_unassigned, facts_dropped, structure_changed } },
  questions: [{ text, pages, blocks }] }`.

### C5. Каталог (владелец - W4b; рендер - W4a)
- `catalog-spec.filters[].values_source` - необязательное enum `analysis | fact | competitor | market_gap`. Значения
  с источником `competitor`/`market_gap` выводятся с пометкой «пример». Пустые `values` - группа с плашкой «нужны
  данные». У `range` - необязательные `min`, `max`, `step` (иначе сборщик берет границы по ценам примеров).
- `catalog-spec.card_fields[].type` - уже есть (`money` - цена; по нему сортировка и фильтр цены).
- Файл `work/catalog/sample-items.json` (схема `kit/schemas/sample-items.schema.json`):
  `{ generated_at, mode: "from_site" | "illustrative", items: [ { key, category_slug, name, price?, price_note?,
  attributes: [{ label, value }], facets?: { "<имя фильтра>": [строки] }, images: [ "work/catalog/samples/<файл>" ],
  source_url?, taken_at?, why? } ] }`. `category_slug` - slug страницы-листинга или `"*"` (карточка на весь сайт).
  `facets` - всегда массив строк (одно значение - массив из одного). `from_site` - реальные товары текущего сайта
  заказчика (не больше 8 категорий, по порядку карты, хабы не обходятся - берут примеры детей; подкатегория без
  своего товара берет товар родителя); `illustrative` - одна карточка `"*"`, `images: []`. Фото: 1-2 на товар,
  каждое не больше 200 КБ (брать самый легкий доступный вариант, например миниатюру), итог всех фото не больше 2 МБ.
- Рендер (W4a): фото встраиваются **один раз** в прототип (data URI в словаре картинок, карточки ссылаются на ключ),
  копии карточек не дублируют байты. Выдача категории: карточки своей категории, иначе карточка `"*"`, иначе
  карточка-шаблон; **товар чужой категории в выдачу не подставляется**. Выдача хаба с `listing: true` - по одной
  карточке каждой дочерней категории, затем копии. Копии - до `listing.cards_per_page` (не меньше 6, не больше 24).
  Каждая карточка с пометкой «пример» (`from_site` - «пример с текущего сайта»). Нет ни catalog-spec, ни примеров -
  карточки-шаблоны (штриховка, серые полосы, кнопка `card_cta.main` или главный CTA).
- Кнопки карточки: `card_cta.main` - окно заявки с названием товара; клик по карточке или `card_cta.secondary` -
  страница товара (`type: product`), если она есть в карте. Никакого угадывания по словам кнопки.

### C6. `rules/decisions.md` (шаблон - W2; заполнение - W3 агентом; парсер - W1)
- Новый файл начинается строкой-маркером `<!-- decisions:v2 -->`. Парсер §1 работает **только при маркере**; у
  старых задач (без маркера) `rule`/`where` не извлекаются и факты по «Где можно» не фильтруются.
- §1 заполняет только агент `01-decisions-drafter` (и человек при `--stop map`). Таблица
  `| Факт | Конфликт | Разрешенная формулировка | Где можно |`: первая колонка - один id факта; «Где можно» - `все` или
  список slug страниц и типов страниц из карты через запятую. Строка, где «Где можно» разбирается не полностью
  (есть неизвестный токен), дает предупреждение и **не фильтрует** факт (правило формулировки при этом действует).
  Факт снимается со страницы только при полностью распознанной колонке, не включающей эту страницу/тип.
- Отдельная строка `Открытые пробелы, по которым не пишем: g1, g4, ...` (id пробелов из `facts.gaps` или короткие
  формулировки).
- §3 CTA - тексты кнопок по типам (результатом для клиента, из ответа d3), без `action`.
- §6 - страницы вне периметра: агент может предложить только короткий набор блоков (`block_set: short`), но не
  снимать страницы (`skip` - только по явному решению анализа или человека); предложение - строкой в §8.
- §7 - пожелания заказчика (как сейчас).
- §8 «Спорное: решения агента» - строки «вопрос | что решил агент | почему». Сюда же пишут стратеги (вместо свободных
  правок §1) и рецензия стратегии. Отчет выводит §8 целиком (C9).
- Повторный запуск составителя (после правки анализа): дописывает недостающее, существующие строки не переписывает,
  строки об исчезнувших фактах помечает «(факт снят)».

### C8. Поток, состояния, волны, остановки (скрипты - W5; текст оркестратора SKILL.md - W6)
