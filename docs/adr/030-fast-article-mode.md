# ADR-030: Быстрый режим `--fast` для `/seo-statya`

**Статус:** Принято

**Дата:** 2026-07-30

## Контекст

`/seo-statya` в обычном режиме - качественный, но дорогой конвейер: 10+
вызовов субагентов (jm-analyst -> tz-builder -> section-writer xN ->
article-finalizer -> text-auditor -> article-fixer-batch -> enhancer ->
photo-promter -> photo-producer -> article-verifier), полный JM-цикл
(`text_generate` + `text_analyze`, ~20 лимитов, ~5-6 минут только на
`text_analyze` и без параллелизации с другими вызовами того же
JM-аккаунта), фото + docx + заливка в Drive. ~2 часа и заметный расход
лимитов на одну статью 2500-3500 слов.

Пользователю нужно закрывать объём - 30-100+ статей на клиентский блог -
не упираясь в лимиты нейросети и токен-бюджет, но не теряя главного:
статья должна реально отвечать на поисковый запрос человека, а не быть
формальной SEO-простынёй. Полный конвейер для такого объёма избыточен -
большая часть его стоимости (`text_analyze` по топ-10 конкурентов, фото,
docx, отдельный LLM-аудит) калибрована под флагманские длинные гайды, а
не под массовую выдачу.

## Решение

Добавлен аддитивный режим `--fast` внутрь существующего `/seo-statya` -
не отдельный скил, не переписывание существующего пайплайна. Алгоритм
вынесен в отдельный файл `FAST.md` рядом с `SKILL.md`/`REFERENCE.md`;
`SKILL.md` меняется в двух местах (сигнатура аргументов + одна ветка в
шаге 0b, читающая `FAST.md` при `--fast` и не возвращающаяся к остальным
шагам).

Ключевые упрощения относительно full-режима:

- **JM без анализа конкурентов.** `jm_text_analyze` в `--fast` не
  вызывается никогда - это осознанное решение, а не временная экономия.
  `jm_text_generate` (LSI) остаётся, но с широким переиспользованием
  кеша: не только по `topic_id` (как раньше), а и по нормализованному
  `main_query` среди ЛЮБЫХ статей проекта (агент `jm-analyst` получил
  параметр `depth: "lite"|"full"`, по умолчанию `"full"` для обратной
  совместимости).
- **Один агент вместо веера.** Новый `fast-writer` (opus) пишет всю
  статью - интро, H2-разделы, заключение с CTA, метатеги, минимальную
  плитку тегов - за один проход, заменяя связку tz-builder +
  section-writer(xN) + article-finalizer. Это прямое отступление от
  паттерна «каждый раздел = отдельный вызов для свежести контекста»
  ([ADR-020](020-writer-context-diet-and-voice.md),
  `docs/SKILL-ADAPTATION-GUIDE.md`) - оправдано тем, что тот паттерн
  калиброван под длинные (2500-3500 слов) статьи с жёсткой
  N-граммной глубиной по разделам, которой в fast-режиме нет вообще;
  для короткой (~800-1200 слов) статьи без глубины один проход дешевле
  и не теряет целостность (наоборот, у одного агента вся статья перед
  глазами сразу, не по кускам).
  - Целевой объём по умолчанию ~1000 слов (флаг `--words=N`), короче
    full-режима, т.к. нет N-граммной глубины конкурентов, которая
    задаёт объём там.
- **Механическая верификация вместо LLM-аудита.** `article-verifier` и
  `text-auditor` в `--fast` не используются - вместо них
  `verify-article-metatags.mjs` (переиспользован без изменений) и новый
  `verify-fast-style.mjs` (ё/тире в теле статьи, grep, без LLM). Частный
  случай отступления от паттерна финального верификатора
  ([ADR-025](025-final-verifiers.md)) - осознанный компромисс объём/цена
  для массового режима.
- **Без фото/enhancer/schema.org/docx/Drive/Тильды.** Вывод -
  `article.md` + `metatags.json` + минимальный `report.md` (только
  «Плитка тегов», для перелинковки в футере) + HTML через существующий
  `assemble-html.mjs` без изменений (скрипт уже gracefully обрабатывает
  отсутствие всех этих файлов).
- **Тема - номер из `topics.xlsx` ИЛИ свободный текст.** Свободная тема
  не получает синтетический числовой `topic_id` (это вернуло бы гонку
  счётчика между worktree, которую full-режим сознательно избегает - см.
  [ADR-013](013-numbering-by-topic-derived-index.md)): `topic_id = null`,
  папка `articles/fast-<slug>-<rand3>/` без числового префикса,
  `meta.source = "freeform"`. Работает только одиночным прогоном, не в
  батче.
- **`meta.pipeline = "fast"`** - новое поле в `meta.json`, отсутствие =
  `"full"`. Общие скрипты (`update-meta.sh`, `verify-article-metatags.mjs`,
  `resolve-article-dir.mjs`, `batch-queue.mjs`) уже полностью generic и
  не валидируют состав ключей - обратная совместимость подтверждена
  чтением кода, не только предположением.
- **`articles/_index.json` получил поле `query`** (`rebuild-index.mjs`,
  `update-index.mjs`) - без него поиск JM-кеша по `main_query` невозможен.
  Индекс производный и gitignored ([ADR-013](013-numbering-by-topic-derived-index.md))
  - расширение без риска обратной несовместимости.

## Альтернативы

- **Отдельный скил `fast-article`.** Отвергнуто пользователем явно: он
  предпочёл расширение существующего `/seo-statya`, чтобы не дублировать
  уже отлаженную машинерию (`meta.json`, `batch-queue.mjs`,
  `assemble-html.mjs`, verify-гейты) в параллельной системе координат.
- **Синтетический `topic_id = max(...)+1` для свободных тем.** Отвергнуто
  при ревью плана: реинтродьюсит ровно ту гонку счётчика между
  параллельными worktree, которую нумерация «по номеру темы из xlsx»
  сознательно избегает (см. [013](013-numbering-by-topic-derived-index.md)).
  Вместо этого - `topic_id: null` + непронумерованная папка.
- **Всегда JM lite (никогда не переиспользовать кеш).** Отвергнуто
  пользователем - «между совсем без JM и всегда лайт»: при батче
  статей с одинаковым или близким `main_query` кеш по нормализованному
  запросу экономит целый вызов `text_generate` (~15 лимитов) на статью.
- **section-writer по разделам, как в full-режиме, только короче.**
  Отвергнуто: overhead на вызов субагента (чтение STYLE.md/GENRES.md/
  предыдущих разделов на каждый H2) не окупается для статьи в 3-5
  разделов - один проход дешевле и не теряет целостность.

## Последствия

**Хорошо:** статья пишется за 2 вызова субагента (jm-analyst-lite +
fast-writer) вместо 10+, JM-лимиты - только LSI (или вообще 0 при
попадании в кеш по `main_query`), нет платного и небыстрого
`text_analyze`. Полностью совместимо с существующей серийной очередью
(`batch-queue.mjs`) и серийным финалом (`build-articles-xlsx.mjs`) без
единой правки в них. Формат `article.md`/`metatags.json` идентичен
full-режиму - fast-статью при необходимости можно вручную «дотянуть» до
полного качества на full-инфраструктуре.

**Плохо:** короче объём (~1000 слов против 2500-3500), нет N-граммной
глубины конкурентов (SEO-фактор из STYLE.md §9 приоритет 4 в fast-режиме
не работает), нет фото/визуального ряда, нет отдельного LLM-аудита -
качество зависит от одного прохода `fast-writer`, а не от
пишет-аудитор-фиксер цикла. Для флагманских/приоритетных тем full-режим
остаётся основным инструментом - `--fast` предназначен для объёма, не
для замены.
