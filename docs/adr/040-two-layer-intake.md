# ADR-040: Двухслойный интейк - факты для анализа отдельно от лексикона для текстов

**Статус:** Принято

**Дата:** 2026-08-23

## Контекст

Боевой прогон конвейера v7 (23.08.2026) показал цену единого `intake.json`:

- файл вышел на **146-150 КБ / 231 факт**;
- из них **62 факта - чистое сырье для копирайтинга**: дословные формулировки заказчика,
  внутренние термины, образы и метафоры, картина жизни клиента «до и после»;
- шаг интейка стоил **14 мин 34 сек и 167 тысяч токенов**;
- **файл читают ВСЕ ступени анализа** (бриф, ЦА, конкуренты по касательной, писатель,
  верификатор), а копирайтерское сырье нужно ровно одной из них - анализу ЦА.

То есть четверть объема самого тяжелого артефакта анализа прокачивается через контекст
ступеней, которым она не адресована. Одновременно падает плотность полезной части: одна
мысль разложена на несколько записей, дубли не схлопнуты - на 231 факт содержательного
материала заметно меньше.

Разделять надо по записям, а не в промтах: инструкция «читай только нужные тебе поля» не
уменьшает файл, потому что лексиконные и аналитические факты перемешаны в одном массиве
`facts[]` и попадают в контекст вместе.

## Решение

### 1. Три артефакта интейка вместо двух

`intake-analyst` пишет ТРИ артефакта вместо двух:

1. `<task_dir>/intake.json` - **факты для анализа**. Все поля словаря `field`, КРОМЕ четырех
   лексиконных. Бюджет: **80-120 фактов** (не жесткий отказ, а требование к плотности:
   дубли схлопывать, один факт = одна мысль; если фактуры реально больше - можно превысить,
   но в сводке в чат честно назвать число и причину).
2. `<task_dir>/intake_lexicon.json` - **сырье для текстов**. РОВНО четыре поля:
   `client_wordings`, `internal_terms`, `client_metaphors`, `client_life_before_after`.
   Бюджета на число записей нет - дословность важнее.
3. `<task_dir>/ВВОДНЫЕ.md` - как и был (человекочитаемый конспект, обе части внутри).

### 2. Схема `intake_lexicon.json`

Ровно та же форма, что у `intake.json`, чтобы потребители не писали второй парсер:

```json
{
  "sources": [ { "id": "...", "type": "...", "path": "...", "label": "..." } ],
  "facts":   [ { "field": "client_wordings", "value": "...", "source": "...", "quote": "...", "decision_impact": true } ],
  "gaps":    [ "client_metaphors: образов и метафор в источниках нет" ]
}
```

- `sources[]` - дублируется из `intake.json` целиком (файл должен читаться автономно).
- `facts[]` - только четыре лексиконных поля. Никаких других полей тут быть не может.
- `gaps[]` - только пустоты по этим четырем полям (в `intake.json.gaps` они больше не пишутся,
  чтобы не задваивать).
- `conflicts` в лексиконе не бывает - не заводить.
- Правило «ключей верхнего уровня с именами полей нет» действует и здесь.

### 3. Кто что читает (обязательно к соблюдению)

| Потребитель | intake.json | intake_lexicon.json |
|---|---|---|
| `brief-structurer` | да | нет |
| `audience-analyst` | да | **да** (живые формулировки ЦА) |
| `competitor-finder`, `leader-scanner`, `direction-scanner`, `serp-verdict` | нет (как и было) | нет |
| `analysis-writer`, `analysis-verifier` | да | нет |
| `pages-planner` | да | нет |
| `offer-strategist` | да | **да** (метафоры и «до/после» - топливо оффера) |
| `page-writer` | да (факты страницы) | нет - словарь получает через `facts.json.lexicon`, см. [ADR-033](033-project-lexicon.md) |
| мост `read-tekst-input.mjs` | да | да, для слияния и разбора; `lexicon.locked` не сеется автоматически, правило трех оснований [ADR-033](033-project-lexicon.md) |

### 4. Диета контекста в промтах ступеней

В делегирующих промтах ступеней 1-3 `/seo-analiz` (бриф, ЦА, конкуренты) - явный список
веток, которые агент читает, и явная фраза, что лексиконные поля ему НЕ нужны
(кроме `audience-analyst`, которому лексикон нужен целиком).

## Альтернативы

- **Оставить один файл, а разделение свести к диете в промтах.** Отвергнуто: это и было
  текущим состоянием. Пока лексикон лежит внутри `intake.json`, любая ступень, читающая
  файл, платит за него контекстом; инструкция «пропусти эти поля» экономит внимание агента,
  но не токены.
- **Сразу писать лексикон в `audience.json` или в `facts.json` текстов.** Отвергнуто:
  интейк - ступень 0, `audience.json` появляется на ступени 2, а `facts.json` вообще
  принадлежит другому скилу. Лексикон - сырье с провенансом, а не готовый словарь проекта;
  превращение сырья в `facts.json.lexicon` остается работой моста и оркестратора текстов
  (ADR-033).
- **Резать интейк дальше - файл на группу полей.** Отвергнуто: шов проходит ровно по одной
  границе «нужно анализу / нужно письму», остальные группы читаются одними и теми же
  ступенями. Каждый дополнительный файл - еще одна пара «писатель-читатель» и еще один
  повод рассинхрона.
- **Просто ужать бюджет всего интейка.** Отвергнуто: бюджет по плотности нужен фактам
  анализа, а лексикону противопоказан - там ценность именно в дословности, схлопывать
  формулировки заказчика нельзя.

## Последствия

**Хорошо:** ступени анализа перестают читать копирайтерское сырье; бюджет 80-120 фактов
делает `intake.json` плотным, а не длинным; лексикон получает собственный файл, где
дословность не конкурирует за место с фактурой; форма файла совпадает с `intake.json`,
поэтому новых парсеров нет.

**Плохо / цена:** артефактов интейка стало три, `sources[]` дублируется в двух файлах
(плата за автономное чтение лексикона); у читателей лексикона появляется ветка легаси
(ниже); при ручной правке одного файла второй может отстать - синхронизирует только
перезапуск ступени 0.

**Связь с [ADR-020](020-writer-context-diet-and-voice.md) и [ADR-033](033-project-lexicon.md).**
Второй файл интейка НЕ становится новым обязательным чтением писателя страниц:
`page-writer` берет словарь из `facts.json.lexicon`, а сырой `intake_lexicon.json` не
читает. Это не недоделка, а прямое следствие двух ранее принятых решений. Во-первых,
потолок диеты ADR-020: `page-writer.md` + `VOICE.md` - не более 33 000 знаков, а по
замеру на 23.08.2026 занято 32 992, свободно 8 - места на инструкцию про еще один
входной файл физически нет. Во-вторых, порядок ADR-033: сырье с провенансом
превращается в словарь проекта руками моста и оркестратора `/seo-tekst`, писатель
получает уже собранный словарь. По той же причине мост лексикон только СЛИВАЕТ для
разбора: `lexicon.locked` он не сеет намеренно - вход в `locked` дает правило трех
оснований ADR-033 (решение оркестратора на гейтах), и это сторожит тест
`.claude/tests/seo-tekst/run.mjs` (сверка B). Реальные читатели `intake_lexicon.json` -
`audience-analyst`, `offer-strategist` и мост.

### Обратная совместимость (ОБЯЗАТЕЛЬНО)

Клиентские проекты, где анализ уже прогнан, имеют старый однослойный `intake.json` с
лексиконными фактами внутри. Поэтому все читатели лексикона обязаны работать так:

> Если `intake_lexicon.json` есть - лексиконные факты берутся из него.
> Если файла нет - лексиконные факты ищутся в `intake.json.facts[]` по тем же именам полей
> (легаси-режим однослойного интейка). Отсутствие обоих - не авария, лексикон просто пуст.

Для `read-tekst-input.mjs` это означает: слить `facts[]` из обоих файлов в один список перед
разбором, а в сводку печатать, откуда взят лексикон (`intake_lexicon.json` | `intake.json (легаси)`).

## Связь с ADR-028 и ADR-033

Ни одно решение этих ADR не отменяется - меняется только адрес хранения четырех полей.

- **[ADR-028](028-intake-provenance-and-questions.md) (провенанс интейка).** Контракт факта
  не тронут: `source` + `quote` + `decision_impact` обязательны в обоих файлах, и `sources[]`
  в лексиконе - копия того же реестра источников. Канал дозаписи подтвержденных клиентом
  own_page-фактов (`source: "own_page:<url>"`) остается адресованным `intake.json`:
  это фактура анализа, а не лексикон.
- **[ADR-033](033-project-lexicon.md) (словарь проекта `facts.json.lexicon`).** Владельцы
  наполнения словаря те же, порядок сборки тот же: кандидаты `client_wordings` /
  `internal_terms` / `client_metaphors` собирает `intake-analyst`, спаривание и перенос
  в `facts.json.lexicon` - работа моста и оркестратора `/seo-tekst`. Уточняется одно:
  кандидаты лежат в `intake_lexicon.json`, а при его отсутствии - там же, где и раньше,
  в `intake.json` (легаси-режим выше). Отвергнутая в ADR-033 альтернатива «отдельный файл
  `lexicon.json`» не пересматривается: речь по-прежнему не о словаре проекта, а о сыром
  входе с провенансом, и число обязательных чтений у писателя не растет.
