# ADR-044: `/site-tekst` - прогон без гейтов с автостопом по аномалиям, один прототип-сайт со служебным слоем

**Статус:** Принято

**Дата:** 2026-09-27 (дополнено 2026-09-28: раздел 5, программа исправлений по аудиту)

> Дополняет [ADR-041](041-v9-site-analiz-single-entry-and-site-tekst.md): заменяет его пункт «Гейты человека» (гейты 1-4
> текстов) и прототип-вайрфрейм kit. Остальное в ADR-041 в силе. [ADR-039](039-single-file-prototype.md) не затронут:
> он уже заменен ADR-042.

## Контекст

- **Прогон Goldax** (`goldax_ru`, `texts/001-goldax`: 22 рабочие страницы, 172 блока, 44 факта) прошел по v9 с гейтами
  1-4. Гейты превратились в ручную проверку текстов: после судей оператор нашел 92 проблемы (32 major), гейт 4 пришлось
  делегировать агенту на ночь, на переделки ушло около 10 млн токенов из 72. Решения гейта 1 (конфликты фактов, CTA,
  периметр) оператор выводил из того же анализа, который уже прочитан агентами.
- **Прототип kit - вайрфрейм.** Серые рамки, подписи блоков, вопросы читателя: для аудита текстов полезно, но заказчик
  по нему не видит сайт, и хорошие тексты воспринимаются как документ. Для Goldax собран второй файл `site.html`
  проектными overrides (оболочка, CSS, свой сборщик) - с нишевым содержимым, в другой проект не переносится.
- **Тихие дефекты**, найденные прогоном: сборка брифов (возражения терялись до выпадения блоков, id фактов брались из
  отрицаний, блок получал первые 6 фактов вида), импорт (конкуренты «Имя - домен», волны по глубине URL, контакты не
  становились фактами), окружение (вложенность `wf-05`, `fetch` из node, один браузер на всех агентов, выключенный
  Google Docs API).
- Решения владельца - раздел 0 спецификации `docs/upgrade-program-2026-09-27-site-tekst-goldax.md`: прогон без
  остановок, один прототип, никакой нишевой конкретики в kit, заказчик видит только финальный прототип.

## Решение

### 1. Прогон без гейтов по умолчанию

- **States прежние** (совместимость со старыми задачами): `init -> facts-done -> map-approved -> ... -> strategy-done ->
  strategy-approved -> waves-done -> catalog-done -> built -> completed`. Переходы `facts-done -> map-approved` и
  `strategy-done -> strategy-approved` - автоматические, волны идут подряд, затем каталог, сборка, отчет, сдача.
  `pilot-done`, `pilot-approved`, `wave-1-done`, `wave-1-approved` проходятся только при паузе пилота; задача в старом
  гейтовом state при `--resume` продолжает вперед без показа гейта.
- **Кто делает работу гейтов.** Решения гейта 1 заполняет агент `01-decisions-drafter` в фазе 0: `rules/decisions.md`
  формата v2 (маркер `<!-- decisions:v2 -->`, §1 «Где можно» разбирает сборщик брифов, §8 «Спорное: решения агента»).
  Стратегию проверяет рецензия (`04-strategist-global` в режиме review по матрице `merge-strategy.mjs --matrix`), затем
  брифы собираются повторно. Вопросы копятся в отчете `work/output/report.md` («Что спросить у заказчика»).
- **Ручная пауза** - одноразовый флаг `--stop map|strategy|pilot` (`meta.stop`); `--pilot a,b` = `--stop pilot` с этим
  пилотом; `--allow-ungated` без `--stop` - пауза пилота (пилот до гейта анализа, как раньше).
- **Автостоп только по аномалии**, машинной проверкой по `task.mjs status`, возвратам воркфлоу и кодам скриптов. Примеры:
  фаза 0 не дала сегментов или решений v2, «Где можно» не разобрано и после повтора составителя, ноль фактов анализа с
  `publish: yes` после гейта, брифы с проблемами или их мало, запись не продвигается, у образца типа в волне 1 exhausted
  не меньше 2 блоков и больше 30%, по всем волнам недописано больше 30%, сборка прототипа или его проверки падают после
  пересборки, воркфлоу падает подряд. Полный перечень условий и действие после снятия ведет только таблица «Автостопы» в
  SKILL.md скила (RUNBOOK kit ссылается на нее); здесь он не повторяется. Причина пишется в `meta.autostop` (`task.mjs stop --autostop`); `--resume` не идет дальше, пока
  человек не решит продолжить, и тогда оркестратор снимает автостоп и сразу отмечает точку пройденной (переход state или
  `meta.wave`), чтобы проверка не сработала снова. Пауза и автостоп пишутся только `task.mjs stop`, не `update-meta.sh`.
- **Страница не встает на трудном блоке.** Блок, не прошедший линтер, не останавливает страницу; после двух неудачных
  запусков по тому же срезу брифа (`attempts`, `brief_sha` в файле блока) он exhausted: в прототипе скелет, в отчете
  строка. Новый срез (новые факты) снова отдает блок писателю.
- **Волны - по карте, стабильно** (`scripts/progress.mjs`): волна 1 - главная и первая страница каждого типа с 2+
  страницами, волна 2 - остальные. Поле `wave` карты больше не пишется и не читается.
- **Ответы заказчика после сдачи** идут через анализ: `/site-analiz` (новый круг листа ответов) ->
  `import-project.mjs --facts-only` -> фаза 4 в режиме обновления (раздел 5) -> брифы -> запись и аудит измененного ->
  сборка. Точечная правка заказчика - факт оператора `F801`-`F899` с источником, отчет печатает такие факты строками листа
  ответов анализа («перенести в анализ»).
- **Гейт анализа** `/site-analiz` (подтверждение фактов заказчиком); к нему добавлено решение d10 - контакты и реквизиты
  для сайта (служебные факты `F901`-`F907`, `company.status: confirmed` только при d10 без правки). С 28.09 гейт
  проверяет готовность анализа (`gate.checks`), а `/site-tekst` считает его пройденным по `nextStep(...).n === "-"`.

### 2. Один прототип-сайт со служебным слоем

- `work/output/prototype.html` - один файл, выглядит как готовый сайт (строго ч/б; визуальный эталон - `site.html`
  Goldax без нишевого содержимого): шапка, мега-меню, первый экран, каталог с фильтрами, страница товара, мобильное
  меню, окна. Блоки писателя - дословно; ненаписанный блок - скелет.
- Служебный слой (id блоков, вопросы читателя, опорные факты, подсветка утверждений без опоры, список страниц) скрыт и
  включается клавишей D или `?debug`. Второго файла нет.
- Проверки `check-html.mjs` (дословность, один h1, серые цвета, мертвые кнопки, внешние ресурсы; код 0/1/2) и
  `check-site-js.mjs` (jsdom: маршруты, клики, ошибки скриптов) идут везде, где собирается прототип (фаза 8, сборка
  после `--fix`); итоги - в отчете.

### 3. Модули из данных и реестр поведений

- Оболочка и модули строятся только по данным проекта: карта (`ui_role`, `nav_label`, `listing`, `template`), контакты
  (`company.channels`), каталог (`catalog-spec.json`, `sample-items.json`), `config.site` (`nav`, `off`, `tagline`).
  Модуля без данных в файле нет вовсе: у сайта услуг нет каталога, корзины и поиска.
- Любой блок отрисовывается без правки кода: раскладка типа -> раскладка по умолчанию для pattern -> секция по
  элементам (`pattern: custom`). Новый живой блок (калькулятор, квиз, онлайн-запись) - одна запись в реестре
  поведений `REGISTRY` (`scripts/site-parts.mjs`) и стили.
- Подписи интерфейса - словарь `html/site/ui.json`; кириллицы вне словаря в коде сборщика нет (тест). Демо-данные -
  только с пометкой «пример».

### 4. Ниша - только в overrides проекта

В kit нет нишевых слов и примеров: нишевые основы `claim_markers` прошлых проектов перенесены в
`examples/lint-niche-markers.example.json`, нишевые правила промтов переписаны категориями. Проектная ниша - в
`overrides/` задачи (`rules/*.md`, `rules/lint.json`, `html/site/ui.json`). Новые файлы оболочки лежат в `html/site/`,
чтобы не совпасть по пути с проектными overrides Goldax (`overrides/html/site-shell.html`, `site.css`).

### 5. Дополнения 28.09 (независимый аудит, `docs/upgrade-program-2026-09-28-audit-fixes.md`)

- **Порядок фазы 6 (решение Р4, вариант Б).** Судья и слепой читатель страницы параллельно, оба только читают -> снимок
  блоков -> один фиксер по всем находкам страницы (судья, линтер страницы, слепой) -> `fix-diff.mjs`: откат блока, который
  правка сломала (находка снова open), и признак правок утверждений считает скрипт, а не фиксер -> второй круг судьи по
  blocker, оценкам ниже порога, правкам утверждений, откату или линтеру -> фиксер в режиме сужения (только удалить,
  вернуть условие, подставить формулировку факта; minor - в отчет без правки). Кросс-судья зовется, только когда есть что
  сравнивать; его фиксеры тоже сужают. Третьего судьи нет: правки без проверки судьей - отдельный раздел отчета и число в
  итоге сдачи. Прежнее «третьего судьи нет» (последние фиксеры правили без проверки) заменено этим порядком; полная
  перестановка фазы 6 отложена до следующего боевого прогона.
- **Режим обновления стратегии.** Ответы заказчика после сдачи не гонят фазы 0 и 4 с нуля: `--facts-only` сравнивает
  анализ с отпечатком прошлого импорта, wf-04 с `update` переносит прежние записи стратегов и правит их только по
  `facts_diff`, с `enrich` - обогатитель карты `mode=facts` со сверкой карты скриптом, `skipLayouts` - без раскладок.
- **Исключение Р6 из «никаких `ctaAttrs` по словам кнопки».** Вторая кнопка CTA без `secondary_action` ищет действие по
  подписи (`secondaryByText` в `site-parts.mjs`: точное имя канала из `company.channels` или основа маршрута из `ui.json` при
  известном адресе) только при старом формате CTA - в стратегии и брифах нет ни одного `action`/`secondary_action`
  (`S.ctaLegacy`; пометка `prototype.modules.json` -> `cta_secondary.legacy_cta`). Это узкий запасной путь для данных до
  контракта C3; в новых прогонах действие задает стратег (у страниц с выдачей главная кнопка - `anchor:` к листингу).
- **Частичные правки проекта.** `overrides/` задачи: `.json` сливается с файлом kit по RFC 7396 (массив и значение правки
  заменяют значение kit, `null` удаляет ключ), `.md` с первой строкой `<!-- overrides:append -->` - файл kit и дописка,
  прочее - полная замена. `task.mjs place` кладет, сравнивает и хеширует итог. База сверки полных замен - `meta.json`
  `overrides_base` (git blob id kit и override; в git, переживает смену worktree; первая база - kit на последнем коммите
  override): kit обновил файл - `place` печатает команду `git diff <база> <kit>`, пока override не изменится или сверка не
  отмечена `--reconciled`. Причина: полная замена молча замораживала исправления kit (у Goldax - правила против выдумок).
- **Живые блоки проекта без форка.** Необязательные `overrides/html/site/registry.json`
  (`{ "<pattern | custom_name | type:<id>>": { "behavior": "<имя>" } }`) и `overrides/html/site/behaviors/<имя>.js` (+ `.css`)
  сливаются с реестром сборщика; нет файлов - поведение kit. Пары в kit у них нет, в слияние и в строку «правки без пары в
  kit» они не идут.

## Альтернативы

- **Оставить гейты 1-4.** Отвергнуто: главная цена прогона - ручная проверка на гейтах, а их решения выводятся из
  данных, которые агенты уже читают; ошибку, которую гейт ловил бы, теперь ловят составитель решений, рецензия
  стратегии и автостопы.
- **Флаг `--auto` поверх гейтов.** Отвергнуто: два режима, и по умолчанию остался бы медленный. Пауза - явный
  одноразовый флаг `--stop`.
- **Два файла: вайрфрейм для аудита и сайт для заказчика.** Отвергнуто владельцем: служебный слой в том же файле
  закрывает нужды аудита.
- **Перенести сборщик `build-site.mjs` Goldax как есть.** Отвергнуто: в нем нишевое содержимое и конфиг под одну нишу;
  перенесены внешний вид и поведение, ниша выброшена.
- **Кастомное ТЗ заказчика в алгоритме (`--tz`, сверка с ТЗ), `config.site` на десятки полей, адаптеры ниш.**
  Отвергнуто: документы заказчика идут через `input/` анализа, прототип строится из данных.

## Последствия

**Хорошо:** заказчик видит сайт, а не документ; прогон идет без оператора от импорта до сдачи; вопросы заказчику -
в одном разделе отчета; трудный блок не останавливает страницу; новый вид блока не требует правки кода.

**Плохо / цена:** без гейтов ошибка карты или стратегии видна только в отчете и прототипе - митигация: составитель
решений консервативен и пишет спорное в §8, рецензия стратегии, автостопы, ручная пауза `--stop`. Проверка скриптов
прототипа требует `jsdom` в `node_modules` клиентского проекта, иначе SKIP (виден в отчете и в итоге сдачи). Строку
`/site-tekst` в `.claude/CLAUDE.md` клиентов синк обновляет, только если клиент файл не правил (с 28.09, ADR-019);
клиентскую правку - вручную. Исключение Р6 (раздел 5) - осознанный долг совместимости: снимается, когда старых данных без
`action` в работе не останется. У Goldax проектные
`overrides/html/site-shell.html`, `site.css` и `overrides/scripts/build-site.mjs` больше не используются - снять их в
сессии клиента.

**Проверка:** набор `tests/site-tekst` (`cases-*.mjs` пакетов, `workflow-models.mjs`, холостой прогон `run.mjs`, три
фикстуры: магазин, услуги, лендинг), наборы `site`, `sync`, `machinery`.
