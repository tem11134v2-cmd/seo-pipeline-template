# ADR-031: Автономный источник текстов от брифа (`--from-brief`) без SEO-артефактов

**Статус:** Частично заменено (см. [ADR-038](038-tiered-analysis-and-writing-split.md))

**Пересмотрено 2026-08-22 (v7, ADR-038):** источник `--from-brief` удален - путь клиента без SEO теперь `/seo-analiz --no-seo` -> `/seo-tekst --from-analysis` (интейк, ЦА и разведка живут в анализе, вето владельца на проверки спроса действует на весь tier=basic). Живыми остаются: `pages-planner` (v2 - быстрая структура из анализа + гейт состава, когда структуры нет) и главный предохранитель п.7 «деградация только отсутствием данных, никогда флагом режима» - он переезжает на мост анализ -> тексты.

**Дата:** 2026-08-19

## Контекст

`/seo-tekst` спроектирован как звено коммерческого трека и питается выходами предыдущих услуг:
`--from-structure` (структура сайта), `--from-analysis` (предпроектный анализ), `--from-table`
(готовая таблица посадок). Появился класс проектов, где SEO не покупается вообще: партнер-
разработчик делает сайты по ТЗ и хочет только конверсионные тексты + прототипы. Ни анализа,
ни структуры по таким проектам не будет, `ЗАКАЗЧИК.md` тоже нет (он появляется после
`/seo-shablon`, а сайта еще не существует).

Разбор кода показал, что зависимость от SEO у скила гораздо уже, чем кажется:

- `audience-analyst` и `offer-strategist` уже принимают `analysis_dir` как **опциональный**.
- `direction-scanner` использует `pages.json.marker` как обычную строку для SERP и явно
  умеет фолбэк на первый запрос страницы. Выгрузки JM/Keyso ему не нужны.
- `block-planner`, `page-writer`, `copy-auditor`, `site-reviewer`, `prototype-builder`
  читают только `texts_dir/*` и kit. Про источник страниц не знают ничего.

То есть SEO-зависимым является **только вход** скила: `pages.json` + `inputs.json` +
`facts.json` (шаги 1c-2). Тело конвейера (2b-9) уже source-agnostic.

Требование заказчика функциональности: это должен быть **режим одной сущности**, а не форк.
Улучшения качества копирайта обязаны автоматически распространяться на все источники.

## Решение

**1. Не новый режим и не новый скил, а четвертый источник: `--from-brief [<путь>]`.**

Ось «источник страниц» уже существует (`--from-structure|--from-table|--from-analysis`).
Автономный кейс встает в тот же ряд. Тело конвейера не получает **ни одной** новой развилки,
`--mode A|B` остается независимой осью (для brief по умолчанию `A`).

**2. Упаковщик брифа - обобщенный `intake-analyst`, а не второй агент.**

Агент, читающий бриф/созвоны/файлы и выдающий факты с провенансом (`source` + `quote`) плюс
`gaps` и `conflicts`, уже написан для `/seo-analiz` (ADR-028). Второй такой агент создал бы
ровно ту раздвоенность, против которой затевался режим. Вместо этого:

- вход `analysis_dir` обобщен до `task_dir` (легаси-имя принимается как алиас);
- добавлен параметр `profile: analysis | tekst`, который переключает **словарь полей**
  (в `tekst` добавлены реквизиты, цены, гарантия, материалы, состав страниц, OPSEC);
- форма выхода (`intake.json` + `ВВОДНЫЕ.md`) не меняется.

**3. Новый агент ровно один - `pages-planner`.**

Состав страниц в брифе на разработку бывает и готовым (ТЗ перечисляет страницы), и
отсутствующим. Агент сам определяет, что перед ним, и работает в одном из двух режимов:
`extracted` (извлечь, нормализовать типы по словарю BLOCKS, добрать пробелы вопросами) или
`designed` (спроектировать состав из ассортимента/услуг). Выход - `pages_draft.json`
(страницы + открытые вопросы). Инструменты только `Read`/`Write`: отсутствие MCP - это
техническая граница режима, а не пожелание.

**4. Гейт состава - чат плюс секция в существующем документе, а не второй Google Doc.**

Состав подтверждается в чате (`AskUserQuestion`, быстро, с тем, кто заказал работу), после
чего попадает секцией «0. Состав страниц» в уже существующий `Analysis_<slug>.docx`, который
и так обязателен по гейту шага 5. Итог: один клиентский круг вместо двух, ноль новой обвязки
с Drive, состав при этом документирован и подписан. Секция рендерится только когда
`pages.json.source` начинается с `brief:`.

Если заказчик правит состав на позднем гейте - берем дифф `pages.json` и до-прогоняем
`direction-scanner` только по добавленным страницам.

**5. Лидеры для скана блоков берутся из уже оплаченной разведки.**

`leader-block-scanner` (шаг 2b) питался лидерами из структуры/анализа, которых в автономном
режиме нет. По ADR-017 для каталогов этот скан обязателен. Решение: `leader-block-scanner`
получил опциональный вход `leaders` (явный список доменов), а в brief-источнике порядок
шагов меняется на `2c -> 2b`: `direction-scanner` уже возвращает `competitors[]` в каждом
`recon/<slug>.json`, и топ-3 самых частых домена становятся лидерами. Новых MCP-вызовов ноль.

**6. Проверки поискового спроса в режиме НЕТ.**

Рассматривалась дешевая батч-проверка частотности названий страниц для защиты дробления.
Отклонено сознательно: режим не должен иметь отношения к SEO. Маркером служит название
направления. `direction-scanner` остается включенным - он не меряет частотность и не
оптимизирует под выдачу, а инвентаризует, какую информацию публикуют конкуренты; это вход в
качество копирайта, и выключается существующим `--no-recon`.

**7. Предохранитель против форка качества (главное).**

**Деградация выражается только отсутствием данных, никогда - флагом режима.**
`block-planner`, `page-writer`, `copy-auditor`, `site-reviewer`, `prototype-builder` не
должны узнать, что автономный источник существует. Условия вида «если есть `leader_blocks`»
и «если есть `recon`» в их промптах - единственный разрешенный способ учесть нехватку
данных. Любой `if mode == brief` в пишущем агенте означает, что режим начал форкаться, и
должен быть отклонен на ревью.

## Альтернативы

- **Отдельный скил `/tekst-avtonom`.** Отвергнуто: две сущности, качество копирайта
  расходится с первой же правкой `VOICE.md`.
- **Флаг `--mode C` (автономный).** Отвергнуто: смешивает две ортогональные оси. `--mode`
  отвечает на «новый сайт или существующий», источник - на «откуда состав страниц».
  Автономному проекту нужны обе оси независимо.
- **Второй агент-упаковщик под тексты.** Отвергнуто: дублирует `intake-analyst`, провенанс
  фактов пришлось бы улучшать в двух местах.
- **Отдельный Google Doc на согласование состава (исходное предложение).** Отвергнуто: два
  клиентских круга и два revising-цикла в режиме, который затевался как быстрый. Состав
  все равно получает подпись - секцией в документе, который уходит клиенту по гейту.
- **Мини-`/seo-struktura` из брифа.** Отвергнуто: тянет за собой маркеры, `semantic_pack`,
  каннибализацию и топ-10 - то есть ровно ту сеошку, ради отсутствия которой режим и нужен.

## Последствия

- Партнер-разработчик обслуживается тем же конвейером: `/new-project <slug> none` ->
  `/seo-tekst --from-brief <бриф>`. Предпродажные услуги не требуются.
- Улучшения `VOICE.md` / `COPY.md` / `BLOCKS.md` / промптов писателей действуют во всех
  источниках сразу - развилки в теле нет.
- Без структуры теряются проверенные маркеры: дробление страниц опирается на бриф и
  подтверждение заказчика, а не на спрос. Это принятый размен (п. 6), а не дефект.
- `intake.json` появляется в двух типах задач (`analyses/`, `texts/`) с одинаковой формой -
  будущие потребители фактуры могут читать ее единообразно.
- Клиентские клоны получают режим через `/sync-all --apply` (ADR-019); клиентские файлы не
  затрагиваются, миграция данных не нужна - новые артефакты появляются только у новых задач.
