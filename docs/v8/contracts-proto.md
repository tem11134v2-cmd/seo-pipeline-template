# contracts-proto.md - форматы слоя письма v8

Читают их `plan.mjs`, задание автору, `site-author`, `lift.mjs`, `verify-page.mjs`,
`site-strengthener`, `site-judge` и `site-editor`. Вход у всех один - `project.json`
этапа 1 плюс файлы отсюда. Полей-обоснований (`rationale`, `why`, `note`, `confidence`,
`evidence`, `status`, `function_why`, `client_why`) тут нет: причина живет в коде
правила, а не в строке данных.

**Граница среза.** Путь письма собран для всех семи типов: `landing`, `home`, `service`,
`category`, `facet`, `product`, `info`. Данные каталога готовит режим магазина
(`catalog.mjs`, `render-products.mjs`, `build-catalog-tz.mjs`, форматы -
`docs/v8/contracts-catalog.md`), а текст пишет тот же один автор тем же трактом: третьего
движка письма нет. За границей среза осталась СТРУКТУРА сайта: `/seo-struktura` живет
машинерией v7 и на контракт v8 в этой работе не переводится.

## 0. `pages.json` - адреса и слаги

Пишет `pages.mjs` на шаге 1, читают `plan.mjs` (поле `dir` привязывает сегменты к
направлению), `build-tasks.mjs` и `assemble.mjs` (поле `name` - имя в меню), `verify-page`
(правило `bad_link`: адрес, которого тут нет, писать в текст нельзя).

```json
{"v":1,"slug":"nevskiy","at":"2026-09-16","site_kind":"multipage",
 "pages":[{"url":"/remont-vannoy-komnaty-klyuch/","slug":"remont-vannoy-komnaty-klyuch",
           "type":"service","marker":"ремонт ванной комнаты","name":"Ремонт ванной",
           "dir":"remont-vannoy","parent":"/","fixed":false}],
 "redirects":[{"from":"/vannaya/","to":"/remont-vannoy-komnaty-klyuch/"}],
 "warnings":["/uslugi/ и /services/ метят один маркер"]}
```

| Поле | Что это |
|---|---|
| `url` | адрес страницы. У главной и у лендинга - `/`, и `slug` при этом ПУСТ |
| `slug` | сегмент адреса. Имя файла считает правило `pageName` из `_contract.mjs`: слаг, а при пустом слаге - `index`. Правило одно на все пять скриптов; сверять страницу с планом по голому слагу нельзя - у главной он не совпадет никогда |
| `type` | один из `PAGE_TYPES`. `category`, `facet` и `product` типизируются из `catalog.json`: узел дерева, ИНДЕКСИРУЕМАЯ посадка и карточка тира A. Посадка, закрытая `canonical` либо Clean-param, страницей письма не становится: мы сами склеили ее с категорией, и свой текст ей писать не за что. Узел в режиме `service_like` получает тип `service` и идет обычным трактом письма |
| `marker` | запрос-маркер направления, стоит в H1 дословно |
| `name` | короткое имя для меню сборки. H1 туда не идет: заголовок-ответ в меню занимает три строки |
| `dir` | id направления из `business.directions[]`: по нему `plan.mjs` берет сегменты, которые обслуживает страница |
| `parent`, `fixed` | место в дереве и признак «адрес уже живет, не пересоздавать» |
| `from_catalog` | страница рождена из `catalog.json`. По нему `plan.mjs` держит узлу `service_like` потолок 6 блоков вместо вилки страницы услуги, а `build-tasks.mjs` печатает в задание блок КАТАЛОЖНЫЕ НОРМЫ |
| `kids`, `sku` | только у каталожной страницы: сколько у узла потомков и сколько в нем позиций. Это МАТЕРИАЛ каталожных блоков: у такой страницы `dir` пуст, и без этих двух чисел плитка подкатегорий и блок похожих позиций уходили бы в снятые на каждом узле |
| `redirects` | смена адреса, ложится в `redirects.csv` |
| `warnings` | каннибализация и прочее, что ловится до письма |

## 1. `leaders/<cluster>.json` - замер рынка

Кластер - это ТИП СТРАНИЦЫ (`landing`, `home`, `service`, дальше `category`, `product`):
рынок ставит на главной и на услуге разные блоки, и общая куча не меряет ничего. Пишет
`recon.mjs parse`.

| Поле | Что это |
|---|---|
| `attempted` | адресов пробовали снять |
| `alive` | сколько ЖИВЫХ: из main без навигации и без разделов, повторяющихся на двух адресах домена, снято от 3 заголовков и 800 знаков |
| `measured` | `alive >= 3`. При `false` правила R1 и R2 не применяются вовсе, а в отчет идет строка «померено на N из M» |
| `cov` | `{блок: доля}` от ЖИВЫХ, не от попыток. `0.67` значит «у двоих из трех» |
| `cov_evidence` | `{блок: url}` - первый по позиции живой адрес с этим блоком: замер можно открыть и проверить |
| `blocks_median` | медиана блоков на живой странице. ПЕРВИЧНАЯ ЕДИНИЦА ОБЪЕМА |
| `chars_median` | медиана знаков. Справка «у лидеров столько», а не цель |
| `order` | блоки по медианному рангу; ничьи разводит порядок `pages.yml` |
| `form` | `{блок: форма}` словами: `"price":"таблица 3 строк"`, `"cta_form":"форма 3 полей"` |
| `extra` | `[{name, pages}]` - то, чего в `pages.yml` нет: `{"name":"калькулятор стоимости","pages":3}` |
| `tainted` | ВСЕ числа лидеров. Форму и состав с рынка берем, цифры - никогда: список грепается по собранному сайту в финале |
| `pages` | `[{url, pos, chars, blocks[]}]` - что именно нашли на каждом живом адресе |

```json
{"v":1,"cluster":"service","at":"2026-09-16","attempted":4,"alive":3,"measured":true,
 "cov":{"hero":1,"scope":1,"fit":1,"price":1,"steps":1,"cases":1,"reviews":1,"qa":1,"cta_form":1},
 "cov_evidence":{"price":"https://a-remont.ru/vannaya/"},
 "blocks_median":9,"chars_median":1321,
 "order":["hero","scope","price","steps","fit","cases","reviews","qa","cta_form"],
 "form":{"price":"таблица 3 строк","steps":"5 шагов"},
 "extra":[{"name":"калькулятор стоимости","pages":3}],
 "tainted":["1200 руб","14 дней","2400 руб","4 кв м"],
 "pages":[{"url":"https://a-remont.ru/vannaya/","pos":1,"chars":1321,"blocks":["hero","scope","price"]}]}
```

Глубину задает `business.site_kind`, заказчик не присылает ничего: `landing` - 3 адреса
одним кластером (блоки лендингов однородны, скелет из `pages.yml`), `multipage` - кластер
на тип страницы по 8 адресов. При `tier: basic` платные инструменты не вызываются вовсе,
адреса берутся из `competitors.list`. Кэш по маркеру и региону живет 14 дней; записанный
в проект замер заморожен: иначе план страницы перестает быть воспроизводимым.

## 2. `plan.json` - состав страниц арифметикой

Пишет `plan.mjs`, читают задание автору, `verify-page.mjs` и `lift.mjs`. Один и тот же
замер обязан давать байт-в-байт тот же план.

```json
{"v":1,"slug":"nevskiy","at":"2026-09-16","pages":[{
 "page":{"slug":"remont-vannoy-komnaty-klyuch","type":"service",
         "marker":"ремонт ванной комнаты","url":"/remont-vannoy-komnaty-klyuch/"},
 "bud":9,"measured":true,"cluster":"service",
 "blocks":[
  {"id":"hero","ord":1,"mode":"work","needs":"число","answers_with":["f03"]},
  {"id":"scope","ord":2,"mode":"work","needs":"состав","answers_with":["f07","f08"]},
  {"id":"price","ord":3,"mode":"tmpl","needs":"условие","answers_with":[]},
  {"id":"docs","ord":0,"mode":"stub","needs":"число","answers_with":[]}]}]}
```

Верхние поля: `v`, `slug`, `at`, `site_kind`, `pages`, `later` (страницы, чей тип этот
срез не ведет: без них список читался бы как потерянные адреса; сейчас список пуст - тракт
берет все семь типов) и `warnings` (что не сошлось в составе).

- `page` - из `pages.json`. Адрес справочный: писать его в текст автор не может, адреса
  делает слаг-движок.
- `bud` - ЧИСЛО БЛОКОВ: медиана живых лидеров, зажатая в вилку типа страницы, потолок 12.
  Вилка - константа `VOL` в `plan.mjs`, знаки вторичны:

  | тип | вилка блоков |
  |---|---|
  | `landing` | 8-12 |
  | `home` | 6-10 |
  | `service` | 6-11, а при `from_catalog` (узел `service_like`) - 4-6 |
  | `category` | 4-6 |
  | `facet` | 3-5 |
  | `product` | 5-8 |
  | `info` | 3-7 |

  Каталожные вилки КОРОТКИЕ намеренно: центр тяжести категории не текст, ее ранжируют
  ассортимент, цены, наличие и доставка, а полотно под листингом - прямой риск фильтра за
  переспам. Кластер замера у каталожных типов пуст: рынок узла уже замерен
  `catalog.mjs mode` по маркеру категории, и второй замер того же рынка дал бы два места,
  решающих одно.

  Признак ниши `urgent` опускает верх вилки на два блока (`SIG_SHORT` в `plan.mjs`): в
  аварийной нише выбирают за час, и длинная страница там работает против себя.
- `ord` - место в странице. У снятого блока `ord: 0`.
- `cut` и `ask` - только у снятого блока: причина снятия и вопрос заказчику, рожденный
  этим снятием. Вопрос лежит в файле, а не в консоли: иначе третий исход пустой фактуры
  («всплывет, когда фактура появится») не наступает никогда. Собирает их
  `assemble.mjs --ask` вместе со строками `недостает:` из хвостов страниц.
- `needs` - одно из пяти значений `pages.yml` ПОСЛЕ деградации: R6 понижает тип ответа по
  лестнице (число -> условие -> состав; действие -> состав; граница и состав не
  понижаются), затем режим шаблона, затем снятие.
- `mode`: `work` - фактура есть, блок пишется целиком; `tmpl` - блок идет по своему
  FALLBACK из `pages.yml` (короче и без числа); `stub` - блок СНЯТ, на страницу не идет;
  строка остается, чтобы его вопрос ушел заказчику.
- `answers_with` - чем блок отвечает: `fNN` - id факта с `publish: "yes"`; `oN.M` -
  возражение M у сегмента N. Пусто при `work` быть не может.

Правил состава ровно шесть, они лежат в `plan.mjs` константой, тест валит сборку на
седьмом: **R1** покрытие от 0.6 - блок в ядро даже при опциональности; **R2** покрытие до
0.2 и блок опционален - снять, но блок, чей признак найден у двух живых лидеров,
демотируется в `tmpl`; **R3** блок `core` не снимается, блок без рынка остается как
отстройка и такой один; **R4** объем - число блоков; **R5** порядок - медианный ранг,
остальные встают на место из `pages.yml`; **R6** деградация.

## 3. `tasks/<slug>.md` - задание автору

Автор один, пишет страницу целиком, за один проход. Он видит ровно это и в этом порядке:

1. **МЫСЛЬ** - одна строка: что страница доказывает.
2. **СОСТАВ** - таблица из `plan.json`, колонки ровно такие:
   `ord | id | вопрос читателя | что ответ делает | ориентир знаков | форма у лидеров |
   чем закрываем | режим/ответ`. Ориентир знаков - колонка ЗНАКИ из `pages.yml`, та же
   линейка, по которой потом предупреждает `chars_norm`: судить автора по норме, которой
   он не видел, значит вернуть текст в ячейку.
3. **МАТЕРИАЛ** - `project.json` целиком, тезисы соседних страниц (`theses.md`), строка
   лидеров по своему кластеру: `cov`, `order`, `form`, `blocks_median`.
4. **ПОТОЛКИ** - счетчики числами.

Метатегов в задании НЕТ: их считает формула и кладет в `tasks/meta.json`, оттуда их берет
`assemble.mjs`. Автор их не пишет, и место в потолке инструкций на них не тратится.

Потолка два: ИНСТРУКЦИИ (`site-author.md` + `AUTHOR.md` + задание) не больше 12000 знаков,
из них запретов не больше 2500; МАТЕРИАЛ (`project.json` + тезисы + строка лидеров) не
больше 16000. Общего потолка не хватило бы: один `project.json` на хорошо заполненном
проекте - 15000 знаков.

Пропорция считается ДВУМЯ мерками, и они не взаимозаменяемы:

| мерка | что значит | исход |
|---|---|---|
| материала больше, чем ЗАДАНИЯ | задание пишет сам конвейер, и в v7 автору приезжало 32982 знака собранного задания | exit 1, чинится усушкой входа |
| материала больше, чем ВСЕХ инструкций | методичка на всех страницах одна и на пустом проекте весит столько же, сколько на полном | предупреждение с названной причиной |

Вторая мерка при потолках 12000 и 16000 может не сойтись только от тонкого контракта -
это факт о ПРОЕКТЕ, а не дефект слоя письма. Ронять им сборку значит требовать фактуру
ценой несобираемого сайта, а недостающее и так уже лежит в `gaps` и в вопросах заказчику.

Чего в задании нет: цифр лидеров (`tainted` автору не показывается), стоп-листов и
типографики. Все, что ловится грепом, живет в `verify-page.mjs`: место в промте дорогое,
а машина проверяет это дешевле и надежнее.

## 4. `pages/<slug>.md` - страница

Страница - упорядоченные ответы на вопросы читателя: над разделом машиночитаемая метка,
заголовок раздела - ОТВЕТ, а не ярлык секции.

```markdown
# Ремонт ванной под ключ за 21 день, смета по пунктам до начала работ

<!-- q:hero closes:f03 -->
Делаем ванную под ключ в Санкт-Петербурге. Замер бесплатный, смета до начала работ.

<!-- q:price closes:f03,o1.1 -->
## Цена считается от площади: 2 400 руб./м2 под ключ

<!-- q:steps closes:f11 -->
## После заявки: замер за 1 день, смета на 3 день, работа 14 дней

---
мысль: бригада видна по смете и срокам, а не по обещаниям
снят: docs - нет номера и срока действия документа
недостает: срок выезда замерщика, номер СРО
канон: монтаж под ключ; инженерная доска
слито: fit+scope
```

- `q:<id>` - вопрос, на который отвечает раздел. По умолчанию это id блока; при слиянии
  автор пишет тот, который отвечен. Метки нет или она неизвестна - ПРЕДУПРЕЖДЕНИЕ и
  позиционный фолбэк сборки, никогда не ошибка: опечатка не валит хороший текст.
- `closes:` - что раздел закрывает: `fNN` (факт), `oN.M` (возражение). Отсюда бесплатно
  берутся покрытие для `lift.mjs` и заготовка FAQ. Пересечение `closes:` двух страниц
  от 70 процентов - предупреждение «одна мысль разными словами».
- После `---` идет служебный хвост. **ПРОЗА ХВОСТА НЕ ПАРСИТСЯ НИКОГДА.** Машина читает
  ровно три формы: `снят: <id> - <причина>` (до первого ` - ` id, дальше проза),
  `слито: <a>+<b>` и `недостает: <строка>` (строка идет в список вопросов целиком и никак
  не толкуется). Строки `мысль:` и `канон:` не разбираются вовсе, и хвост целиком
  вырезается ДО всех проверок на числа. Боевой баг v7: валидатор вычитал число из
  пояснения и заблокировал живой блок.
- Жестких лимитов знаков ровно два: метатеги (70 и 160) и интро категории (500). Нормы
  блоков - предупреждение ПОСЛЕ письма: верстка собирается под текст, а не текст под ячейку.

## 5. `theses.md` - цельность сайта

Собирается детерминированно из `plan.json` и `project.json` ДО письма, одинаков для всех
авторов: в v7 писатели шли веером вслепую, и цельность потом чинилась вычитанием
самоповторов. Строка на страницу и раздел канона.

```markdown
/remont-vannoy-komnaty-klyuch/ | service | H1: Ремонт ванной комнаты под ключ |
обещание: смета по пунктам до начала работ | закрывает: price, steps, scope

## Канон
монтаж под ключ
инженерная доска
```

`H1` тут плановый: файл нужен авторам до того, как написана хоть одна страница. Канон
повторяется ДОСЛОВНО, перефразировать «чтобы не повторяться» запрещено: это ломает
узнавание, а не спасает от повтора.

## 6. `verify.json` и `lift.json` - отметки лестницы

`verify.json` пишет `verify-page.mjs` при ПОЛНОМ прогоне (с `--page` не пишет: проверка
одной страницы полной не считается), `lift.json` - `lift.mjs`. Своего состояния у конвейера
нет, оно выводится из содержимого, и эти два файла - единственный способ увидеть, что
страницу трогали после проверки.

```json
{"v":1,"at":"2026-09-16","block":0,
 "pages":[{"slug":"index","planned":true,"block":0,"warn":2}]}
```

`verify-build.mjs` отказывает, если любого из них нет или он старше самой свежей страницы.
Это не педантизм: усиление - единственный шаг, который пишет НОВЫЙ текст после проверки, и
без отметки дописанное им не встретило бы ни одного из двенадцати блокирующих правил.
